# 团队治理与评审基线

> **适用范围**：技术分册引用的规则执行级别，以及采用多人团队流程的项目治理；个人模式按下述适用方式接入。  
> **边界**：语言和平台专属规则、格式工具、技术配置、专项测试要求分别以对应分册为准。

## 0. 协作方式与记录位置

| 项目采用的方式 | 适用要求 |
| --- | --- |
| 多人团队 | 执行本文件的 R0/R1/R2、非作者评审人数、模块责任及团队批准要求。 |
| C 项目的个人+AI | 项目明确采用具体版本的 AI 协作规范，由用户确认设计与实施边界，按该规范安排自检、必要独立复审和批准；不额外套用团队非作者人数、备份与轮值要求。C 技术规则、构建测试和专项证据要求继续适用。 |

协作方式及真实确认来源只记录在项目 `PROJECT.md` 或已有项目基线中，其他入口引用。既有项目继承已采用的方式；未明确选择个人+AI 的 C 项目继续沿用团队要求，不能因一次对话只有一名用户就自行切换。LuatOS 维持其分册已采用的模式。AI 复审次数不得折算成团队非作者人数，模式切换也不降低已确认的技术验收标准。

项目基线、技术配置、检查、批准和豁免可使用已有等价记录，不强制复制模板另建文件。一次检查只记一份结果；源码、配置、范围和相关依赖仍适用时共用证据，变化后只补受影响项。

## 1. 规则执行级别与冲突优先级

- **AUTO-BLOCK**：可由格式、构建、语法或固定脚本客观检查；失败时阻断合并。自动工具尚未接入前，由作者和评审者按同一方法人工确认。
- **REVIEW-BLOCK**：需要工程判断；未满足或没有有效豁免时，评审者阻断合并。
- **ADVISORY**：团队默认做法；偏离时在评审中简要说明即可。

这些级别说明检查性质和阻断条件，不单独增加独立 AI 复审轮次。个人+AI 项目的核查和批准角色按已采用协作规范确定；自动工具未覆盖的技术项仍须核查，不能用模式选择或勾选框代替实际结果。

“必须、禁止、不得”均属于阻断规则；“应当、建议、可以”属于建议。冲突优先级为：产品安全/法规要求 > 已确认的目标硬件、固件和工具链限制 > 对应语言分册 > 个人习惯。

每个分册使用自己的稳定规则 ID（C 为 `GOV-*`、`RTOS-*` 等，LuatOS 为 `LUA-*`）。规则 ID 发布后不复用；删除时保留删除原因和历史记录。

## 2. 多人团队的 R0/R1/R2 风险与评审

| 等级 | 通用判定 | 最低评审 | 最低证据 |
| --- | --- | --- | --- |
| R0 | 文档、注释、纯格式，不改变打包/构建产物或运行行为 | 1 名非作者 | 格式/文档检查；修改代码文件时完成对应语言的基础语法或构建检查 |
| R1 | 常规自研逻辑、驱动/服务、解析、缺陷修复或可控接口变更 | 1 名非作者 | 受影响配置的基础检查，以及与风险匹配的正常、边界、失败路径测试 |
| R2 | 平台/启动基线、打包或构建链、持久化/升级、物理硬件或电源、并发/任务框架、安全/远控、协议兼容、资源预算等高风险变更 | 2 名非作者，其中至少 1 名为模块主负责人或备份 | R1 全部要求；目标组合证据，以及故障恢复、掉电、回滚或安全测试中适用项 |

不能确定时按较高等级执行。各分册的 R2 具体触发项见其主规范和合并检查表；不得通过将紧急修复标记为 R0 来规避验证。

## 3. 多人团队的评审与证据要求

1. 作者在评审记录中写明风险等级、受影响模块、目标组合、验证步骤与结果、资源变化、兼容性/回滚影响和豁免编号。
2. 模块负责人不拥有跳过评审的特权；R2 必须由两名非作者核验，作者不得自批。
3. 证据必须区分主机/模拟、语法/打包、构建与真实目标板验证。能通过编译或语法检查不等于功能验证。
4. 人工新增/修改超过 300 行或涉及超过 8 个代码文件时，作者与评审者应先讨论拆分。这是评审负荷提醒，不是机械门禁。
5. 上游、厂商、生成代码和机械格式化改动必须与自研功能改动分开；不得为了格式而重排上游文件。

## 4. 试运行、复盘与正式化

- 新分册或重大规则调整先试运行 4 周，记录误报、过期豁免、评审等待、资源异常和发布后缺陷。
- 每季度或重大事故后复盘规则是否仍有收益；无收益规则可删除，但保留原 ID 和删除原因。
- 正式发布前，项目基线、技术配置及所采用流程要求的责任和批准字段必须完整；可引用现有记录，不要求另建模板实例。多人团队仍须覆盖 [模块责任与轮值模板](模块责任与轮值模板.md) 中的适用角色要求。
