# 规则豁免与紧急修复流程

适用方式见 [治理基线](团队治理与评审基线.md)。团队人数、非作者和轮值要求用于多人团队；C 个人+AI 项目按已采用协作规范履行用户确认和必要独立复审。技术验证、证据、到期和回滚要求继续适用。以下字段可写入现有里程碑或事件记录，不强制另建表单。

## 1. 规则豁免

豁免用于暂时无法满足明确规则的情况，不用于跳过测试、掩盖缺陷或长期保留无负责人债务。

### 批准和到期

- 多人团队的 R0/R1 豁免：至少由 1 名非作者评审，并由模块主负责人或备份批准。
- 多人团队的 R2 豁免：至少由 2 名非作者评审，其中 1 名为模块主负责人或备份。
- C 个人+AI 的豁免：保留规则、范围、风险、替代控制、到期日和用户真实批准，按已采用协作规范完成必要复审；不得取消其红线任务的最终验收要求。
- 豁免必须在代码评审记录和受影响代码附近使用编号互相引用。
- 责任人按到期日维护豁免，团队轮值规范维护人每月汇总检查；到期前必须删除、续期或转为正式设计决策。
- 续期必须重新评估风险、替代措施和根治日期，不能只修改到期日。

## 2. 紧急修复适用条件

仅在生产中断、设备不可用、数据/安全风险或即将造成重大交付损失时使用。普通排期压力不属于紧急修复。

## 3. 紧急修复最小流程

1. **登记事件**：记录现象、影响范围、目标固件/硬件版本、事件负责人和批准人。
2. **冻结范围**：只修改恢复服务所需内容；禁止顺带重构、批量格式化或升级工具链。
3. **准备回滚**：保存当前可用固件、配置和烧录方式，明确回滚负责人及触发条件。
4. **完成最低验证**：受影响配置 clean build、零新增警告、针对性测试和目标板冒烟测试必须完成。
5. **核对专项风险**：涉及 Boot/OTA/存储/IRQ/看门狗时，至少验证地址边界、完整性、失败恢复或掉电场景中与故障直接相关的项目。
6. **履行批准要求**：多人团队发布前至少由 1 名非作者检查补丁、构建证据、目标版本和回滚方案；确实无法完成时必须由事件批准人书面接受风险。C 个人+AI 按已采用协作规范完成批准和必要独立复审，不得把自检写成独立复审。
7. **可追溯发布**：记录提交号、工具链、目标硬件、二进制 SHA-256、发布时间、发布人、设备范围和验证结果。
8. **发布后观察**：明确监控指标、观察时长、异常阈值和回滚决定人。

## 4. 下一工作日补齐

紧急修复发布后的下一个工作日内，事件负责人必须：

- [ ] 补齐所采用流程规定的检查和复审；多人团队还须补齐正常 R1/R2 评审人数。已有等价记录可引用。
- [ ] 完成此前跳过的回归、边界、失败、掉电或回滚测试。
- [ ] 将临时补丁整理为可维护方案；仍需保留例外时登记正式豁免。
- [ ] 核对所有发布设备/批次的版本和运行结果，处理失败或遗漏设备。
- [ ] 记录根因、为何现有测试未发现、为何现有门禁未阻止及后续责任人。
- [ ] 更新测试用例、项目配置或团队规则；不需要修改时也记录理由。

无法在下一工作日完成的项目，必须写明负责人、风险和新的明确截止日期，并由项目负责人批准。
