## 1. 核心抽象

- **a/b/c/d/e 是角色槽，不是固定进程**。A 在整个阶段保持连续；其他角色按任务需要启用。新里程碑可新开会话，同一里程碑内的修正与复测沿用对应会话；中途换人时在已有任务记录中写清当前对象、剩余项和续接入口。
- **阶段决定职责**：编码阶段不使用 E；测试阶段预留五个角色，有现成候选和用例时 B、D 可先待命。
- **用户是最终决策者**：B 产出的所有方案（编码方案、测试方案、用例方案、失败修改方案）必须经用户拍板。获批方案与白名单内的实现纠错、既定复测可继续；改变方案、接口、产品行为或范围时回 B 并重新由用户拍板。Git 推送、上机等授权沿项目既有约定。
- **A 统一维护进度与调度**：用户启用 A 后，A 在已授权范围内派发、转交和收口；其他 AI 不自行接管 A。B 可把获批任务直接交 D，同时通知 A；所有角色的完成、失败和阻断都回报 A。A 不替用户作产品决策。

共通职责只维护在下表；后续阶段只写流程与特有边界。

| 角色 | 唯一职责说明 |
|---|---|
| A | 维护范围、派发、进度和收口；用户决定产品方案与授权，A 在已授权范围内调度 |
| B | 补必要方案、接口和用例方案；结合源码与现场证据分析生产功能失败；所有方案由用户拍板 |
| C | 审核实现、自检与测试证据；测试阶段可直接修正现有用例说明或脚本，通知 A、E；不直接修改生产代码 |
| D | 按获批方案实现生产代码和初次测试脚本，完成基本自检后交 C 审核，回报 A |
| E | 按获批用例执行测试、采集证据、回报 A 并交 C 复核；用例有误直接告诉 C，同时通知 A，修正后针对复测 |

## 2. 会话命名与登记

- 会话名：`<版本>-<阶段>-<角色>[-<里程碑>]`，按项目已有命名约定使用。
- 每个项目复用一处有效会话登记入口，当前绑定随实际创建或换会话更新，旧绑定进入已有历史记录。通用协议与命令表只保留 `<会话ID>` 模板。
- 新建后登记工具实际返回的完整原生 ID；续接使用明确 ID 和正确入口，不按显示名或最近会话猜测。

| 角色 | 当前任务 / 里程碑 | Agent / 入口 | 实际工作目录 | 原生会话 ID | 实际模型 / 思考设置 | 状态 |
|---|---|---|---|---|---|---|

## 4. 编码阶段（E 不使用）

前提：用户与 AI 确定总体设计方案和具体里程碑划分后启用本工作流。任务划分沿用项目已确认的规则和任务卡，本文件不复制技术设计。Agent、模型与思考目标只看 §3。

流程：

```text
用户确定了总体方案与里程碑
  → A 启用调度
  → B 补当前里程碑下具体设计方案 → 用户拍板 → B 交 D，同时通知 A
  → D 实现+自检 → C 审核 → 通过：报告 A，由 A 安排下一包 / 集成
                          → 实现缺陷、漏功能或交付证据不足：退 D
                          → 设计或接口契约冲突：退 B，改方案仍需用户拍板
```

## 5. 测试阶段（新增 E）

前提：用户与 AI 确定总体测试方案、里程碑划分和测试用例后启用。新增用例由 B 出方案、用户拍板、D 实现测试脚本、C 审核、E 执行；现有用例说明或脚本有错误时，C 依据已确认的测试目标直接修正，通知 A、E，由 E 复测受影响用例，无需再绕 B、D。已有候选和用例可直接交 E，不为切换角色重复实现或重审已通过的软件。Agent、模型与思考目标只看 §3。

流程（含失败回路）：

```text
用户确定了测试方案/里程碑/用例
  → A 启用调度
  → 已有候选与用例：直接 E 测试
  → 需要补方案或实现：B 出方案 → 用户拍板 → D 实现+自检 → C 审核 → E 测试
E 测试 → 所有结果报告 A，并把本轮证据交 C 复核
       → 通过且 C 复核认可：A 核对本阶段剩余项，收口并安排下一步
       → 生产功能不符：A 交 B 分析并给修改方案 → 用户拍板 → D 修改 → C 审核 → E 针对复测
       → 用例说明/脚本错误：E 告诉 C，同时通知 A → C 直接修正，通知 A、E → E 针对复测
       → 环境/工具阻断：A 按已有恢复步骤安排处理
       → 证据不足：A 安排 E 补证；未执行项保留待测
```

结果区分「通过 / 功能失败 / 环境或工具阻断 / 未测」；证据不足写「待补证」，不判通过。通过按用例的预期行为判断，预期拒绝升级等负向用例也可通过。用例自身错误按用例修正分支处理；C 在审核时发现也直接修正并通知 A、E。生产功能失败由 B 基于源码和现场证据分析，不默认要求测试期 D 参与原代码定位。一般优化按项目版本深度进入后续清单。

## 6. 移交关系速查

**任务指令与结果报告分开写**：A 向指定角色派发流程任务；各角色向 A 报告实际结果，A 据此更新进度、决定并安排下一动作。B → D、D → C 等直接交接是已授权任务的接续，同时通知 A，A 不重复派发同一项工作。

| 从 → 到 | 条件 | 交接物 |
|---|---|---|
| A → 各角色 | 已授权任务需要执行或续接 | 本轮范围、对象、允许操作、完成条件与回报目标 |
| B → D | 方案经用户拍板后（直接交 D，同时通知 A） | 获批方案、白名单、完成条件 |
| D → C | 实现完成（强制） | 改动清单、自检证据、候选 |
| C → E | 审核通过（测试阶段） | 待测项、用例、环境 |
| C → D | 生产实现缺陷、漏功能或 D 交付证据不足 | 问题与所需补交项 |
| C → B | 设计或接口契约冲突 | 冲突点与依据 |
| E → A | 测试完成、失败、阻断或需补证 | 结果、原始证据、未测项和下一动作 |
| E → C | 本轮测试结果待复核 | 所测候选、用例、判定与原始证据 |
| E → C | 发现现有用例问题（同时通知 A） | 错误步骤、断言或脚本位置及现场证据 |
| C → E | 用例已直接修正（同时通知 A） | 修正位置、依据与需复测的用例 |
| C → A | 实现审核或测试证据复核结束 | 结论、对象、剩余项与建议下一动作 |
| A → B | 生产功能不符合预期 | 失败现象、所测版本、现场日志与现有源码入口 |
| B → A | 分析需要补充观测 | 需要 E 补充的步骤、观察点或日志 |
| B → 用户 | 任何方案产出 | 方案正文（待拍板） |

交接注明任务与轮次、实际工作目录和代码/镜像/用例版本、允许范围、完成条件或结果、证据和剩余项；方案批准入口等已有文件能表达的直接引用。

- **同一结果不重复派发**：各角色向 A 发送一句结论和本轮独立记录的链接。A 收到后更新状态，按结果安排后续任务；同一份记录再次通知时确认收到即可，不重复派发已经安排过的任务。使用现有记录文件和轮次识别，不额外增加交付 ID 或登记表。
- **报告写清所审、所测版本**：生产代码或镜像变化时，C 复核相关差异与受影响路径；现有用例修错由 C 直接处理并交 E 针对复测。旧结论保留原覆盖范围。

## 7. 与项目文档的关系

- 项目任务划分、Git/板测授权、已确认技术契约、白名单归属和融合要求沿项目现行体系；启用时只调整必要的角色与执行入口，复用已有状态、报告和证据文件。
- **同一文件同时只有一个写入者**：A 维护当前状态，B 维护获批设计，D 维护生产代码、初次实现的测试脚本和融合说明，C 维护审核报告并接续现有用例修错，E 维护测试报告和原始证据。用例修错期间其他角色暂停写入同一文件，E 待修正后复测；公共索引和 Git 写操作串行，保留其他改动。
- **同一板卡同时只有一个执行者**：E 执行测试期间独占板卡、串口、SWD 及相关资源；D 需要上板定位时由 A 明确移交，结束后交回 E。文件不重叠也不能并行操作同一板卡。
