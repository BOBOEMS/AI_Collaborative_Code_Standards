# 嵌入式 AI 协作开发规范（EAI-DP）

版本：V1.2（试行）  
适用对象：MCU、RTU、BootLoader、驱动、RTOS、通信协议、低功耗和配套 PC 工具  
适用工具：Aider、Codex、Claude Code、GitHub Copilot 及其他能读写代码的 AI Agent

## 0. 一句话协议

> 人负责冻结“系统应该怎样工作、哪些边界不能碰、怎样才算通过”；AI 负责理解工程、提出方案、完成局部实现、运行可用的验证并整理证据。任何新增的可观察行为，都不得由 AI 静默决定。

本规范解决的不是“如何让 AI 写更多代码”，而是把人的审查从“反向猜代码”变成“审设计、审关键路径、审证据”。用户不需要把每个函数和 `if` 写进提示词；AI 必须把它自行补全的关键决定显式列出来。

## 1. 规范用语与职责

本规范中：

- **必须 / 不得**：违反后暂停当前任务，不能以“代码能编译”为理由跳过。
- **应**：默认采用；确有理由偏离时，在交付报告中说明。
- **可**：按项目实际情况采用。
- **行为变化**：外部接口、协议字节、状态、时序、错误码、重试、超时、资源占用、功耗、复位或恢复方式的任何变化。
- **证据**：可复查的命令、日志、测试输出、测量值、Map 文件、板端现象或录屏；“看起来没问题”不是证据。
- **生产文件**：参与交付固件、配套 PC 工具或生产配置的源码、头文件、启动文件、链接文件和配置文件；测试、纯文档和临时分析脚本不计入。
- **有效生产代码**：新增或改变语义的生产代码；空行、纯注释、纯格式变化和自动生成结果不计入，但生成源文件或工程配置的变化必须单独报告。
- **模块**：拥有独立职责和接口边界、可单独说明输入输出的子系统；目录数量不等于模块数量。
- **修改前基线**：在本次改变前，对实际源码、构建配置、告警、资源和测试状态留下的可复查记录。
- **批准范围**：用户已经批准的方案版本、行为边界、允许实施的切片、验证方式和操作权限；以可追溯的用户原话、Issue、PR 或其他明确记录为准。

### 1.1 人负责什么

对于本次变化涉及的部分，人必须掌握并批准：

- 对外可观察行为和验收标准；
- 模块边界、状态机、数据所有权和关键时序；
- 协议、Flash/EEPROM/FRAM 数据格式及兼容策略；
- RAM、Flash、栈、CPU、延迟、启动时间和功耗预算；
- 失败、超时、复位、掉电、回滚和安全策略；
- 目标板、真实外设和生产环境的最终验收。

AI 必须先把相关系统模型压缩成可审查的状态、数据、时序和失败路径，并说明它与未修改部分的连接；不得要求人重新理解整个工程后才能批准一个局部任务。

### 1.2 AI 可以决定什么

在已批准的范围内，AI 可以自行决定：

- 局部函数如何拆分；
- 局部变量和内部辅助函数如何命名；
- 重复性代码和不影响生产构建的测试样板如何实现；
- 已冻结格式和边界条件的局部解析如何实现；
- 已批准的普通日志如何实现，但 ISR、实时路径、低功耗路径和线上协议中的日志不属于普通日志；
- 如何调用已有接口、复用已有模式；
- 如何组织不改变行为的局部重构。

如果一个决定可能改变系统行为，AI 必须把它列入“需要确认”或“建议项”，不能因为它看起来更健壮、更优雅就直接加入。

## 2. 最小文档集：一份长期规则 + 一张任务卡

不要为每个小修改创建一套厚重文档。默认只保留：

```text
AGENTS.md              项目长期规则，尽量控制在一页左右
任务卡                 当前任务的目标、边界和验收，放在聊天、Issue 或 PR 中
DECISIONS.md           只有长期架构决定才记录
```

可直接从 [AGENTS.md 模板](./embedded-ai-agents-template.md) 和 [任务卡模板](./embedded-ai-task-card-template.md) 开始。对需要追溯的红色任务，再把任务卡扩展为 `FEATURE_SPEC.md` 和 `IMPLEMENTATION_PLAN.md`。普通函数拆分、命名和局部实现不需要写入长期文档。

### 2.1 `AGENTS.md` 应该写什么

只写跨任务仍然有效、且删掉后容易造成错误的内容：

- 芯片、板卡、编译器、RTOS 和构建入口；
- 目录结构和模块职责；
- C/Lua 等语言规范的链接，不要把全部语言规则复制进来；
- ISR、DMA、任务、队列、锁和缓冲区所有权规则；
- BootLoader、OTA、NVM、协议、低功耗、看门狗和资源红线；
- 可直接修改、必须先方案、必须设计冻结的权限边界；
- 编译、主机测试、板端测试的入口和完成声明规则；
- 真实发生过的 AI 失误及对应的短规则。

不要把 API 手册、逐文件说明、长教程和经常变化的事项塞进 `AGENTS.md`。需要时用链接或按目录放置更具体的 `AGENTS.md`。

## 3. AI 权限分级

AI 必须在开始修改前自行判级；同一任务命中多个等级时按最高等级执行。AI 可以主动升级，不能自行降级。

| 等级 | 名称 | 典型任务 | AI 权限 | 编码前门槛 |
|---|---|---|---|---|
| A0 | 只读分析 | 分析、定位、审查、诊断、先给方案；用户未明确要求修改 | 读文件、追踪调用链、运行非破坏性检查、给出假设和测量方案 | 不得改变受版本控制的源码、配置和文档；允许在指定输出目录产生可丢弃的构建产物 |
| A1 | 直接修改 | 一个局部行为；不超过 2 个生产文件；不超过约 80 行有效生产代码；不触及红线 | 修改、编译/测试、自审、提交交付卡 | 任务卡中的完成标准明确，且不存在影响行为的未决问题 |
| A2 | 方案后修改 | 未触及红线的驱动内部行为、内部协议处理、内部接口、多文件变更、新增普通状态、约 80–250 行有效生产代码 | 先探索并提交微型方案；批准后只实施批准的切片 | 人批准范围、行为、构建矩阵和验证方式 |
| A3 | 设计冻结后修改 | BootLoader、OTA、NVM、硬件/寄存器配置、ISR/DMA、RTOS 并发、低功耗、看门狗、安全、对外协议/数据格式、关键资源或时序 | 与人共同冻结设计，再按独立行为分片实现 | 人明确批准设计冻结卡；目标板验收不能省略 |

补充规则：

- “改一行分区地址、优先级或有效标志”仍然是 A3；风险由行为决定，不由行数决定。
- 表中的任务类型只是例子，任何 A1/A2 任务只要命中 A3 红线，必须立即按 A3 执行。
- 改变线上字节、GPIO/电源默认状态、时钟、复位、模拟阈值、关键寄存器或实时/功耗行为的驱动和协议任务都是 A3。
- 在 ISR、实时链路或低功耗链路增加日志，可能改变时序、阻塞和功耗，应按 A3 评估。
- 需求存在会影响架构、兼容性、安全、并发、资源或验证的歧义时，不得边猜边写。
- “分析、解释、审查、诊断”默认是 A0；只有用户明确要求改变代码时才进入修改等级。
- A1 的行数和文件数是复核预算，不是质量保证；达到阈值应升级，不得为了过阈值而制造碎片化提交。

### 3.1 与团队风险和证据等级的关系

`A0–A3`、团队评审等级和 `E0–E4` 分别回答不同问题：

- `A0–A3`：本次任务中 AI 可以直接做什么，何时需要先提交方案并由人批准；
- `R0–R2`（项目采用[共享治理](../共享/团队治理与评审基线.md)时）：变更需要多少人工评审以及哪些团队门禁；
- `E0–E4`：某个验收结论实际获得了什么环境和强度的证据。

三者不得机械换算。A0 可以分析一个 R2 高风险问题；A1 的“AI 自审即可”不能取消项目要求的人工评审；A3 也不会因为做过独立 AI 复审就自动获得 E3/E4 证据。项目未采用 `R0–R2` 时，仍执行本规范的 A、E 两套规则及项目自身的人工评审要求。

## 4. 固定工作流

```text
任务卡
  → 确认实际源码树、版本、目标板和生效配置
  → 采集修改前基线和受影响的构建配置矩阵
  → 判定 A0/A1/A2/A3
  → 读取相关实现并画出当前调用链/数据流
  → A2/A3 提交微型方案或设计冻结卡
  → 人批准方案版本、关键行为、允许实施的切片和汇报检查点
  → 按可独立验收的行为拆片
  → AI 实施批准范围内的切片，每片完成编译/测试/AI 自审
  → 到达汇报检查点后，按 A1/A2/A3 要求执行自审或独立上下文复审
  → 人在约定检查点审行为、关键路径和证据
  → 继续已批准的下一阶段或执行板级验收
```

历史目录、旧版本、旧日志和文档只能作为参考，不能自动继承当前项目的地址、协议、引脚、时序或硬件结论。开始前必须明确当前实际生效的文件和构建配置。

### 4.1 编码前基线

A2/A3 在编码前必须记录；A1 在条件允许时应记录：

1. 当前仓库、分支/提交、工作区未提交修改，以及实际生效的源码目录；
2. 产品型号、板卡/PCB 版本、模块型号和影响本任务的 BOM 差异；
3. 编译器、SDK、RTOS、优化等级，以及相关数据手册和勘误版本；
4. 受影响的构建矩阵：板型、功能宏、Boot/App、Debug/Release 等组合；
5. 当前目标构建、错误/告警、ROM/RAM/镜像尺寸和已有测试结果；
6. 无法采集的项目及原因。

基线失败不等于本次修改造成失败，但不能被写成“目标构建通过”。AI 必须把历史失败与本次新增回归分开报告。A2/A3 的规定目标在修改前已经构建失败时，编码前必须选择并记录以下一种处理方式：先用独立切片修复基线；或由用户批准“已知失败基线”、可继续的工作范围和替代检查。采用已知失败基线时，本次不得新增错误或扩大原失败，交付状态必须写“目标构建未通过”，且不得合并、发布或进入依赖该构建结果的后续切片。无法确认实际版本或构建目标时，应提高风险等级并暂停会受其影响的实现决定。

### 4.2 A0：只读探索输出

A0 至少输出：

1. 当前实现入口和调用链；
2. 已确认事实、AI 推断、仍需实测的内容；
3. 影响行为的歧义；
4. 建议的修改范围和风险等级；
5. 可以在 PC/静态环境完成的检查，以及必须上板的检查。
6. 已取得的基线及仍无法确认的版本/配置。

没有用户授权时，A0 不得顺手修改受版本控制的源码、配置和文档；构建产物必须放在项目约定或临时输出目录，不得覆盖用户交付物。

### 4.3 A2：微型方案

方案控制在一屏左右，回答“改什么、保持什么、如何证明”，不提前设计每一行代码：

```text
方案标识/版本：
任务级别：
需求理解：
修改前基线：
当前调用链/数据流：
行为将发生什么变化：
明确保持不变：
本次不做：
正常路径：
异常、超时和恢复路径：
预计修改文件：
受影响的构建配置：
资源影响：
验证办法：
需要我确认的决定：
AI 建议但不实施的额外逻辑：
允许连续实施的切片与汇报检查点：
```

### 4.4 A3：设计冻结卡

设计冻结卡应明确系统模型，而不是罗列函数：

```text
【设计冻结卡】
方案标识/版本：
目标：
当前仓库/提交/实际源码目录：
板卡/PCB/模块/BOM 版本：
编译器/SDK/RTOS/优化等级：
相关数据手册/勘误版本：
修改前构建、告警、资源和测试基线：
不做什么：
必须保持不变：
接口、状态和数据所有权：
正常路径：
错误、超时、复位和掉电路径：
兼容性要求：
资源和时序预算：
受影响的构建配置矩阵：
任务切片及依赖：
允许连续实施的切片与汇报检查点：
每个验收项要求达到的证据等级：
仍未确认的事实：
```

冻结后，AI 不得自行改变接口、状态、数据格式、任务模型、重试/超时/恢复策略或资源预算。发现必须改变时，暂停当前切片，提交“设计变更”，说明原因、影响和替代方案，等待确认。

用户批准某一方案版本和允许实施的切片后，该批准在对应范围内持续有效。AI 应按约定连续实施并在指定检查点汇报，不得对冻结卡内已经明确批准的文件、行为或高风险面重复请求批准。只有出现计划外变化、原批准所依赖的事实失效，或需要新增不可逆操作权限时，才重新确认。

## 5. 任务切片与停止条件

切片单位是“一个能独立说明、独立验证、独立回退的行为”，不是一个函数，也不是一个文件。示例：

```text
先实现 ACK 过滤并通过 PC 日志回放
再实现超时恢复并通过异常帧测试
最后做目标板干扰测试
```

默认一个切片：

- 只解决一个可观察行为或一个失败边界；
- 不超过 3 个生产文件、约 200 行有效生产代码；
- 修改前目标构建通过时，结束时必须保持该目标构建通过；采用已批准的“已知失败基线”时，必须满足 4.1 节的限制；
- 不夹带格式化、清理、未来扩展或无关重构。

80/200/250 行和文件数量是拆分与评审负荷提醒，不是质量评分，也不能覆盖 A3 红线。A1 超出其范围时必须升级为 A2/A3；已经批准的 A2/A3 切片仅因实际行数变化不重复审批，但应在交付卡解释明显偏差，并确认行为仍可独立审查和回退。经明确批准的脚手架阶段可以暂时不可构建，但必须单独标记为“不可交付”，不得进入下一实现切片或合并，直到规定目标重新构建通过。

下列规模信号要求 AI 重新评估切片，并在交付卡说明是否需要拆分；只有因此无法维持已批准的行为边界、独立验证或独立回退时，才暂停并重新确认：

- 预计超过 5 个生产文件、250 行有效生产代码或 2 个模块；
- 同时包含超过 2 个可独立验收的行为；
- 同时改变两个高风险面，例如“升级协议 + Flash 布局”；
- 实际修改量明显超过方案估计。

出现以下任一实质偏离时，AI 必须暂停受影响的实现并重新确认：

- 新增计划外生产文件、状态、任务、队列、定时器、重试、超时或恢复策略；
- 需要修改批准范围外的公共接口、协议字段、Flash 布局、链接地址或生成/厂商文件；
- 状态、数据所有权、时序、失败/恢复、兼容性、资源预算或验证方法超出批准范围；
- 原批准所依赖的源码、硬件版本、构建配置或其他基线事实已经失效；
- 冻结卡要求的关键验证无法执行，且继续实现会依赖对硬件行为的猜测；
- 为修复当前问题必须进行无关重构。

高风险功能确实需要跨两个领域时，应先分别完成可验证的基础切片，再做明确的集成切片，而不是让 AI 一次铺开全部实现。

## 6. 嵌入式红线（A3）

以下事项不得由 AI 静默决定。表中的“最低要求”是设计冻结和验收时至少要回答的问题。

| 领域 | 不得静默决定的内容 | 最低设计/验证要求 |
|---|---|---|
| BootLoader / OTA | 分区地址、向量、镜像有效条件、校验顺序、安装时机、回滚、版本/降级、最大镜像 | 明确状态与有效标志；验证损坏镜像、空间边界、复位/掉电、旧镜像保留 |
| Flash / EEPROM / FRAM | 数据格式、版本迁移、擦写粒度、原子提交、CRC、寿命和磨损均衡 | 给出布局、提交顺序和掉电中断点；验证断电恢复、重复写入和容量边界 |
| 硬件接口 / 寄存器 | 引脚复用、时钟树、复位、启动电平、电源轨、ADC/DAC 阈值、校准参数、PWM/执行器和关键寄存器 | 引用实际数据手册/勘误；列出寄存器和默认状态变化；验证上电、复位、掉电、故障安全状态及必要的示波器/逻辑分析仪/万用表结果 |
| ISR / DMA | ISR 可调用 API、缓冲区所有权、生命周期、完成/错误/中止路径、原子性、缓存/对齐/屏障 | 画出所有权转移；验证高负载、竞争、超时、重复使用和错误中止 |
| RTOS 并发 | 新任务、优先级、栈、锁/队列、阻塞、锁顺序、ISR-safe API、死锁恢复 | 给出任务/资源关系；检查栈余量、队列满、超时、优先级和死锁路径 |
| 通信协议 / RS485 | 线上字节、版本、长度、端序、ACK、回显/噪声、半双工切换、重试、幂等和超时 | 验证丢包、重复、错长、CRC 错、噪声、回显、乱序和超时恢复 |
| 低功耗 / 电源 | 进入条件、唤醒源、GPIO 保持、时钟和外设恢复顺序、网络/GNSS 周期 | 给出睡眠/唤醒状态；用仪器测电流并验证多次唤醒和异常唤醒 |
| 看门狗 / 恢复 | 喂狗位置、覆盖范围、启动/升级阶段行为、复位原因和恢复动作 | 验证真实卡死/超时触发复位，并检查复位后的安全状态 |
| 安全 / 安全关键控制 | 鉴权、密钥、固件可信条件、调试口、执行器默认状态和故障降级 | 明确信任边界和失败安全状态；不能用 Mock 代替关键安全验证 |
| 资源 / 实时性 | RAM、Flash、堆、栈、CPU、ISR 延迟、启动时间、功耗和增量上限 | 对比构建 Map、栈高水位、延迟/功耗基线和变化量 |

未经确认，AI 不得新增动态内存、任务、定时器、配置项、抽象层、重试机制、对外接口或恢复策略。额外想法只进入“建议项（未实施）”。

日志、参数检查和解析代码也按实际行为判级：它们一旦影响线上协议、ISR/实时路径、低功耗、资源预算或失败策略，就不是普通辅助代码，必须进入相应 A3 设计。

决定或改变 RAM、Flash、栈、CPU、时序、功耗等预算属于 A3；在已经批准的预算内测量并报告实际增量属于验证，不因数值发生小幅变化而再次升级或审批。实测超出批准预算时才按设计偏离处理。

## 7. 修改与工具边界

- 修改范围只限任务卡或冻结卡批准的文件和行为；优先复用现有接口和项目模式。
- 为理解调用链、接口契约、配置来源和验证结果，可以只读查看任务范围外的关联源码、头文件、工程配置和历史证据；不得因此修改或把无关问题纳入本次任务。
- 保留用户已有的未提交修改；发现目标文件有未知改动时先报告。
- 不修改厂商生成文件、链接脚本、启动文件、生产配置或协议常量，除非任务卡明确包含且已通过对应等级门禁。
- 编译、静态检查、主机测试和日志分析属于正常验证；擦除/写入目标板 Flash 或 EEPROM、烧录固件、修改生产设备、推送远端、删除文件和其他不可逆操作必须获得明确授权。任务卡已经明确授权具体目标、范围和次数时，在授权范围内执行无需重复询问；目标、范围、次数或风险条件变化时重新确认。
- AI 不得把“为了修复所以顺手格式化/重构”算进当前任务；若确有必要，先停下来说明影响。
- 代码、测试、文档和脚本的新增都必须说明用途；未使用的临时代码不得留在提交中。

## 8. 验证证据等级与完成声明

| 等级 | 证据 | 可以声明 | 不可以声明 |
|---|---|---|---|
| E0 | 源码阅读、调用链、静态推理 | 已定位入口/风险/可能原因 | Bug 已修复、硬件已通过 |
| E1 | 静态检查、目标编译、链接、Map、告警和镜像检查 | 目标构建/静态检查通过 | 功能、时序、功耗或板端通过 |
| E2 | PC 单测、Mock、协议回放、模拟器、主机侧故障注入 | 列出的主机/模拟场景通过 | 真实外设、真实中断、功耗或板端通过 |
| E3 | 指定目标板、真实外设、调试器/仪器测试 | 列出的板级场景通过 | 所有异常、长期可靠性或量产通过 |
| E4 | 在指定目标板或真实系统环境中执行断电、复位、丢包、噪声、压力、长稳、温度/电源边界等故障注入 | 列出的目标板故障/环境场景通过 | 未执行场景也安全或量产通过 |

证据等级不是统一“刷到最高级”。A2/A3 必须在方案冻结时为每个验收项指定所需等级。例如：

- OTA/NVM 的掉电一致性通常需要 E4；
- ISR/DMA/RTOS 的基本功能需要 E3，竞争、超时或压力边界通常需要 E4；
- 协议纯解析可由 E2 覆盖，但真实收发切换、噪声和时序仍需要 E3/E4；
- 低功耗电流和唤醒恢复至少需要带仪器结果的 E3，异常或长期循环按风险要求 E4。

同一种异常即使在 PC/Mock 中完整模拟，最高仍按 E2 记录；只有在验收指定的目标板或真实系统环境中实际施加故障，才能记为 E4。E3/E4 记录必须给出板卡/PCB/BOM、固件标识、测试条件、施加方法和原始结果。

目标构建、告警、ROM/RAM、镜像和关键时序必须同时给出“修改前基线”和“修改后结果”；只给修改后的单点数值不能证明没有回归。

强制表述：

- 编译成功只能写“目标编译通过”；
- Mock 成功只能写“PC/Mock 测试通过”；
- 没有实机证据必须写“实机尚未验证”；
- A3 未达到冻结卡为相应验收项规定的 E3/E4 时，状态应写为“实现完成，发布验收未完成”；
- 硬件诊断必须分开写“已证实”“最可能”“待实测排除”。

每个验收项必须对应至少一条证据。没有证据的结论不得写成 PASS。证据必须能追溯到被验证的源码和产物；同一份证据可由多个验收项引用，不必重复复制。

交付时建立最小证据索引：

```text
证据 ID：EV-01
源码标识：提交号；未提交时记录工作区状态或补丁位置
构建标识：目标、板型、功能宏、Debug/Release、工具链
产物标识：固件/可执行文件路径与 SHA-256（适用时）
硬件标识：板卡/PCB/BOM/模块版本（E3/E4 必填）
执行条件与步骤：
原始日志、测量结果或录屏位置：
```

AI 到达每个汇报检查点时，必须用一屏左右的交付卡汇报，不能只说“已完成”。检查点通常放在一个切片结束处；用户批准连续实施多个切片时可以合并汇报，但仍须逐片列出改动、验证和偏差：

```text
【本次交付】

实际完成：
明确未改变：
行为变化：

需求未明确但 AI 补充的逻辑：无 / 内容及批准来源

与方案的偏差：无 / 有（原因及是否已确认）

- [AC-1] 结果：PASS / FAIL / 未验证；证据等级：E0-E4；证据 ID：
```

## 10. 人的三层 Review

人不需要把所有普通循环重新推导一遍，按以下顺序审查：

### 第一层：行为与范围

- 是否满足完成标准？
- 是否出现未要求的外部行为？
- “必须保持不变”的接口、协议、超时、布局和时序是否真的没变？
- 是否新增了未经批准的默认值、重试、超时、恢复或防御性逻辑？
- 修改范围是否超出任务卡/冻结卡？

这一层不通过，直接退回，不进入逐行审查。

### 第二层：心智模型与关键路径

只先回答四条主线：

1. **状态**：有哪些状态，谁能改变它，何时离开当前状态？
2. **数据**：缓冲区和共享数据归谁所有，何时产生、消费和释放？
3. **时序**：谁触发、谁阻塞、何时超时，ISR 与任务的先后关系是什么？
4. **失败**：错误、复位、掉电后资源、Flash、外设和系统状态是什么？

至少走通一条正常路径和一条最危险的异常/恢复路径。对协议、状态迁移、ISR/DMA、Flash、低功耗、看门狗和陌生算法逐行审；对机械性辅助代码抽查即可。

### 第三层：证据

- 构建是否使用了正确的目标和配置？
- 测试是否覆盖正常、边界、超时、恢复和兼容性？
- Mock 是否掩盖真实中断、时序、电气或功耗行为？
- AI 的 PASS/完成结论是否超过证据等级？
- 高风险场景能否由人复现，日志和测量值是否完整？

## 11. 独立 AI 复审

复审强度按权限等级执行：

- A1：实现 Agent 自审即可；缺少确定性验证或接近红线时可升级为独立复审；
- A2：推荐独立复审；涉及共享内部接口、出现方案偏差或验证不完整时必须独立复审；
- A3：必须使用独立上下文复审，然后再由人审关键设计和证据。

实现 Agent 与复审 Agent 应尽量使用独立上下文。复审以任务卡、冻结卡、diff、验证证据和验收标准为中心；为了核对调用契约、数据所有权、并发和配置来源，可以沿依赖只读查看必要的关联源码、头文件和工程配置。复审结论必须与本次变化相关，不把无关的既有问题算作本次缺陷。重点报告：

- 漏掉的需求或异常路径；
- 计划外文件和行为变化；
- 状态、所有权、生命周期、边界和资源问题；
- 证据不足或过度宣称的地方。

复审必须报告“影响正确性或任务要求的缺口”，不要把个人风格偏好当缺陷，也不要因为追求“更健壮”而自动扩大设计。

独立 AI 复审属于缺陷筛查，不会提升 E0–E4 证据等级，也不能代替人的设计批准、目标构建、板端测试或故障注入。

可直接复制的复审提示：

```text
以本次任务的 diff 为审查对象，不修改代码。
允许沿调用链只读查看核对结论所必需的关联源码、头文件和工程配置；
不要把与本次变化无关的既有问题算作本次缺陷。
对照任务卡/设计冻结卡和验收标准，依次检查：
1. 范围漂移和计划外行为；
2. 状态机、调用链、数据所有权和生命周期；
3. 超时、错误、复位、掉电和恢复路径；
4. 协议兼容性、Flash/RAM/栈/时序/功耗预算；
5. 验证证据是否足以支持每个 PASS。
只报告会影响正确性、兼容性、安全或验收的缺口；
把风格建议和未批准的改进列为可选项。
```

## 12. 异常、热修复与豁免

- **需求不清**：先问会改变架构、接口、状态、兼容性、安全、并发、资源或验收的最小问题；其余信息采用保守假设并明确标注。
- **方案偏离**：暂停当前切片，提交设计变更；不得在交付卡里事后“顺便说明”。
- **构建环境不可用**：可以继续做源码分析或准备测试，但必须把验证标为未执行，不能称为通过。
- **紧急热修复**：允许压缩文档和切片，但不得跳过范围确认、最小 diff、目标构建、关键恢复路径和后续板端验证；事后补记决定和证据。
- **豁免**：必须记录对应条款（章节/小节）、原因、风险、替代控制、批准人和失效日期；临时豁免不能改变红线任务的最终验收要求。

## 13. 反官僚约束

本规范本身也受以下约束：

1. 小改动不强制写长方案；能用一句话描述清楚的 diff，可以走 A1。
2. 同一事实只保留一个权威位置；不要同时复制到 Prompt、README、Issue 和多个规则文件。
3. 计划和交付卡服务于审查，不是为了“看起来完整”；没人会使用的图表和文档不要生成。
4. 不为了满足行数阈值制造碎片化提交；行为闭环优先于机械拆分。
5. 测试数量不等于证据强度；AI 自己编写并通过的 Mock 测试不能代替独立的板端或故障验证。
6. 规则只从真实错误中增长；季度清理一次，删除已经不再减少错误的条款。
7. 任务卡按风险裁剪；不适用字段可以整段省略，不要求用大量“无”把模板填满。

## 14. 最短日常用法

模板按风险裁剪：

| 等级 | 最小记录 |
|---|---|
| A0 | 已确认事实、AI 推断、待实测、风险和建议；不需要填写批准区和交付卡 |
| A1 | 目标/范围、完成标准、修改摘要、验证结果、未验证项；无需展开完整系统模型 |
| A2 | 用户输入、AI 只读确认、修改前基线、微型方案、批准记录和交付卡 |
| A3 | 使用完整任务卡、设计冻结卡、逐项证据计划、批准记录和交付卡 |

项目长期基线已有权威记录时，任务卡只引用该位置并记录本次差异，不重复抄写全部内容。

### 14.1 用户开始一个任务

```text
按《嵌入式 AI 协作开发规范》处理。

目标：
上下文/版本/日志（可留空，由 AI 从工程确认）：
不能改变：
本次不做：
完成标准：
验证方式：

请先读取实际工程并自动判定 A0/A1/A2/A3。
A2/A3 先给方案，不要修改代码。
只询问会改变架构、安全、兼容性、并发、资源或验收的问题；
其他信息请给出保守假设并明确标注。
需求未明确的额外逻辑只能列为建议，不得直接实施。
```

### 14.2 用户批准方案

```text
批准方案：<方案标识/版本>。

调整：
1.
2.

允许实施的切片：Task 1。
汇报检查点：Task 1 完成后停止并给出交付卡。
不要实施建议项，不要做无关重构。
```

### 14.3 用户要求解释而不是修改

```text
只读分析，不修改代码。
请说明当前调用链、状态、数据所有权、时序、失败恢复，
并把“已证实 / AI 推断 / 待实测”分开。
```

## 15. 工具落地映射

本节是非规范性映射，应在工具升级后复核。规范内容与工具命令分开维护；工具变动时不改协议本身：

- **Aider**：把 `AGENTS.md` 或 `CONVENTIONS.md` 作为只读上下文；复杂任务先用 `/ask` 讨论，批准后再进入代码模式；每个切片后运行测试并查看 diff，必要时用回退功能撤销。
- **Codex**：把 `AGENTS.md` 放在项目根目录，复杂任务使用 Plan/Review；任务卡和冻结卡仍按本规范输出。
- **Claude Code**：使用其项目级说明文件承载同一份长期规则；开启计划阶段和独立复审上下文。
- **GitHub Copilot**：使用仓库级或路径级自定义指令；把本规范的 A3 红线放在仓库规则中，把单次任务放在 Issue/PR 或提示文件中。

如果某工具不支持某个文件名，不要复制出多份互相漂移的规则；保留一个权威版本，再用工具支持的方式引用或同步。

## 16. 依据与适配说明

截至 2026-08-31，我核对的主流官方工作流有一个共同骨架，但它们不是嵌入式行业强制标准。本规范只吸收适合当前场景的部分：

| 来源 | 可借鉴的事实 | 本规范的适配 |
|---|---|---|
| [GitHub Spec Kit](https://github.github.com/spec-kit/) | `Spec → Plan → Tasks → Implement`；生产路径可加入澄清、清单、一致性分析和收敛；每阶段产生结构化制品 | 小任务不强制全套流程；A2 用微型方案，A3 才使用设计冻结和任务制品 |
| [AGENTS.md](https://agents.md/) 与 [GitHub Copilot 自定义指令](https://docs.github.com/en/copilot/concepts/prompting/response-customization) | 用短的、项目级或路径级 Markdown 保存构建、测试、约定和安全上下文；大仓库可按目录细化 | 用 `AGENTS.md` 保存长期规则，C/Lua 专项规则分册化，避免把任务过程塞进长期文件 |
| [Claude Code 最佳实践](https://code.claude.com/docs/en/best-practices) | `Explore → Plan → Implement → Commit`；给 Agent 可执行的验证信号；用独立上下文做对抗式复审；控制上下文和任务范围 | 增加嵌入式 A0–A3 门禁、E0–E4 硬件证据等级、掉电/时序/资源红线 |
| [Aider 使用技巧](https://aider.chat/docs/usage/tips.html)、[Repo map](https://aider.chat/docs/repomap.html) | 只加入相关文件；复杂任务先讨论；按小步骤工作；用仓库地图减少无关上下文 | 把“按行为切片”作为核心，而不是机械地一函数一任务 |
| [OpenAI 官方模型指导](https://developers.openai.com/api/docs/guides/latest-model) | 采用精简、结果导向的提示；明确约束、验收、授权边界和证据；不要重复规则 | 把用户输入压缩为“目标/不能改变/完成标准/验证方式”，把不可逆硬件操作列为需授权事项 |

本规范不是对上述工具的背书，也不是声称存在一个统一的行业标准；它是把这些共同做法与嵌入式工程的真实风险结合后的项目治理基线。
