# 里程碑设计规范

所属规范：嵌入式 AI 协作开发规范。更新日期：2026-10-21。

AI 入口：[协议使用入口](AGENT.md)。前置：[总体方案设计规范](总体方案设计规范.md)。实例：[Reuse_RTU OTA 里程碑划分示例](example/PLAN.md)。

## 1. 定位与基本关系

本分册将已确认总体方案的当前版本范围，划分为能够连续推进、结果可判断的里程碑，并明确依赖、必要验证和完成条件。用语沿用总体方案设计规范。

- **版本**：确定本轮交付范围和工作深度。
- **里程碑**：交付一项有明确用途、结果可判断的能力，或解决一个关键可行性问题。
- **任务**：完成里程碑所需的具体设计、实现、审查和验证工作。

一个功能可跨多个里程碑，相关功能也可合并交付。按可交付能力和实际依赖组织工作，设计、实现、自检、审查和测试随能力推进。里程碑不要求与一个函数、文件、角色会话或一次上板操作一一对应。

<a id="milestone-order"></a>

里程碑按用户确认的顺序串行进入和结束，不并行执行，也不挂起当前里程碑、穿插另一里程碑后再返回。当前里程碑内的设计、实现与用例准备可以按获批安排开展协作；这一安排不授予提前执行后续里程碑的权限。需要调整顺序或范围时先由用户确认并更新计划，未结束当前里程碑前不擅自切换。

### 1.1 成果文件与存放位置

`AI/` 为项目入口登记的唯一协作文档根目录；已有等价文件须在入口集中登记映射。

| 成果 | 规定位置 | 建立时机与主要维护者 |
|---|---|---|
| 当前版本里程碑计划 | `AI/PLAN.md` | 总体方案确认后维护轮廓，规划设计者维护，执行中由当前 B 修订受影响方案 |
| 当前里程碑具体设计 | `AI/milestones/Mxx/DESIGN.md` | 进入该阶段后由 B 细化，必要方案由用户确认 |
| 正式验证用例 | `AI/milestones/Mxx/CASES.md` | 需要正式验证时建立；B 确定方案，E 维护执行细节 |
| 当前审核结论 | `AI/milestones/Mxx/REVIEW.md` | C 开始审核时建立并维护 |
| 当前验证报告 | `AI/milestones/Mxx/TEST_REPORT.md` | E 开始正式验证时建立并维护，失败和未完成同样报告 |

`Mxx` 替换为项目内唯一的里程碑编号，如 `M01`。简单阶段可由已登记的等价文档明确章节承载；必须能定位具体设计和 C 的审核结论。D 开发自测随实现交付记录维护，未安排 E 正式验证时不为凑齐文件创建空用例或空报告。

本文件第 2、3、9 章规定划分，第 4 章规定进入阶段后的具体方案及文件内容，其余章节规定验证安排与完成判断。完整关联示例见[计划](example/PLAN.md)及[M01 具体设计](example/milestones/M01/DESIGN.md)。

## 2. 划分原则


1. **覆盖当前版本目标**：在里程碑条目中引用总体方案的功能编号，说明本阶段承担的部分。所有当前版本功能及总体验收目标均须有承接，不另建重复维护的映射表。
2. **交付结果明确**：可以是完整功能、可复用支撑能力、可运行链路或必要可行性结论。仅写“编码完成”“测试完成”不足以表达该阶段的能力和范围。
3. **尽早形成有意义的运行链路**：优先连接关键模块，减少大量实现建立在未验证接口或硬件假设上的情况。局部支撑能力可先用主机检查验证，再接入实际链路。
4. **必要保护随能力交付**：相关能力实际启用前具备已确认的边界、失败处理和恢复条件。例如覆盖唯一运行镜像前，须具备约定的恢复条件。
5. **颗粒度按理解和交付负担决定**：目标互不相关、依赖或验收差异较大时可拆分；共享紧密、结果需要一起判断时可合并。不以文件数、代码行数或测试数量机械拆分。
6. **未知项只限制依赖它的工作**：说明缺少的事实、影响范围和取得时点。当前里程碑内已授权的独立工作可继续，未验证假设不能被当作已经成立的前提；不能据此绕过串行次序启动另一里程碑。

划分不要求为每项设计、每个测试脚本或每次修正建立新里程碑。必要预研或专门集成验证可以单独成阶段，但须有明确问题、成果和结束条件。

## 3. 每个里程碑的六项信息

先为当前版本建立完整轮廓，确定以下内容；已有资料直接引用。

| 内容 | 必须明确的信息 |
|---|---|
| 目标与范围 | 对应哪些总体功能，本阶段承担哪部分能力及必要失败处理 |
| 前置依赖 | 区分进入阶段、具体实现及验证开始前所需的设计、接口、代码或真实环境条件，说明当前是否具备及核对时点 |
| 交付结果 | 完成后得到什么可使用、可审查或可验证的成果 |
| 验证安排 | 本阶段检查什么，是否上板；延后验证由哪个里程碑承接、验证什么 |
| 完成条件 | 哪些结果满足后可以结束本阶段，哪些结论仍有明确限制 |
| 设计与执行入口 | 具体设计、内部任务和实际结果维护在哪里；近期未展开时注明细化时点 |

技术依赖应具体到实际所需的成果或结论，执行次序则按已确认计划串行维护。前一里程碑按自身约定范围结束，不自动要求取得已明确安排在后续的整体验收结果；技术依赖较少也不能作为跨里程碑交错执行的依据。

<a id="milestone-prerequisites"></a>

前置依赖须说明适用时点。进入阶段只要求确实决定该阶段能否开展的已有成果及条件；本阶段负责形成的具体方案、实现和工具属于阶段内部任务，不能反过来列为进入本阶段的前提。依赖这些成果的实现、部署或具体验证，在相应动作开始前再核对所需条件；缺项只限制实际依赖它的工作，不能借此跨里程碑执行。

延后验证必须指定承接里程碑和预期结果，不能只写“以后再测”。共同验证的条目在承接阶段统一维护，前序通过引用关联；划分调整时同步受影响指针。

## 4. 当前里程碑的设计细化

总体规划先确定当前版本各里程碑的轮廓。进入某个里程碑时，再形成清楚的实施依据，按实际需要说明：

- 涉及模块、主要文件及职责。
- 接口、数据和状态之间的关系。
- 正常路径、关键判断和失败出口。
- 必要资源、兼容性和硬件约束。
- 实施任务、必要审查及验证办法。

函数和内部逻辑按理解与实现需要展开。简单部分可以简述，复杂或高风险部分重点说明，不要求在划分阶段提前确定全部函数或逐个启动审批。

必要设计与实施范围经用户确认后，在获批范围内连续执行实现纠错和必要验证。发现总体范围、产品行为、共用约定或重要依赖需要改变时，提交受影响的调整，由用户决定。

<a id="milestone-files"></a>

### 4.1 具体设计 DESIGN.md

推荐按以下内容组织，简单部分合并短述，复杂或高风险部分重点展开：

1. **目标与范围**：引用 `PLAN.md` 中当前阶段及总体功能，明确承担部分和边界。
2. **依据与前提**：已确认方案、必要授权、已有成果、硬件事实和采用的共用设计。
3. **具体设计**：涉及模块、主要文件及职责，接口、数据和状态关系，正常路径、关键失败及恢复出口。
4. **实施任务与交付**：D/E 分别做什么、修改范围、必要接入说明、交付及接续。
5. **审查与验证安排**：D 的必要自测、C 审核对象、E 正式用例入口、是否上板以及延后验证承接。
6. **完成条件与相关记录**：本阶段需要哪些结果，限制和剩余项如何判断，以及确认和变更依据。

涉及 C 实现时，沿[规范接入规则](多AI会话工作流规范.md#c-standards)引用项目已确认的采用范围及实际技术配置，说明 D 必要自检和 C 审核入口；正式验证仍按本阶段已确认目标安排，不因规范条文自动扩展功能或验证深度。

本组 B 维护当前已确认设计。D 发现实现需要改变既有设计时，沿工作流交 B 分析；设计澄清与实质变更按[分析返回边界](多AI会话工作流规范.md#analysis-return)办理，普通已授权实现纠错继续推进。DESIGN 保留已确认行为、任务和完成条件，通过入口引用当前结果，不累计候选更替、执行轮次、PASS/FAIL 或阶段完成声明。

### 4.2 正式验证 CASES.md

B 与用户确定必要用例方案，E 将其维护为可执行的文字步骤和工具入口，C 核对用例实现是否符合获批预期。每个用例采用稳定编号，至少包含验证目标、所需对象条件与环境、输入或操作、预期及失败判定、证据要求、停止及必要恢复条件。

核对当前阶段承担的功能及其已确认入口、正常成功条件和必要拒绝或恢复条件，不能只测一个入口的成功和另一入口的拒绝，就声明该功能完整通过。同一用例包含多个入口时分别保存结果。补齐已确认功能的漏测由 E 完善、C 审核；不因补漏重新批准原目标，实质改变目标或操作授权仍按确认规则办理。

说明本阶段不测和延后承接的范围。正式验证可以是主机回放、上板、系统联动或研究试验，按目标选取；开发调试与 D 自测不因此改称正式验收。改变目标、预期、验收或停止条件的实质内容，回 B 并由用户确认；脚本实现错误由 E 修正后交 C。

CASES 可说明候选要求及复测选择原则；实际获准执行的候选、用例组合、范围和旧结果复用判断由 C 在 REVIEW 维护，实际执行结果由 E 在 TEST_REPORT 维护。仅因执行轮次或结果变化，不回写用例方案；步骤或判定实际改变时再更新 CASES。

### 4.3 审核结论 REVIEW.md

C 维护当前结论，写清审核依据、实际对象与范围、采用的交付和证据、问题及影响、限制和接续。

实现及自测审核、正式用例审核、验证证据审核分别表达。尚未审核、无需执行或等待条件时直接说明，不以一个笼统的“通过”覆盖不同对象。正式验证开始前，C 明确可执行的候选、用例及范围组合；仅某一部分审核通过不自动启动全部验证。

针对修正只复核问题及受影响范围，并确认原结论的适用性。当前正文保留有效结论与必要指针，普通意见和被替代结论由 REVIEW 的 Git 历次版本保存，引用时标明当时对象及提交。复杂争议、重要遗漏或跨阶段影响分析按[事件记录规则](文档组织与维护.md#record-policy)补充，不因 C 每轮审核另写一份相同过程记录。

后续里程碑发现旧成果缺陷时，由当前 C 按[旧结论适用性规则](多AI会话工作流规范.md#prior-verdict)补充受影响审核入口的说明，保留原对象和原始证据，通过引用关联当前修复。

### 4.4 验证报告 TEST_REPORT.md

E 维护实际候选、用例版本、环境和操作范围，逐项列出实际结果、证据入口、失败及未测、限制和待处理事项。失败、停止或条件不足同样形成报告，不能只保存成功运行。

正式验证结果、脚本离线调试、资料核对和主机检查分别标明证据等级。修正后注明哪些用例重测、哪些既有结果仍适用及依据，不覆盖原失败证据。报告交 C 审核证据，再由 A 核对阶段完成条件。同一阶段按需要更新这份当前报告，各轮原件分别保存；不再额外抄写同内容的 E 工作记录。候选、用例、必要环境和范围可由本报告及已有来源共同定位，不为每个证据目录重复填表，具体见[证据规则](文档组织与维护.md#evidence-policy)。

### 4.5 文件形成顺序与工作深度

进入阶段时形成 `DESIGN.md`；需要正式验证时同步确定 `CASES.md`。D 实现和自测、E 用例实现与准备按获批范围推进；C 开始审核后维护 `REVIEW.md`，E 正式执行后维护 `TEST_REPORT.md`。A 在阶段、责任、阻断、有效结果或下一步改变时维护 `STATE.md`，普通收口由当前成果和共享回执说明；受限收口仍须保存用户决定。共享交接沿[工作流要求](多AI会话工作流规范.md#handoff-record)，不复制全部过程。

各文件按[版本工作深度](总体方案设计规范.md#2-三个版本的工作深度)控制内容：V1 围绕完整链路、必要保护和代表场景；V2 围绕实际改善和针对回归；V3 按已确认研究问题展开必要时序、矩阵、资源或压力。文件数量不决定工作深度。

## 5. 上板时机与组合验证

上板安排按验证对象和实际依赖确定，不统一要求每个里程碑上板，也不统一推迟到所有代码实现之后。

| 情况 | 推荐安排 |
|---|---|
| 纯计算、解析、版本比较、打包等，主机检查能够验证当前成果 | 本阶段完成对应检查，后续接入真实链路时组合验证 |
| 实际存储、启动交接、外设通信等关键假设，会影响大量后续工作 | 提前取得必要事实；需要实物证据时在本阶段安排小范围上板验证 |
| 多项能力组合后才能观察完整结果 | 形成最小可运行链路后集中上板，前序阶段保留待验证范围与承接节点 |
| 完整业务、模块交互和版本交付结果 | 在版本收口节点进行整机验证，复用仍然有效的阶段结果 |

安排时遵守以下要求：

1. 对影响后续选择的关键事实，先采用成本合适的方法取得必要依据。资料核对能够解决的问题不强制增加板测；真实硬件行为需要实物证据时不能用推理替代。
2. 关键硬件验证可以早于完整功能闭环。例如存储容量、基本读写、启动交接可先做针对检查，无需同时展开完整故障矩阵。
3. 已具备条件的关键链路应及时验证。例如本地安装和恢复可运行时，就验证该链路，不等待无关业务全部完成。
4. 同一里程碑可按需要多次做有明确目的的小范围实测；多个软件任务也可连续完成后组合验证。不按任务数量机械增加上板次数。
5. 当前验证应包括相应能力所需的成功、关键失败和恢复场景。按当前工作深度选择覆盖，不自动展开完整输入、逐写入点或长期压力矩阵。
6. 缺少设备或环境时记录未测、影响和后续条件，只限制实际依赖该证据的工作。不得把构建、主机检查或启动成功推广为全部硬件功能通过。

实际设备操作遵守项目已确认授权和数据保护要求。本分册安排验证节点，不直接授予烧录、擦写、掉电试验或发布权限。共享板卡及相关资源的操作应串行安排。

## 6. 里程碑内的实现、审查和修正

推荐执行关系：必要设计与用户确认 → 实现和基本自检 → 必要审查与修正 → 按计划验证 → 修正及针对复测 → 核对完成条件。

这是成果之间的关系，不要求实现与测试完全分成两个阶段。开发中可测试、定位和修正，具备条件时可提前上板；执行者和多 AI 调用方式由后续工作流规范及项目安排确定。

审查和验证按以下方式控制范围：

- 对能够说明完整行为的成果集中审查，不为每个小任务单独增加审查轮次。
- 会影响后续正确性或关键操作的高风险选择，在依赖它的工作开始前完成必要审查并处理阻断问题。
- 修正后复核问题及受影响部分；出现新影响或失败时，再说明理由并扩大范围。
- 已通过且对象、配置、相关依赖及适用环境未变化的结果直接复用。代码变化后核对证据适用范围，补受影响检查。
- 审查、工具收件和执行者报告不能替代所需实际验证；未执行项保留未测。

达到本阶段约定审查范围和结束条件后继续推进，不以反复“零问题”作为完成要求，也不因无关后续研究尚未执行而重开已有效的检查。

## 7. 阶段完成、后续验证与版本验收

里程碑按事先约定的目标、交付及验证范围判断完成，不将每个软件成果都挂到最终验收，也不把局部完成扩大为产品功能全部通过。

| 情况 | 完成口径 |
|---|---|
| 本阶段的软件能力和约定检查完成，真实联动明确安排在后续 | 可以结束本阶段，写清“软件阶段完成，真实联动由指定里程碑验证” |
| 本阶段目标包含真实安装、通信、恢复等实物结果，但未取得所需证据 | 写“实现完成，实物待验证”，本阶段完成条件尚未满足 |
| 本阶段必需功能失败或关键证据不足 | 保留失败或待补证；处理受影响问题，独立且已授权工作可继续 |
| 各阶段已完成，但系统集成或总体场景未全部验证 | 不能据此宣布当前版本整体验收通过；由版本收口节点核对 |

阶段结束时还须按[Git 提交与推送规则](多AI会话工作流规范.md#git-delivery)完成当前成果提交和远程同步。下一里程碑须在当前里程碑按约定结束或经用户明确受限收口后，且[阶段进入条件](#milestone-prerequisites)具备、处于[已授权接续范围](多AI会话工作流规范.md#milestone-authorization)时进入。阶段停止或任务取消不等于功能完成，不能借此绕过完成条件。版本收口时按总体方案核对主要功能、完整使用场景、原业务保持及关键失败处理，使用明确的最终候选并复用适用证据。

因条件限制需结束当前轮次时，按[总体方案的验收与受限收口规则](总体方案设计规范.md#36-总体验收目标)由用户决定，保留失败、未测、影响和后续条件，不事后改写原验收结果。

## 8. 三个版本的划分深度

三个版本的完整目标与使用规则统一见[工作深度](总体方案设计规范.md#2-三个版本的工作深度)。本分册按以下方式组织里程碑：

| 工作深度 | 里程碑重点 | 完成判断重点 |
|---|---|---|
| **V1 初版** | 已确认功能、最小可运行链路、必要保护和失败处理、实物代表场景、整机业务 | 当前范围功能及规定验证满足要求；一般优化和深度研究不自动成为前置条件 |
| **V2 优化** | 实际问题或明确改善目标，及受影响路径回归 | 问题得到修复或达到确认的改善目标，相关功能回归通过 |
| **V3 深度研究** | 具体研究问题、覆盖范围、取证方法和停止条件 | 取得规定范围内可重复、可解释的证据与结论，明确覆盖限制 |

V2 不要求重开全部 V1 里程碑；根据实际影响复用已有成果。V3 在满足事先确定的研究完成条件后，可以得出指标满足、无法满足或约束冲突的结论，并如实说明依据。缺少必要设备、输入或证据而使研究计划未完成时，保留未完成或阻断；不得默认写成有效研究结论。形成有效研究结论不等于产品指标已经满足，也不能事后将原本要求达到指标的优化任务改为仅需取得结论。

研究执行中的证据审核、方案分析与用户决定，按[多 AI 工作流的研究边界](多AI会话工作流规范.md#research-boundary)接续。

影响本轮功能正确性的问题按当前问题处理，不能仅因属于资源、时序或异常行为就自动推到 V2/V3。是否开展深度研究按实际需要决定。

## 9. 划分审查与后续调整

里程碑轮廓形成后集中检查：

1. 当前版本功能和总体验收目标是否都有承接。
2. 依赖是否成立，核对时点是否正确，是否误将本阶段产物列为进入前提，或存在循环等待和无关的全局阻断。
3. 是否尽早形成有意义的运行链路。
4. 关键未知项是否在大量后续工作依赖它之前解决。
5. 颗粒度是否便于理解、执行和判断结果。
6. 延后验证是否明确承接节点、预期结果及必要条件。
7. 必要系统集成、整机业务和版本收口验证是否安排。
8. 设备、公共文件和集成资源是否具备可执行的安排。

用户确认后按计划细化和执行。后续局部实现细节在对应设计维护；总体范围、主要产品行为、重要依赖或验证目标改变时，确认受影响部分并同步计划和承接关系。

## 10. 文档组织

按 1.1 节维护 `AI/PLAN.md` 和当前 `AI/milestones/Mxx/`，已有等价资料在入口登记映射。计划维护当前版本里程碑轮廓与关联，当前里程碑按需要展开具体设计；不预生成全部远期设计、空白表单或尚未进入阶段的角色会话。实际进入每个新里程碑时，按[工作流会话组规则](多AI会话工作流规范.md#51-每个里程碑新建会话组)新建本阶段 A/B/C/D/E 五个会话，同阶段修正与复测续用该组。

阶段组的目标配置和实际绑定沿[会话登记要求](多AI会话工作流规范.md#session-register)维护在 `AI/SESSIONS.md` 的唯一来源，`AI/STATE.md` 只保留当前组编号及进展入口，`AI/ROLES.md` 维护稳定的协作约定。已有等价资料仍按项目入口登记映射，具体字段和权限不在本分册重复规定。

每项内容只维护一处有效正文。项目 `AGENT.md` 提供 AI 导航与项目约定，`README.md` 用于说明介绍，不要求 AI 必须读取；材料位置、决定变更和记录维护按[文档组织与维护](文档组织与维护.md)执行。实际状态、逐轮审查测试和原始证据沿项目已有入口维护，计划及设计引用必要记录，不累计全部过程。已有项目采用本分册时可映射原有成果，不因新划分重新实施或重测未变化且有效的内容。
