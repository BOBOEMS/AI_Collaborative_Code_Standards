# 多会话工作流：文档组织与维护

> 2026-10-13 按用户审核通过的文档组织方案整理。
> 协议入口：[README.md](README.md)；角色职责与用例修正权限：[ABCDE 角色与分工](多会话工作流-ABCDE角色与分工.md)。

## 1. 通用协议与项目材料

通用协议维护角色分工、目标配置、根目录命令表、工具手册和文档写法。各项目的技术方案、任务、状态、测试、审核和历史记录放在该项目的方案目录。

每个项目只维护一个有效方案入口，所有会话和工作树引用同一处。每项内容只有一处有效正文，其它位置通过链接引用；沿用项目已有目录名称和入口，按实际任务创建文件和子目录。

## 2. 项目目录与索引

以下为通用结构示例，项目已有 `board-test/` 等对应目录时直接复用。

```text
项目方案目录/
├── README.md             总导航
├── RULES.md              当前工作规则
├── PLAN.md               范围、里程碑、完成条件
├── STATE.md              当前阶段、负责人、对象、下一步
├── design/               按模块或主题拆分的有效设计
├── testing/
│   ├── INDEX.md
│   ├── cases/            按阶段拆分的当前用例
│   ├── test-reports/     按阶段拆分的当前测试结果
│   └── audit/            按阶段拆分的当前审核结果
├── records/
│   ├── INDEX.md
│   └── <阶段>/           每轮独立记录，必要时设子索引
└── evidence/
    └── <阶段>/<轮次>/    原始日志、截图、回读等材料
```

每个需要导航的目录使用 `INDEX.md`，已有 `README.md` 或其他文件承担导航职责的直接复用。总入口指向目录入口，目录入口再指向具体文件；入口只说明用途和读取路径。

索引只登记标题或任务、简短结论和链接。记录较多时按阶段或时间分成子索引，总索引只保留子索引入口。

## 3. 内容分类与更新方式

| 内容 | 存放位置 | 更新方式 |
|---|---|---|
| 工作规则 | 项目规则正文 | 约定变化时修改对应条款 |
| 有效设计与任务卡 | `design/` 或项目既有位置 | 按模块或主题维护当前生效内容 |
| 当前用例与脚本入口 | `cases/` 或项目既有位置 | 修改相应用例；实际修正进入本轮记录 |
| 当前状态 | 项目指定状态文件 | 覆盖当前事实、负责人、剩余项与下一步 |
| 阶段测试摘要 | `test-reports/` | 覆盖当前判定、有效数字、问题和证据链接 |
| 阶段审核摘要 | `audit/` | 覆盖当前结论、对象、缺口和必要依据 |
| 每轮工作记录 | `records/` | 实际方案、实现、审核或测试一轮一份 |
| 原始证据 | `evidence/` 或已有工具目录 | 保存当轮原始材料，正文链接实际位置 |
| 后续问题 | 项目后续清单 | 按实际问题归属维护，引用相关记录 |

有效正文只写当前。被替代的方案、旧数字、审核经过和复测细节进入独立历史记录，当前正文保留必要链接。数字或判定被取代时就地更新。

生效的新约定同步到对应规则、设计、任务或用例正文。待用户拍板的方案明确标注待定状态；历史记录和聊天中的建议不能自动成为生效约定。

## 4. 当前摘要与每轮记录

当前状态和阶段摘要写当前任务所需的信息：实际工作目录与代码/候选对象、当前判定、未完成项、负责人、下一动作，以及最近有效记录和证据入口。

每轮记录注明任务、角色和轮次，简述实际对象、工作内容、步骤或检查、结论、未测项与剩余问题。文件命名沿项目惯例，使每轮记录可独立定位；例如 `<日期>-<任务>-<角色>-R1.md`。状态查询和等待无需制造新记录。

原始日志、截图、回读 dump 和长输出留在证据目录；较大镜像和既有构建材料可留在实际工具目录，由记录链接。记录写结论及必要依据，不逐条抄写工具调用。

未执行项写未测，证据不足写待补证。通知送达、实现审核通过和实际测试通过分别按真实范围记录；旧结论保持原代码、镜像、用例和环境的覆盖范围。

## 5. 文件预算与拆分

- 阶段测试、审核摘要各以 250 行为默认预算；接近上限时先将历史过程移到独立记录，再继续更新当前正文。
- 技术设计或单轮记录过长时按模块或主题拆分，长日志留在证据目录，原文件保留必要导航。
- 索引过长时按阶段或时间拆成子索引，总索引只保留入口。
- 跨文件引用使用文件链接和稳定标题，避免依赖重写后会漂移的章节编号。
- 拆分后更新相关入口和链接，历史事实保留其实际对象与结论范围。

## 6. 每轮收工与结果回报

1. 本轮作者先保存独立记录和原始证据，包括失败、阻断、只审不改及未完成的实际交付。
2. 更新本轮对应的当前摘要和必要索引；涉及进度时，通知 A 更新项目状态。
3. 按项目已授权的交付与 Git 规则处理本轮文件，明确本轮写入者，公共索引和 Git 写操作串行。
4. 向 A 发送一句结论及本轮独立记录的链接；需交给 C、E 等角色接续时同步对应角色。

A 接收结果报告后更新进度，并按结果派发后续任务。同一份记录重复通知时确认收到即可，不重复派发已经安排过的工作；使用现有文件和轮次识别，不增加交付 ID 表或独立交接表单。

用例修错由 C 记录修正位置和依据，通知 A、E，由 E 复测受影响用例。角色权限和处理回路以角色分工正文为准。

## 7. 新会话与中断恢复

新会话或恢复后的会话先读项目当前状态，再沿索引读取本任务的有效方案、用例、实际对象和最近有效记录。未变化且已读的材料可以复用，历史和原始日志按需要追溯。

同一里程碑内的修正与复测沿用对应会话。确需换会话时，在已有记录中写明当前对象、未提交成果、剩余项和续接入口，再更新项目会话绑定。

项目已有执行配置时，真实 ID、Agent/transport 和实际参数只在该配置维护，Markdown 会话登记从其同步展示；通用命令表只放模板和入口引用。可在项目已有登记中附当前续接指令，不能反过来用手工展示覆盖机器绑定。

## 8. 写入责任

职责按角色分工执行：A 维护当前状态，B 维护获批设计，D 维护实现和融合说明，C 维护审核与用例修正，E 维护测试结果和现场证据；每个实际工作轮次由其作者维护独立记录。

同一可变文件同时只有一个写入者。用例修错时由 C 接续相关说明或脚本的写入，其他角色暂停修改同一文件，E 待修正后复测。公共索引的更新按本轮归属串行执行。

本协议目录只随规则变化更新；项目逐轮材料归项目目录，协议入口保持简短。
