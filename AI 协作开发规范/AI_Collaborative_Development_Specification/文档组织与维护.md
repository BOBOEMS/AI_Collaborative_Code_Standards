# 文档组织与维护

更新日期：2026-10-21。

协议入口：[AGENT.md](AGENT.md)。设计内容分别按[总体方案设计](总体方案设计规范.md)、[里程碑划分](里程碑设计规范.md)维护；角色权限、问题返回和接续按[多 AI 会话工作流](多AI会话工作流规范.md)执行。

## 1. 适用范围与基本原则

本文件规定总体方案、里程碑规划及实施过程中的文档写法、材料位置和维护方式。读者包括用户和 AI，文档应能说明当前采用什么、为什么、实际做到哪里，以及依据在哪里。

协议根目录维护规则，`example/` 维护一套相互关联的项目示例；示例目录中的文件对应项目 `AI/` 内的职责。各业务分册规定自身成果的内容和位置，本文件汇总项目目录并规定通用维护方法。

每个项目维护一个有效方案入口，所有会话和工作树引用同一处。项目 `AGENT.md` 承担稳定项目约束、材料导航和读取入口，`ROLES.md` 维护协作规则，`SESSIONS.md` 维护配置与各阶段会话身份，`STATE.md` 维护当前进度。`shared_design.md` 只承载按需建立的共用技术约定；`README.md` 用于介绍，不列为 AI 必读材料。文档中的推荐名称可映射到项目已有等价文件，不强制迁移目录或复制正文。

一件事的详细内容只维护一次，其他位置通过引用取得。记录按实际事件和缺失信息建立，不按角色或对话轮次配齐文件。规则、方案和状态文档各自只有一处有效正文；脚本可按[阶段与会话复用规则](#internal-tools)保存独立副本。方案保持最新已确认内容，当前状态反映实际进展，重要决定和无法由现有交付讲清的异常经过进入记录，日常交付由当前成果、提交及共享交接定位；正式验证所需原始材料进入证据位置。按实际需要建立文件，未进入的阶段不预生成整套空目录和表单。

通用协作规则维护在本协议，项目特有规则和技术材料维护在项目目录。项目的 `AGENT.md` 引用适用规范及范围，不复制整套规范，也不因采用新入口而改变既有授权或验收结果。

## 2. 文档书写与术语说明

- 先用自然语言说明目的、条件、行为和结果。避免用大量函数名、状态名、缩写与中文拼接成说明，或让读者必须先阅读代码才能理解方案。
- 需要准确定位接口、字段、源码、配置或日志时，可以使用代码名称，并说明它在此处代表的含义。不能为了回避术语而丢失必要精度。
- 术语较少时在首次出现处解释。全文术语较多、缩写密集，或理解主要内容依赖专门概念时，在正文开头设置独立的“术语与阅读说明”章节。
- 术语说明至少包含名称、本文含义和定义来源。大量术语来自其他文档时，按来源给出对应章节链接及必要的简短解释，详细定义在来源处维护；本文采用的范围或含义有差异时明确说明。
- 同一概念保持同一名称，少量必要简称先解释后使用。代码、文件和工具的实际名称准确保留；不要自行创造难以理解的缩写或混合称呼。
- 区分已核实事实、方案决定、待确认建议、尚未验证的假设和实际结果。写清适用范围、必要条件和限制，不只写“完成”“通过”。
- 用段落解释因果，用表格比较平行信息，用步骤表达执行顺序。图、表和正文相互补充，不重复展示同一套长内容。

术语章节帮助理解正文，正文仍须把行为和理由说清楚。重要选择保留当前采用理由和必要限制，不要求读者查完全部记录才能理解现行方案。

## 3. 项目文件架构与材料归属

### 3.1 参考目录树

以下展示项目采用后的结构，文件随实际工作建立。项目唯一 AI 协作文档根目录记为 `AI/`，具体位置由项目入口登记；已有同等职责的文件和目录须在入口集中登记映射，所有会话共用，不各自选择路径。完整示例位于本协议的 `example/`。

里程碑目录直接使用稳定编号，如 `M01/`、`M02/`，能力名称写在 `PLAN.md`、索引和设计标题中，不拼入路径。编号在项目内保持唯一；已有 `V1-M01` 等完整编号时沿用完整编号，避免不同阶段覆盖同一路径。

`A-01`～`E-01` 是本里程碑各角色的会话工具目录，01 为同角色会话序号，不是工具返回的真实会话标识；替换会话时使用新序号，具体见[内部工具规则](#internal-tools)。

新建文件优先采用简短英文名称，正文和用途说明可用中文。`tools/` 及其下自行命名的目录、脚本、配置和样例文件使用 ASCII 英文字母、数字、下划线或连字符及必要的扩展名分隔点，不使用中文或空格；脚本运行输出优先放入同样采用英文路径的 `evidence/`。Python 脚本推荐使用 `lowercase_with_underscores.py` 形式，名称遵守所用语言规则。保持大小写一致，脚本通过参数或相对脚本位置定位工作目录，避免写死本机目录和前阶段路径。

```text
AI/                             项目唯一协作文档根目录，实际位置由项目入口登记
├── AGENT.md                    AI 入口、项目约定、材料导航和恢复读取路径
├── README.md                   项目介绍，AI 按需阅读
├── PROJECT.md                  总体方案
├── PLAN.md                     里程碑计划
├── STATE.md                    当前状态、剩余项和下一动作
├── ROLES.md                    稳定的项目分工、协作、交接及 Git 约定
├── SESSIONS.md                 目标配置、各里程碑实际会话及替换入口
├── shared_design.md            可选：少量跨里程碑共用的详细约定
│
├── milestones/
│   └── M01/
│       ├── DESIGN.md           当前确认的具体方案和实施任务
│       ├── CASES.md            按需：正式验证方案和实际脚本入口
│       ├── REVIEW.md           C 的当前实现、用例及证据审核结论
│       └── TEST_REPORT.md      按需：E 的实际结果、未测及证据入口
│
├── tools/
│   ├── INDEX.md                各里程碑工具总索引
│   └── M01/
│       ├── INDEX.md            各会话工具索引
│       ├── C-01/
│       │   ├── INDEX.md
│       │   └── verify_evidence.py
│       ├── D-01/
│       │   ├── INDEX.md
│       │   └── run_self_checks.py
│       └── E-01/
│           ├── INDEX.md
│           ├── run_cases.py
│           └── fixtures/       固定输入，由会话索引说明来源和用途
│
├── records/
│   ├── INDEX.md
│   ├── decisions/
│   │   └── YYYYMMDD-topic.md    决策、原因、确认来源和影响
│   └── M01/
│       └── YYYYMMDD-topic.md    按需：复杂异常、返修原因或特殊交接
└── evidence/
    └── M01/
        ├── YYYYMMDD-R01/        一轮正式执行的必要证据
        │   ├── serial.log
        │   └── results.csv
        └── communication/       按需：关键通信原件归档，优先引用工具已有持久记录
```

共用设计的建立条件、内容和分册位置由[总体方案规范](总体方案设计规范.md#shared-design)规定。主题较多、确需拆分时，改用 `AI/design/INDEX.md` 及各主题分册，如 `storage_layout.md`；少量内容先维护根目录的 `shared_design.md`。索引、引用和拆分方法见第 6 章。

没有工具的角色无需建目录；A/B 产生实际脚本时再增加 `A-01/`、`B-01/`。目录树中脚本名仅作通用位置示意，具体脚本按任务选用。


`YYYYMMDD`、`topic`、`R01` 分别表示日期、简短主题和轮次，实际命名替换为对应值。事件名表达发生了什么；参与角色写入必要正文或交接，不以文件名为每个角色分配一份记录。总体方案和规划阶段的记录、证据可以按英文主题目录组织，不必先分配里程碑编号；材料较少可合并文件，职责不同的内容分节说明。

### 3.2 文件职责与存放规则

以下是各分册规定位置的汇总，详细内容及建立条件以对应分册为准。调整所属成果位置时同步本表、目录树和项目入口，不能只改一处后让会话使用不同路径。

| 文件或材料 | 维护内容 | 存放与更新要求 |
|---|---|---|
| 项目 `AGENT.md` | 项目及采用范围、唯一方案位置、材料入口、读取规则、工程与工具入口、项目特有约束和权限依据 | 保持相对稳定；登记实际授权及允许接续范围，指向当前状态和实际配置，不累计进度或重复维护模型、真实会话标识 |
| `README.md` | 项目背景、用途和面向用户的说明介绍 | 可以提供阅读入口，但不能成为 AI 获取执行规则的唯一位置，不要求 AI 必须读取 |
| `PROJECT.md`（总体方案） | 当前目标、范围、主要功能、系统关系、总体选择和验收目标 | 按总体方案规范维护；不混入各轮实现过程 |
| `PLAN.md`（里程碑计划） | 当前划分、依赖、交付、验证承接、完成条件和设计入口 | 按里程碑规范维护；调整时同步受影响的承接关系 |
| `shared_design.md` / 分册后的 `design/INDEX.md` | 多个里程碑共同采用的详细约定 | 由[总体方案规范](总体方案设计规范.md#shared-design)规定条件与默认位置，按需建立；局部设计保留在当前里程碑 |
| 工程接入说明 | 实际接入点、依赖、配置差异、业务保持及接收方需评估的事项 | 可放在现有方案或融合说明中，随代码同一交付维护；具体按[工作流接入规则](多AI会话工作流规范.md#integration-delivery)执行 |
| `milestones/M01/DESIGN.md`（里程碑方案） | 当前已确认的行为、实施任务、完成条件及结果入口 | 进入阶段后细化；用例单独维护时引用其位置，不累计候选更替、执行轮次或完成声明 |
| `milestones/M01/CASES.md`（正式用例） | 当前目标、对象要求、条件、操作、预期、判定、证据及停止条件 | 按实际验证需要建立，引用执行脚本；实际放行组合及复用判断在 REVIEW，执行结果在 TEST_REPORT |
| `REVIEW.md`、`TEST_REPORT.md`（审核与验证摘要） | 当前结论、对象、范围、限制、剩余问题及有效记录 | 分别维护审核和实际验证结果；常规历史由 Git 和共享交接定位，复杂事件按记录触发条件补充 |
| `STATE.md`（当前状态） | 当前阶段、组编号、任务和责任角色、实际对象、结果、剩余项及下一步 | 覆盖当前快照，引用授权范围并说明具体等待事项；身份和模型参数链接 SESSIONS，必要经过链接已有交付或 records |
| `ROLES.md`（项目协作约定） | 角色职责、实际流程和交接、恢复读取、工程工作方式与成果汇合、资源/工具/Git 协作规则 | 位置与内容见[工作流 6.3 节](多AI会话工作流规范.md#63-rolesmd-的内容与实例)；配置和登记只引用 SESSIONS，进度只引用 STATE |
| `SESSIONS.md`（会话配置与登记） | 五角色目标配置、按里程碑保存的实际绑定、核验和运行状态、替换依据 | 位置与内容见[会话登记规则](多AI会话工作流规范.md#session-register)；已有结构化配置时引用或同步，旧组身份和归属保留 |
| `records/decisions/`（重要决策） | 重要取舍、实质变更、验收条件变化，以及用户接受失败或未测限制的决定 | 按第 4 章保存可追溯的确认依据；已有决定记录足够时直接引用，普通确认可放在方案的确认依据章节 |
| `records/M01/`（按需事件记录） | 当前成果、提交和共享交接仍无法讲清的复杂异常、返修原因或特殊交接 | 按事件合并，注明对象、原因、处理及依据；不要求各角色、每轮各建文件，详见[记录触发规则](#record-policy) |

| `evidence/M01/communication/`（可选通信原件） | 工具按需归档的关键消息及回执 | 已有可共享、持久和可定位的工具记录时直接引用；通信只证明交接，不证明功能或审核通过 |
| AI 内部工具 | 各会话自用的分析、审核、自测、正式验证及辅助脚本和样例输入 | 放在 `tools/M01/C-01/` 等独立目录，各层维护 INDEX.md；可复制已有阶段脚本后在本阶段适配，详见[内部工具规则](#internal-tools) |
| 项目源码、对外交付或公共复用工具、构建产物 | 产品实现、公共工具及固件等 | 跟随对应工程或项目工具目录，工作流通过引用使用；构建及部署关联按[候选对象规则](多AI会话工作流规范.md#candidate-identity)核对 |

### 3.3 建立时机与 AI 入口

讨论总体方案时，先维护方案及必要依据；划分里程碑时建立当前范围的计划轮廓；首次需要配置或进入首个里程碑前建立 `SESSIONS.md`，各阶段进入时补齐本组真实登记、设计及实际需要的验证材料。发生实质决定时保留确认依据；每批交付复用已有成果、提交和共享交接，符合下文条件才新增事件记录。正式执行产生必要原件时保存证据，材料较多时再补索引或拆分。

项目 `AGENT.md` 承接稳定项目约定和 AI 总导航，至少能定位适用规范、总体方案、计划、当前状态、当前设计入口、`ROLES.md`、`SESSIONS.md`、工具索引和记录/证据。其他正文引用任务所需材料，完整项目导航表只在入口维护。当前阶段和候选由 STATE 定位，文件/工具/Git 的详细规则在所属正文及项目协作约定维护。尚未产生的材料说明建立时点即可，不为补全入口创建空文件。

项目根目录已有 AI 入口时，可直接承担上述职责，或指向方案目录中的唯一 `AGENT.md`。不同工具需要各自原生入口时，通过引用接入，不复制一套可变规则，也不假定所有工具会自动加载同一文件名。

新会话、替换、上下文压缩或中断恢复时，必须先按[工作流恢复清单](多AI会话工作流规范.md#session-recovery)重新取得当前原文，项目入口提供实际路径。正常连续工作可复用仍在当前上下文且未变化的材料，`README.md` 始终按需阅读。

### 3.4 AI 工作流内部工具

#### 目录归属与索引

面向本工作流使用、无需作为产品接口或公共工具交付的脚本，放在方案目录的 `tools/` 内，按“里程碑编号/会话编号”分别保存，例如 `tools/M01/C-01/`。脚本语言按实际环境选用，目录树中的 Python 文件仅作示意；已有项目脚本和公共工具可直接调用，需要内部副本时按下节复用，公共工具的对外交付入口仍由项目维护。

每个实际建立的工具总目录、里程碑目录和会话脚本目录均设置 `INDEX.md`。总索引指向阶段索引，阶段索引指向会话索引，会话索引逐项说明脚本或子目录的作用和使用入口。脚本较多时可按英文主题名建立子目录并设置索引；`fixtures/` 等固定数据目录的来源和用途可由父索引说明。

索引至少包含脚本或子目录链接、简短中文用途、使用说明位置，复制的脚本注明来源，必要时说明适用对象和限制。不复制完整命令参数、运行日志或真实会话绑定。没有脚本的角色无需创建空目录；规划阶段可按 `tools/planning/session-01/` 等英文路径组织实际产生的脚本。

#### 会话隔离与复制复用

各会话维护自己的脚本目录：C 的目录放审核辅助工具，D 的目录放开发自测工具，E 的目录放正式验证和采集工具；A/B 的工具按其协调、设计任务归属维护。具体权限按[工作流脚本分工](多AI会话工作流规范.md#script-ownership)执行，复制脚本或将其放在内部目录不扩大操作授权。

已有阶段的脚本可以直接复制到当前里程碑、本会话目录使用，再按实际需要适配，无需从头实现；也可以引用原入口直接调用。例如将 `tools/M01/E-01/run_cases.py` 复制为 `tools/M02/E-01/run_cases.py`，后续在 M02 副本中修改。跨会话复用同样可以采用引用或复制方式。

复制复用时遵守以下要求：

1. 在当前 `INDEX.md` 注明来源阶段、会话和脚本路径或其他足以定位的依据；本轮修改及检查可复用已有交付记录，不单独建立复制审批或重复报告。
2. 核对并按需要调整待测对象、运行配置、输入输出路径、依赖和操作范围，运行输出进入本阶段、本轮的 `evidence/`，不得覆盖来源阶段证据。
3. 根据接口、环境、对象和脚本行为的实际变化补必要检查；未变化的逻辑及仍适用的审核、自检结果可以复用，复制本身不要求重做全部测试。正式用例和候选范围仍按本阶段规定确认。
4. 当前副本是本阶段、本会话的执行和维护入口，来源副本保留原阶段用途及证据关联，不要求不同阶段副本同步修改。公共改进如需合入项目工具，由相应维护者办理，避免在同一会话中保留用途不明的多个主用副本。

同角色替换会话时使用新目录，如 D-02。原目录保留，脚本可复制到新目录并注明来源，也可引用未变化工具；同一阶段的任务接续入口和索引更新到实际使用位置。目录序号只表示材料归属，真实会话标识仍引用项目唯一登记来源。

#### 使用说明、用例与输出

工具说明应能定位用途、入口、运行条件与依赖、输入输出、适用对象、影响范围和必要停止条件。多个脚本可共用说明，简单脚本也可在文件头说明并由索引链接，不要求每个脚本单独建立说明文档。

里程碑 `CASES.md` 保存正式验证的目标、步骤和预期，引用 E 会话目录中的实际执行脚本；D 的开发自测和 C 的审核辅助工具在各自索引及交付中说明，不混写成正式实测结果。脚本自检和关键判定按[验证方法规则](多AI会话工作流规范.md#validation-method)执行。

固定样例输入随脚本维护，运行产生的必要原始日志和数据进入当轮证据位置，已有交付直接引用实际输出，不覆盖旧轮次证据。从现场日志提取回放样例时，保留来源和已确认预期，不能仅因输出来自当前实现就认定它正确。脚本变化、必要自检、使用限制及索引随本轮实际交付更新。

本节规定项目内部工具材料的组织；公共会话调用接口及分类适配器见 [session_handover_tool/](session_handover_tool/README.md)。通用代码、说明、样例和测试随模块维护，项目配置及真实绑定留在项目唯一来源，运行回执和日志留在项目选定的运行/证据目录；不将本机路由或项目进度填入通用模块。

## 4. 当前方案与决策变更记录

“当前方案”指最新已确认内容。讨论中的替代建议标注待确认，不直接替换有效决定。方案确认必须可追溯，可以在方案的“确认依据”中简述确认来源、适用内容和范围；不为普通确认一律新建文件。

重要设计取舍、总体目标或范围、产品行为、验收条件、关键依赖和里程碑安排的实质改变，以及用户接受失败或未测限制的决定，须保存能稳定定位的重要决策记录。已有记录完整承载时直接引用；内容较少可在同一决策文件中分节，不因每次讨论增加一份文档。

重要记录至少讲清原决定及调整原因、最终决定和依据、确认来源、影响范围，以及待实施或验证的部分。确认来源应能定位实际用户指示；其他角色的转述或工具送达回执不能单独代替用户批准。

决定生效后更新当前方案及受影响的计划、任务、用例和状态，核对已有审核/验证是否仍适用。由方案 A 改为 B 后，正文直接说明 B 的行为、理由和限制；A 及切换经过在决策记录或稳定旧版本中保留，正文不逐条累计修改历史。

普通文字、格式、链接修正，获批范围内的明确实现纠错，以及[不改变获批决定的设计澄清](多AI会话工作流规范.md#analysis-return)，复用提交、交付及当前结果，不另设方案审批或决策文书。受限收口保留用户实际接受的失败、未测和后续条件，不能因减少记录改写验收结果。

<a id="record-policy"></a>

## 5. 交付留痕、记录触发与证据维护

### 5.1 日常交付复用已有材料

每批实际交付须能定位任务、责任角色、实际对象、完成及检查结果、限制和必要接续。先使用当前成果、具有信息的 Git 提交说明、共享交接及已有证据；这些材料足够时，不再另建同内容的工作记录。

| 类型 | 默认承载位置 | 需要补独立记录的情况 |
|---|---|---|
| 会话交流 | 简短正式交接和工具已有持久记录，字段及可用条件见[工作流](多AI会话工作流规范.md#handoff-record) | 关键交接无法稳定引用，或发生归属争议、重复执行等异常 |
| 方案决定 | 当前方案和确认依据；重要取舍按第 4 章保存 | 重要决定或变更需要独立讲清原因、确认和影响 |
| 生产实现及开发自测 | Git 差异、有信息的提交说明及共享交付，必要数据引用证据 | 复杂原因、实施取舍或接入限制无法由现有材料说明 |
| 独立审核 | C 维护的 REVIEW 及其 Git 历次版本 | 复杂争议、重要遗漏或跨阶段影响需要单独分析 |
| 正式验证 | E 维护的 TEST_REPORT 和本轮原始材料 | 特殊方法、复杂异常或现场处理需要补充说明 |
| 普通阶段收口 | STATE、有效审核/报告及共享推送回执 | 特殊交接需要补缺失信息；受限收口按第 4 章保留决定 |

Git 记录修改与历史，不单独证明检查已经执行。提交说明或已有交付中应有本批必要检查和限制；正式验证仍须有对应结果及必要原件。C 的独立判断和 E 的实际结果各由其负责，合并事件记录不合并或代替独立职责。

等待、轮询、重复回执、没有新结论的讨论和普通机械修正不单独创建工作记录。不会参与结论的临时输出无须全部归档，不为留痕额外实施测试或制造任务。

### 5.2 按重要事件补充记录

现有材料无法清楚回答“做了什么、为什么作出取舍、验证到哪、剩下什么、谁承接”时，补缺失信息。复杂异常、较长返修因果、重要争议和特殊交接可在 `records/Mxx/YYYYMMDD-topic.md` 集中说明；一个事件可以连接 D 实现、C 审核和 E 验证，不要求三者各抄一遍过程。

事件记录注明责任作者和引用来源，结论仍指向对应角色的有效交付。由首次建立者或 A 指定的维护者负责该文件，其他角色提供自身结论和证据链接；同一文件串行写入，不要求 A 为每条消息转抄材料。

常规历史由 Git 和共享交接保留。引用过去的审核、放行或用例时，说明当时对象及相应提交或固定消息，不能仅指向后来已更新的同名文件。当前正文继续维护有效结论，必要事件记录补充原因和关联，不重复保存全部当前表格。

<a id="evidence-policy"></a>

### 5.3 原始、派生及通信材料

每轮正式验证须能共同定位实际候选、采用的用例、必要环境和操作范围、实际结果及原件。报告或已有记录已经具备的信息直接引用，不强制每个证据目录再填写一套表。身份信息以足够区分实际对象为准，不机械要求所有文件使用同一种校验字段。

原始日志、截图、测量和回读保留本轮内容，失败、阻断及必要上下文同样保留；后续成功或复测不覆盖旧原件。采集范围围绕本轮条件、关键过程和结果确定。未执行写未测，证据不足写待补证，失败保留失败；资料、主机检查和真实环境结果按实际覆盖表达。

从原件生成的统计、解析结果和汇总须标明来源，不能以派生文件代替缺失原件。修正后说明哪些用例重测、哪些旧结果仍适用及依据；对象或条件变化时只补受影响检查。研究证据有效性、指标达成和研究完成按[研究边界](多AI会话工作流规范.md#research-boundary)分别判断。

大型镜像、构建输出和既有工具日志可留在项目已确认的存储位置，保存可共享、持久且稳定定位的引用。当前结论、失败分析和后续复用依赖的重要材料不自动清理；临时输出不纳入正式证据，不能以“减负”删除必要失败原件。

通信优先引用工具已保存的关键正文、任务归属和回执。确需统一归档时放在 `evidence/Mxx/communication/`，由工具保存或按批导出，不要求人工逐句转录。通信只证明派工和交接，不能作为功能、实物验证或独立审核通过的证据；原生历史不满足共享和持久条件时，按[交接要求](多AI会话工作流规范.md#handoff-record)补必要内容。

### 5.4 更新频率与工作深度

- `STATE.md` 在阶段、责任、阻断、有效结果或下一步变化时更新，保留当前组编号并引用 SESSIONS，不登记完整模型和会话表；等待用户决定时注明待决定内容和现有授权范围。
- `SESSIONS.md` 或其唯一来源在配置、绑定、替换及有意义的会话生命周期变化时更新，具体任务进展仍由 STATE 维护。
- REVIEW/TEST_REPORT 在对象、有效结论或证据改变时更新，重复通知和等待不制造新版本或新记录。
- 索引只在新增重要材料或入口变化时更新，已有文件正文更新不要求逐消息、逐提交新增索引行。
- V1 使用简短交付和必要证据，保护、独立审核及规定验证照常完成；V2 增加改善前后和针对回归依据；V3 在既有用例与报告中明确方法、条件、覆盖及可重复原始数据，不按深度配齐五类过程文件。

## 6. 索引、引用与文件拆分

项目 `AGENT.md` 提供 AI 总导航，目录材料较多时再设置 `INDEX.md` 或已有等价索引。索引只登记主题或任务、简短结论和链接；不能把 `README.md` 设为唯一必经入口。

跨文件引用优先使用可点击链接和稳定标题或语义锚点，避免只写会漂移的章节号。目录或文件调整后检查受影响链接；项目间复制实例后调整其引用。未变化的资料通过引用复用，不为每个里程碑或会话复制整套规则。

阶段审核、验证摘要以 250 行作为整理参考；常规历史沿 Git 定位，接近时先移出长输出和确需独立解释的事件，不为满足行数裁掉必要依据，也不为整理正文新增重复记录。设计、单轮记录或索引过长时按主题、模块或时间拆分，原入口保留必要导航。

## 7. 维护责任与会话恢复

总体方案和里程碑划分阶段，由本轮方案整理者维护材料，用户确认对应决定，无需提前建立 ABCDE 会话。进入里程碑后的维护分工按工作流执行：

| 材料 | 维护责任 |
|---|---|
| 项目 `AGENT.md` 与公共导航 | 项目指定的维护者；进入里程碑后由 A 协调变更和公共写入 |
| 当前状态与阶段接续入口 | A |
| 项目协作约定 ROLES | A 协调维护；实质流程或权限变化沿用户确认 |
| 会话配置与登记 SESSIONS | A 或获授权配置维护者；核对实际工具后串行更新，已有配置保持唯一来源 |
| 获批方案及对应决策依据 | B |
| 生产实现、开发自测及其工具、融合说明 | D |
| 正式验证用例、执行和采集脚本、验证摘要及对应证据 | E |
| 独立审核结论、审核辅助工具和审核记录 | C；跨阶段缺陷涉及旧结论时，当前 C 按[适用性规则](多AI会话工作流规范.md#prior-verdict)补充旧审核入口 |
| 会话脚本索引、共享交接及对应证据入口 | 对应会话或本批作者；只补实际变化，公共索引串行更新 |
| 按需事件记录 | 该事件指定维护者；引用各角色独立结论，A 协调共享文件归属，不逐消息转抄 |

同一可变文件同时只有一个写入者，公共索引和 Git 写操作串行。机械性小修、各用途脚本修改、方案问题和实测后复测，均按[工作流修正规则](多AI会话工作流规范.md#4-问题返回修正与研究判定)办理，不另设一套权限。

各角色工作目录及成果汇合方式沿[工作目录规则](多AI会话工作流规范.md#workspace-integration)在 ROLES 说明、在 SESSIONS 登记实际目录；构建、审核和验证使用稳定对象，不因只串行写文件就推定读取期间没有变化。

本批作者保存实际交付与必要证据，按第 5 章复用已有材料或补事件记录，只更新实际变化的摘要和入口，再按固定接续交给相应角色并同步 A。同步用于更新状态，不再次派发；具体触发者与重复处理按[工作流交接规则](多AI会话工作流规范.md#52-固定接续报告与重复处理)执行。

新里程碑按[会话组规则](多AI会话工作流规范.md#51-每个里程碑新建会话组)建立全新 ABCDE，同阶段修正和复测继续使用本组。换组或个别会话替换时，在已有状态和记录中留下当前对象、未提交成果、结果限制、待承接验证、资源状态和下一入口，再沿 `SESSIONS.md` 更新唯一绑定来源，保留旧任务和旧组归属，不增加重复交接表。

会话启动与压缩恢复必须执行[共同读取清单及 ABCDE 补读矩阵](多AI会话工作流规范.md#session-recovery)，通过项目 `AGENT.md` 定位当前原文，摘要不替代规则；真实会话标识及工具配置始终按项目唯一来源使用。文档已更新不等于运行会话已切换，工具通知送达也不等于工作已完成。
## 8. Git 提交与远程同步的材料维护

ABCDE 每批文件操作交付前提交、每个里程碑结束正常推送的执行要求，统一见[工作流 Git 规则](多AI会话工作流规范.md#git-delivery)。项目 `AGENT.md` 指向仓库、远端和分支的唯一配置来源；`ROLES.md` 约定推送执行者及交接。会话模型和身份仍由 `SESSIONS.md` 承载，不与当前任务进度混写。

本批作者在提交前同步实际变化的正文、结果和必要入口，显式提交本批文件；没有新增事件或入口时，不为提交配套新建记录和索引行。原始证据按项目已确认方式保存，记录必须能定位实际对象。提交后在交付消息报告提交标识，推送成功回执随阶段交接保存，不为回写当前提交标识或推送回执形成循环提交。

工具持续追加运行日志不按每条消息触发一次提交。按交付批次封存需要共享的证据，再提交或引用项目已确认的持久存储；回执和日志不得触发自我重复的报告与提交循环。
