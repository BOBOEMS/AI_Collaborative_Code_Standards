## 统一教学快照

本例采用 V1 深度，计划 M01 → M02 → M03 → M04 串行推进。采用 M01 本地安装恢复的教学过程，候选由 DEMO-M01-R1 修正为 DEMO-M01-R2；当前阶段和进度统一由 [STATE.md](STATE.md)维护。

演示过程为：B/用户确认后，A 派发 D 实现、自测及 E 用例准备，再安排 C 审核；E 验证发现无备份维修准入失败，回报 A，由 C 明确修正要求、A 安排 D 修正；之后 A 依次安排 C 针对复核、E 复测及 C 证据审核，最后核对收口。原失败保留，未受影响结果由 C 说明复用依据；只为重要确认与复杂异常保留独立记录。

原六项用例遗漏了合格备份下的 Boot 维修成功，旧收口不能支持该功能完整覆盖。示例继续在同一 M01 补充 T07，另存 R03 合成材料，并由 C 明确六项旧结果的复用依据后重新核对收口；原 R01/R02 和旧消息不改写，不提前进入 M02。

[按需读取和接续分支](#flow-branches)补充说明方案改变、无需当期 E 验证、研究否定结论、条件不足及后续发现旧缺陷时的处理；这些是假设情形，不是额外执行记录。

所有候选名、会话占位符、提交/推送回执、日志和数据都是教学材料，均未执行真实会话创建、固件构建、烧录或板测。工具仅运行离线数据处理，不能把示例 PASS 当作真实产品验收。后续里程碑只保留计划，不预生成具体设计和会话。

配置示例只说明已接入适配器的组织方式，写动作授权与真实绑定均为空。工具能力和既有验证直接沿 [session_handover_tool](../session_handover_tool/README.md)及其验证记录读取，示例不要求重复执行工具验证。

## 按需阅读：任务读取与特殊接续

本节用于学习和维护示例，不列为执行会话的共同必读。下表按[唯一读取规则](../多AI会话工作流规范.md#session-recovery)演示怎样选读；“共同读取”仍包含当前入口、共同底线、任务/授权、绑定及作用于当前任务的项目约束，不以摘要代替。

| 场景 | 共同读取之后的主要路径 | 要核对的执行边界 |
|---|---|---|
| D 修正已明确的实现错误 | [D 权限](../多AI会话工作流规范.md#role-d) → [实现/自测](../多AI会话工作流规范.md#implementation-preparation)、[复测范围](../多AI会话工作流规范.md#retest-scope) → 相关 DESIGN、C 问题、源码 → [交付](../多AI会话工作流规范.md#handoff-content)、[提交](../多AI会话工作流规范.md#local-commit) | 只修获批问题；原失败场景仍承接必要复测；不加载总体方案编写方法或研究展开 |
| C 审核实现 | [C 权限](../多AI会话工作流规范.md#role-c) → [审核和放行](../多AI会话工作流规范.md#review-gate)、[问题分类](../多AI会话工作流规范.md#problem-routing) → 获批设计、实际差异、自测和未关闭问题 | C 保持独立；代码通过不等于实测通过；涉及证据时补读原件及其规则 |
| E 执行正式验证 | [E 权限](../多AI会话工作流规范.md#role-e) → [放行](../多AI会话工作流规范.md#review-gate)、[方法](../多AI会话工作流规范.md#validation-method)、[异常停止](../多AI会话工作流规范.md#test-anomaly)、[证据](../文档组织与维护.md#evidence-policy) → CASES、C 固定组合、实际对象/环境及工具 | 未放行或条件不足不擅自执行；失败和未测按真实范围交付，原件不覆盖 |
| A 同阶段替换会话 | [A 权限](../多AI会话工作流规范.md#role-a) → [替换接续](../多AI会话工作流规范.md#session-replacement)、[登记](../多AI会话工作流规范.md#session-register) → 旧任务、停点、原结果及余项；实际调用时再读所用工具操作 | 唯一收集者、旧执行停手、冻结归属、剩余工作新任务均需明确；不靠换绑定迁移旧回报 |

以下为假设分支，不改变 STATE 的教学快照，也不说明这些情况已经执行。详细技术与权限判断仍沿所引规则办理。

| 假设情况 | 接续与停点 | 复用或更新的现有材料 |
|---|---|---|
| 实测表明已确认方案本身无法满足目标 | C 向 A 说明事实，A 派发 B 分析；B 提出实质变更并待用户确认，再由 A 安排 D/E、C 和必要复测 | 重要决定、受影响 DESIGN/共用设计及 CASES、审核和报告；保留原失败 |
| 软件阶段的计划只要求 D 自测及 C 审核，没有当期 E 正式验证 | D 回报 A，由 A 派发 C 审核，再按软件范围核对结束；E 待命，真实联动交指定后续阶段 | DESIGN、REVIEW、STATE 和原有交付；不创建空 CASES 或 TEST_REPORT |
| 研究问题是判断指定条件能否达到指标，完整执行后得到否定结论 | E 报告实际数据，C 判断证据与研究完成条件；A 可按约定结束研究，工程指标仍记未达到；需要新方案时才交 B/用户 | 现有 CASES、TEST_REPORT、REVIEW 和 STATE，不为得到 PASS 自动扩展研究 |
| 缺少研究必需设备或输入，计划未完成 | E 保存已有材料并注明未执行范围，C 判断证据不足；A 说明阻断和待决定事项，由用户决定补条件或受限结束 | 当前报告、审核和状态；不能写成研究完成或指标已被证伪 |
| 后续阶段发现旧阶段的实现缺陷 | C 明确要求，A 派发当前 D 修正并安排受影响审核、验证；C 同时限制旧结论复用并关联新修复 | 旧 REVIEW 的适用性说明和当前阶段交付，不恢复旧组或重写旧证据 |
| 本阶段 A 因故障更换，旧任务仍回报原 A | 新 A 为唯一收集者，从旧任务正文、原件和回执收集；旧 A 不可用时由原作者补可访问的必要交付并通知新 A，不重做已完成验证 | STATE、原任务与成果入口；原快照及接收者不改写 |
| 本阶段 D 未做完需更换 | 先确认原 D 停止并移交资源，A 向新 D 派发引用旧任务的新任务，仅承接余项；新 D 只回报自己的新任务 | STATE 记录旧任务停点、新任务和剩余项，SESSIONS 保留新旧真实绑定 |

阶段交付和后续启动继续按 [ROLES](ROLES.md#project-git)及实际授权办理，不从这些示例推断新增权限。
