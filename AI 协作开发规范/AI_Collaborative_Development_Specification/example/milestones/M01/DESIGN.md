# M01：基础启动与本地升级恢复

规定位置：`AI/milestones/M01/DESIGN.md`。当前由 B 维护，依据为[教学范围确认](../../records/decisions/20261019-M01-scope.md)。本文件全部用于演示，术语见[总体方案](../../PROJECT.md#术语与阅读说明)，DEMO 为教学候选标识。

## 1. 目标与范围

承接 [PLAN.md 的 M01](../../PLAN.md#3-m01基础启动与本地升级恢复)：使 Boot/App 正常启动，以蓝牙来源完成请求、旧 App 备份、新镜像安装、试用确认及必要失败恢复或维修。

本阶段验证 F-01 的启动确认、F-03/F-04/F-05 及 F-07 的最小本地主机支持；完整业务交 M04，版本包交 M02，4G、URL 写入交 M03。本例不扩展实际掉电矩阵、长期压力或 Boot 自升级。

## 2. 依据和前提

采用 [shared_design.md](../../shared_design.md)的区域与保护约定。真实实施前须核实设备、匹配 Boot/App 链接镜像、备份容量、测试包及操作授权；本教学场景仅假定这些条件已在场景内确认，没有提供可操作设备参数。

本阶段 C/H 实现沿[项目采用边界](../../PROJECT.md#c-adoption)使用 C 规范，入口及实际工程配置由 [AGENT](../../AGENT.md)定位。D 将适用分片和自检关联已有交付，C 在现有实现审核中核对；本阶段正式验证仍采用 CASES，不因接入语言规范追加功能或研究。

FRAM 容量矛盾已记录，当前只核对事实，不进行 URL 持久化操作。实际来源见[示例边界](../../README.md#source-facts)。

## 3. 模块及关键连接

以下是教学职责划分，源码名仅说明实施范围，不代表本示例提供固件：

| 模块 / 示例源码 | 当前职责 |
|---|---|
| App 本地升级服务：`App/ota_service.c` | 本地初始化成功后确认运行；验证本地请求，完整提交后复位交 Boot |
| Boot 请求与安装：`Boot/ota_install.c` | 解释有效请求，核对镜像和恢复条件，完成备份、安装及阶段提交 |
| Boot 试用恢复：`Boot/ota_recovery.c` | 限制新 App 试用，确认后转正常启动；失败恢复或停留维修 |
| Boot 本地来源：`Boot/local_source.c` | 请求并读取目标镜像片段，检查本次数据有效，失败交统一出口 |
| 主机最小供包工具：`host/local_update.py` | 按设备请求供给对应包，保持候选、版本和长度关联 |

正常链路：健康 App 接收本地请求 → 核对目标包 → 完整提交请求并复位 → Boot 核对恢复条件 → 合格旧 App 备份 → 安装并校验新 App → 有限试用 → App 本地初始化成功后确认。

维修链路：App 不可用时进入 Boot 维修入口 → 核对已有合格备份及目标包 → 通过准入后安装 → 新 App 启动并确认。该入口的成功由 T07 独立验证，不能由健康 App 升级 T02 或无备份拒绝 T05 代替。

关键失败：

- 请求不完整或镜像错误：拒绝提交或安装，保持可运行对象，记录原因。
- 备份失败：不将其标为有效，不覆盖 App。
- 无合格备份的维修请求：在任何 App 擦写前拒绝，保持区内容不变。
- 试用失败：合格备份可用时恢复，否则保留可操作维修入口。
- 代表性复位中断：依据保留阶段和实体检查恢复到可操作状态；不将复位结果推广为实际掉电结论。

## 4. 实施任务和交付

| 任务 | 承担者 | 交付 |
|---|---|---|
| D-01 | D | 实现上述生产模块及最小主机接续，核对实际工程接入和镜像配对，提交候选及开发自测 |
| E-01 | E | 实现七项[正式用例](CASES.md)的操作/采集办法，准备对象和停止条件，交 C 审核 |
| C-01 | C | 对实现、自测、用例和实际证据分别给出当前结论；验证启动组合写入 [REVIEW.md](REVIEW.md) |
| A-01 | A | 维护当前任务、固定接续和资源移交，核对完成条件、提交及阶段推送 |

D 必要自测包括工程构建和镜像范围、请求拒绝、备份有效性、维修擦写前置判断及受影响原业务接入。C 核对真实实现与自测对象，不能将样例配置检查当作生产代码验证。

实际交付的候选和实现审核沿 [REVIEW.md](REVIEW.md)定位；发现既定保护未实现时，按获批范围交 D 修正、自测，再由 C 针对审核。复杂异常按需要记录，不分别编写 D/C/E 的重复过程文件。

## 5. 审查与验证

D 实现与 E 用例准备可按接口就绪程度协作；正式执行须由 C 确认可执行的候选、用例及范围。本例七项用例需要实物观察，操作方法和停止条件见 [CASES.md](CASES.md)。

生产修正后按影响范围复测，包含原失败场景及相关正常、恢复路径；C 核对未重测结果的适用性。实际放行组合和复用判断在 [REVIEW.md](REVIEW.md)，执行结果在 [TEST_REPORT.md](TEST_REPORT.md)。离线工具仅整理和审核教学材料，不驱动设备。

## 6. 完成条件与结果入口

健康 App 升级、合格备份下的 Boot 维修安装及无备份维修拒绝分别取得所需实物结果，其他关键失败和恢复代表场景满足要求，C 的实现、用例及证据审核有效，任务和资源已交接，文件已提交且阶段远程同步完成时结束。

当前实现、用例及证据结论沿 [REVIEW.md](REVIEW.md)、[TEST_REPORT.md](TEST_REPORT.md)取得；是否收口、Git 同步、资源和下一步由 [STATE.md](../../STATE.md)定位。复杂维修准入异常见[事件记录](../../records/M01/20261019-repair-guard.md)，本设计不保存当前候选或阶段完成状态。
