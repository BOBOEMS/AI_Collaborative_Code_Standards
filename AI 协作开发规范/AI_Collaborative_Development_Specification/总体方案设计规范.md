# 总体方案设计规范

所属规范：嵌入式 AI 协作开发规范。更新日期：2026-10-20。

AI 入口：[协议使用入口](AGENT.md)。实例：[Reuse_RTU OTA 总体方案示例](example/PROJECT.md)。

## 1. 定位与适用范围

总体方案明确产品总目标、当前版本范围、主要功能、系统关系、关键约束和完成判断，为后续里程碑划分提供依据。

本分册适用于新产品建设及已有产品的功能扩展。已有方案可以映射、引用并补齐必要差异，无需重新设计整个产品。正文中的“必须、不得”表示执行要求；“应”表示默认做法，偏离时说明理由；“可”表示按需要采用。

总体方案设计到主要能力与系统关系清楚、能够判断范围和依赖的程度。各功能的具体实现设计在对应里程碑中讨论、确认和实施。

本层确定必要审查与实物验证的目标。里程碑如何划分、每个里程碑是否上板、哪些功能闭环后组合实测，以及多 AI 角色和调用方式，由后续相应规范与项目安排确定。总体方案不预设代码实现和测试必须完全分为两个阶段。

### 1.1 成果文件与存放位置

`AI/` 表示项目唯一的 AI 协作文档根目录，实际位置由项目 `AGENT.md` 登记。新项目按以下位置建立；已有等价资料时在入口登记明确映射，所有会话共用该映射。

| 成果 | 规定位置 | 建立时机与维护者 |
|---|---|---|
| 当前总体方案 | `AI/PROJECT.md` | 总体讨论形成可审阅草案时建立，设计者维护，用户确认目标与实质选择 |
| 共用详细设计 | `AI/shared_design.md` | 符合[共用设计条件](#shared-design)时再建立，当前里程碑 B 维护 |
| 分册后的共用设计入口 | `AI/design/INDEX.md` | 共用主题确需拆分时建立，列明各分册用途、适用范围及链接 |

总体方案的推荐正文结构见第 3 章。项目总体方案与[示例总体方案](example/PROJECT.md)对应；材料维护和目录汇总见[文档组织与维护](文档组织与维护.md)。

## 2. 三个版本的工作深度


| 阶段 | 主要目标 |
|---|---|
| **V1 初版** | **实现确认的功能，跑通完整链路，完成必要保护、审查和实物验证** |
| **V2 优化** | **根据实际使用修复问题，优化资源、结构和体验，做针对回归** |
| **V3 深度研究** | **按需要研究最坏时序、完整故障矩阵、全路径资源和长期压力** |

使用时遵守以下规则：

1. 总体方案必须标明当前工作深度和本轮版本目标。各深度可包含多轮迭代；是否开展 V3、研究哪些问题，由实际需要决定。
2. V1 以完成已确认功能和必要保护、打通功能链路为目标。基本容量与可行性检查、必要失败处理、兼容性、恢复和实物验证按本轮实际功能要求完成。
3. 编译失败、越界、误擦写、死锁、升级或恢复失败、破坏既有业务等影响本轮功能正确性的问题，必须在当前范围内处理；超出授权时报告并由用户决定处理范围，不以“后续优化”自动后置。
4. 一般资源精简、结构改善和体验优化可进入 V2；最坏时序、完整输入或故障矩阵、全路径资源证明及长期压力研究可按需要进入 V3。不得把这些工作自动作为所有 V1 功能推进的前置条件。
5. 如果某项时序、资源或可靠性指标本身就是当前版本的必要功能或硬件约束，仍须取得支撑该能力的必要依据，不能仅因归入 V1 而后置。
6. 后续版本先记录方向和实际问题，不要求在 V1 总体方案中完成其全部设计。启动后续版本时再确定本轮目标、影响范围和验证要求。

## 3. 总体方案的七类内容

项目可在一份总体方案中按以下七节组织；已有同等职责的资料直接引用。内容复杂时再按主题拆分，并保留一个有效入口。

### 3.1 项目总目标

说明产品面向谁、用于什么场景、解决什么问题，以及最终希望具备的主要能力。目标应能对应可观察的结果，避免只写“稳定、高效、可扩展”等无法判断的描述。

已有产品须说明本次建设与原产品的关系：新增、替换或保留哪些能力。区分长期方向与当前版本交付，不能把长期愿景默认全部纳入本轮。

### 3.2 当前版本范围

必须明确：

- 本轮采用的工作深度，以及本轮必须交付的能力。
- 本轮明确暂不做的内容。
- 必须保持的既有业务、兼容性及外部行为。
- 后续版本的方向或已知问题；只记录必要内容，不提前展开完整设计。

范围应足以支持后续取舍。必要保护和关键失败处理随对应功能纳入本轮，不能把“主流程能运行”单独当作 V1 功能完整。

### 3.3 主要功能

按可观察能力组织功能，不按函数、文件或代码行数机械拆分。每项主要功能使用简短且稳定的编号，供里程碑和验收引用；沿用已有编号即可，不另建重复的映射表。

每项功能说明以下内容，可用表格或短段落表达：

| 项目 | 应回答的问题 |
|---|---|
| 功能与目的 | 用户或系统获得什么能力，服务于哪个目标？ |
| 触发与输入 | 什么条件下发生，需要什么信息或前置状态？ |
| 预期结果 | 正常情况下应产生什么可观察结果？ |
| 关键失败行为 | 主要失败时如何退出、恢复或继续业务？ |
| 依赖与完成判断 | 依赖哪些能力，观察到什么才算实现？ |

只展开会影响产品行为、功能连接和后续划分的内容。函数、内部状态机、算法、缓冲管理和具体测试用例，由对应里程碑细化。

### 3.4 系统结构与主要流程

明确设备、软件、服务器、主机工具和外设等系统边界，以及主要模块各自的职责、输入输出和上下游关系。只列实际需要的参与方和模块。

至少讲清一条完整正常路径和关键失败路径，能沿“触发 → 判断或处理 → 结果 → 后续去向”解释系统如何工作。图、表或步骤均可，不要求同时提供多种等价表达。

跨模块共同遵守的关键约定，以及影响多个里程碑的总体选择，应在这一层确定。例如安装与恢复由谁负责、数据由谁产生和使用、不同来源如何进入共同流程。

本层不要求列出全部源码文件、函数及其签名。已有模块或工程可引用其入口，具体文件和调用设计在里程碑中补齐。

### 3.5 关键约束与总体取舍

列出影响整体选择的实际约束，例如目标硬件及容量、固件空间、外部协议、业务兼容、数据保留和必要运行条件。区分已确认事实、待核实假设和方案决定，引用依据或已有权威资料。

对会影响功能范围、整体可行性或多个里程碑的选择，说明采用什么方案、为什么，以及需要接受的限制。仅在有实际选择时比较候选，不为凑数量制造方案。

V1 应确认基本可行性，例如目标空间是否容纳固件、存储是否支持所选恢复策略。具体线程栈、局部缓冲、逐路径耗时等在相关里程碑中确定；只有影响总体选择时才提前展开必要部分。

指标和阈值应来自产品要求、硬件事实或经确认的取舍。不得为了完整填写方案自行增加严格时序指标、额外保护、重试策略或未来扩展功能。

### 3.6 总体验收目标

总体方案必须明确预期结果，至少覆盖：

- 各项主要功能的完成判断，可直接引用功能条目中的内容。
- 多项功能连接后的完整使用场景。
- 必须保持的既有业务及兼容性。
- 必须正确处理的关键失败、恢复或退出场景。
- 哪些结论需要真实设备、外设或运行环境验证，以及必要条件。

这一层定义验证目标与必要条件，不要求编写全部测试步骤或完整异常矩阵。具体审查对象、用例、验证时机和执行安排，在后续里程碑设计与划分中确定。

完成声明必须区分设计已确认、实现完成、主机检查通过、实物场景通过和整体验收完成。未执行的项保留未测，实际失败保留失败，不能由方案确认或软件完成推断实物通过。

完整验收须满足当前版本已确认的功能和验证目标，并由用户确认。因明确条件限制需结束当前轮次时，可由用户决定受限收口，记录接受的失败、未测、影响和后续处理条件；受限收口不能改写原验收结果，也不等同正式发布。

### 3.7 未决事项

每项未决事项写明问题、影响范围、需要什么依据或决定，以及最晚在什么工作开始前解决。已有结论明确的限制直接记录事实，不重复列为未知。

- **影响总体选择的事项**：在确认相关总体方案前解决，或由用户明确暂不确认受影响范围。
- **影响局部实现的事项**：交给对应里程碑细化，在依赖它的工作开始前解决。
- **影响实物验证条件的事项**：说明所需设备或环境，在相应验证开始前核对；不默认阻断独立的软件或设计工作。

未知项只阻断实际依赖它的决定和工作；其他工作仍限于当前获批范围，实施按[里程碑串行规则](里程碑设计规范.md#milestone-order)推进。必要预研围绕具体问题，提前说明试验范围、需要取得的结论和停止条件；取得足以支持选择的依据后结束该项调查。实际代码或设备操作遵守项目授权。

## 4. 总体方案的设计深度

| 总体方案应确定 | 在对应里程碑中细化 |
|---|---|
| 产品目标、当前版本范围、主要功能与完成结果 | 各功能具体设计、实施任务和验证用例 |
| 系统边界、模块职责、正常及关键失败主路径 | 源码文件、函数、内部状态机、调用与调度细节 |
| 影响多个里程碑的共用约定和总体技术选择 | 局部算法、缓冲管理、错误码和实现参数 |
| 实际硬件及兼容约束、基本可行性 | 局部资源预算、具体工具和检查步骤 |
| 总体验收目标与必要真实环境条件 | 上板节点、组合验证、执行者和测试脚本 |

划分依据是影响范围。如果具体字段、时序或内部选择已经影响多个功能、外部兼容或总体可行性，就提前确定必要部分；其余细节仍留给里程碑。

## 5. 讨论、审查与确认

推荐顺序：讨论目标和范围 → AI 整理总体方案 → 集中审查 → 修正必要问题 → 用户确认 → 进入里程碑划分。

AI 负责调查必要事实、整理方案和取舍建议。用户确认目标、当前版本范围、主要产品行为和总体选择。总体方案确认不要求用户预先独自设计完整工程。

形成完整草案后做一次集中审查，重点检查目标覆盖、范围清晰度、模块连接、共用约定、关键失败行为、整体可行性假设和完成判断。高风险总体选择可安排独立上下文审查；修正后针对问题及受影响部分复核，不以反复“零问题”作为结束条件。

同时满足以下条件，即可确认总体方案并进入里程碑划分：

1. 目标和当前版本范围明确。
2. 主要功能可理解，结果可以判断。
3. 系统关系和主要流程可解释，关键失败有明确去向。
4. 关键约束与总体选择有必要依据。
5. 总体验收目标及必要真实环境条件明确。
6. 不存在阻碍划分的重大未决事项；其余事项已有影响范围和解决时点。

确认依据可在方案的确认章节或已有重要记录中保存，只保留实际方案版本或内容标识、用户确认来源、适用范围及剩余事项；不为普通确认一律新建记录文件。总体方案确认支持进入后续规划，不自动等同全部代码实施、设备操作或发布授权。

## 6. 文档与后续变更

总体方案的当前有效正文维护在 `AI/PROJECT.md`；已有等价文件时按 1.1 节登记映射。项目 `AGENT.md` 提供 AI 导航与项目约定，`README.md` 用于说明介绍，不要求 AI 必须读取；文件位置和维护方式按[文档组织与维护](文档组织与维护.md)执行，不强制迁移目录或新建整套表单。

后续里程碑补充内部实现细节时，在对应设计中维护。需要改变总体目标、当前版本范围、主要产品行为或跨模块约定时，先由用户确认受影响部分，再更新当前有效总体方案；决定经过单独记录，未变化内容继续复用。

总体方案保留当前有效目标、功能、约定及必要引用。普通实现、审核和验证交付由当前成果、提交历史及共享交接定位；重要取舍和复杂异常按[记录触发规则](文档组织与维护.md#record-policy)保存，正式验证原件进入证据位置。实际状态由项目状态入口维护，不在总体方案累计工作日志。

## 7. 共用设计的建立与维护

### 7.1 建立条件与边界

多个里程碑共同采用、需要集中维护的详细技术约定，才建立共用设计。例如 App 与 Boot 共用的存储布局、多个模块共同解释的消息字段。已有工程权威文档能够承担职责时直接引用，不再复制正文。

总体方案确定会影响整体选择的关键约定；共用设计承载产品及工程的必要详细技术内容；仅当前里程碑使用的实现细节保留在 `AI/milestones/Mxx/DESIGN.md`。文件维护、工具分工及 Git 等协作规则沿[工作流](多AI会话工作流规范.md)和[文档组织规则](文档组织与维护.md)使用，会话配置与登记由 `AI/SESSIONS.md` 承载。共用设计不构成新的独立设计阶段，也不要求预先设计所有未来能力。

进入相关里程碑、当前工作确实需要时，由本组 B 整理，沿现有方案确认流程形成有效依据。没有共用详细技术内容时，不建立空白 `shared_design.md`；项目必需的协作和恢复约束不能只放在这一可选文件中。

### 7.2 内容与引用

`AI/shared_design.md` 按实际主题说明：

- 用途、适用范围和采用它的里程碑。
- 已确认的具体约定，如布局、接口、数据含义或共同限制。
- 当前约定的必要理由、事实依据和仍待确认的部分。
- 相关方案及决策记录入口。

细节只展开到当前依赖成立所需的程度，不复制各里程碑的任务、进度或验证结果。`PROJECT.md` 和采用它的里程碑设计引用具体章节，保持一处有效定义。

### 7.3 变更与分册

当前 B 维护共用设计。改变已确认约定时，说明对当前及既有成果、配置和证据的影响，由用户确认实质方案调整后更新正文，再由本组 D/E 实施、C 针对审核或核对验证。不因共用设计改变而自动恢复旧会话组，也不沿用已不适用的通过结论。

独立主题增多，集中阅读、维护或引用已经不方便时，将正文拆入 `AI/design/`，如 `storage_layout.md`、`communication_protocol.md`。以 `AI/design/INDEX.md` 为唯一共用设计入口，正文迁入分册，同步 `AGENT.md`、总体方案及里程碑的有效引用。原 `shared_design.md` 不再保留重复正文；兼容已有引用确有需要时，只保留指向新入口的说明。

索引、拆分与记录的通用方法按[文档组织与维护](文档组织与维护.md#6-索引引用与文件拆分)执行。
