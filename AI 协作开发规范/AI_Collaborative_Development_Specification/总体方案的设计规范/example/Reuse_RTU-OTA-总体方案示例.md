# Reuse_RTU OTA 总体方案示例

编制日期：2026-10-16。采用规范：[总体方案的设计规范](../总体方案的设计规范.md)。

本文件以 Reuse_RTU 已确认的目标、技术选择和项目经验，演示总体方案的七类内容。下文功能和验收描述表示应达到的目标；实际结果单独注明。本示例用于规范说明，不替代该项目的有效方案，不产生新增实施或测试授权。

事实来源：[项目总体设计](../../../../../Reuse_RTU/5.Document/si/design/OVERVIEW.md)、[初版方案](../../../../../Reuse_RTU/5.Document/si/PLAN.md)、[当前状态](../../../../../Reuse_RTU/5.Document/si/STATE.md)、[受限收口决定](../../../../../Reuse_RTU/5.Document/si/records/V1-A-limited-closeout-20261016.md)。实际状态快照截至 2026-10-16；此后的项目变化查其有效入口。

## 1. 项目总目标

为低功耗地下水监测测控终端增加本机 App 固件升级能力。设备在自身启动周期内主动检查并取得新固件，由 Boot 安装和管理新固件；升级失败时按约定恢复或进入可操作的蓝牙维修状态。

升级能力接入后，保持原采集、阀门、查询、正常上报和离线补报业务。设备休眠期间由服务器主动唤醒 MCU，不在本次目标中。

## 2. 当前版本范围

当前工作深度为 **V1 初版**：实现确认的功能，跑通完整链路，完成必要保护、审查和实物验证。下一节 F-01～F-07 均属于本轮功能目标。

本轮包括 4G 主动检查和下载、Boot 安装与恢复、试用确认、蓝牙升级与维修、版本和 URL 配置，以及配套发布工具。

本轮不增加 Boot 自身或模组、外设固件升级，不增加双 App 槽、平台推送 URL、完整低功耗改造或新的晚期卡死维修策略。

后续方向依照[工作深度规则](../总体方案的设计规范.md#2-三个版本的工作深度)：

- **V2 优化**：依据实际使用和本轮问题，安排资源精简、结构和体验优化及针对回归；具体问题和范围在启动该轮时确定。
- **V3 深度研究**：按需要研究最坏时序、全路径栈堆资源、完整故障与实际掉电矩阵，以及长期压力。

当前版本的必要恢复、完整性检查、请求互斥和业务保持随功能实现。已知功能失败与未测项按第 6、7 节保留；不能通过改称 V2/V3 工作使其变成 V1 已完成。

## 3. 主要功能

### F-01 启动与原业务保持

- **目的**：设备正常启动并运行原业务，OTA 接入不破坏业务处理。
- **触发与输入**：设备启动、必要本地初始化结果、网络和业务事件。
- **预期结果**：本地初始化成功后按约定确认 App；OTA 检查期间保持业务事件消费，首次连接按检查结束条件放行。
- **关键失败**：本地初始化失败不确认成功；提交升级前的一般检查失败清理后继续原业务；开始提交升级后按升级路径复位，不重新放行业务发送。
- **依赖与完成判断**：依赖原 App 和升级检查状态；启动及确认正常，无升级和一般检查失败时原业务可继续，提交后交接正确。

### F-02 4G 新版本检查与下载

- **目的**：取得符合条件的新 App 固件，供 Boot 安装。
- **触发与输入**：每次 MCU 启动网络就绪后检查一次，使用本机版本、服务器 URL 和版本清单。
- **预期结果**：仅在存在符合条件的更高版本时下载目标文件，并核对本次下载完成和文件长度。
- **关键失败**：无新版本、清单失败、下载失败或长度不符时，不提交错误升级请求，回到原业务路径。
- **依赖与完成判断**：依赖 F-06 的版本和配置、Air780 通信及 F-03；新版本能进入安装，无升级和一般失败分支能继续业务。

### F-03 升级请求与安装

- **目的**：将合格来源的新镜像安装到 App 区，并保留必要恢复条件。
- **触发与输入**：App 或 Boot 维修入口取得合格升级请求及对应镜像信息。
- **预期结果**：请求完整提交后交给 Boot；覆盖当前 App 前具备合格旧镜像备份；安装完成并通过镜像校验后进入新 App 试用。
- **关键失败**：部分提交不能作为完整请求；残缺备份不能标为有效；安装失败、中断或坏包不能被当作可运行新镜像。
- **依赖与完成判断**：依赖持久状态、外部备份存储及来源读取，连接 F-04；真实来源升级后新 App 可启动，关键失败按恢复或维修路径处理。

### F-04 试用确认与失败恢复

- **目的**：限制异常新固件的试用，失败时恢复可运行状态或进入维修。
- **触发与输入**：新 App 安装完成、App 本地确认结果、启动失败或中断后的保留状态。
- **预期结果**：新 App 在有限试用内确认成功后结束试用；失败时恢复经验证的旧 App。
- **关键失败**：没有合格备份时进入可操作维修；不盲目跳转、反复无限试用或使用残缺镜像。
- **依赖与完成判断**：依赖 F-01、F-03 和备份实体校验；确认成功、试用失败及代表性中断恢复的实际结果符合约定。

### F-05 蓝牙升级与维修

- **目的**：为健康 App 提供本地升级入口，并为 App 无法运行的设备提供 Boot 维修入口。
- **触发与输入**：蓝牙主机提交升级信息，并按 Boot 请求提供目标镜像。
- **预期结果**：健康 App 可提交升级；Boot 维修在已有合格备份时安装，完成主机、Boot 与 App 的跨复位接续。
- **关键失败**：没有合格备份时拒绝维修安装，不擦写当前 App；传输失败交安装与恢复流程处理。
- **依赖与完成判断**：依赖 F-03、F-04 和主机工具；健康 App 升级、合格备份维修和无备份拒绝均符合预期。

### F-06 产品版本与 URL 配置

- **目的**：让设备、查询接口和发布包使用一致产品版本，并支持约定的升级地址配置。
- **触发与输入**：构建版本信息、版本查询、设备本地 URL 读取和设置。
- **预期结果**：设备查询与目标发布清单版本同源；默认地址可用，配置地址可保存并在重启后读回。
- **关键失败**：无效配置不能作为合格地址使用；保存失败如实返回，不表示持久化成功。
- **依赖与完成判断**：依赖真实 FRAM 容量、既有存储系统和 F-07；版本一致，地址读写及重启保留在实际设备上通过。

### F-07 配套固件包与主机工具

- **目的**：为设备提供与实际构建对应的升级文件，并支持蓝牙来源读取。
- **触发与输入**：同一构建的版本信息、App 镜像及配套构建材料，或蓝牙升级操作。
- **预期结果**：工具生成并核验与镜像一致的版本、长度和 CRC 信息；蓝牙工具按 Boot 请求提供镜像。
- **关键失败**：拒绝超限、错误对象或版本与镜像不一致的包；镜像变化后重新生成对应材料。
- **依赖与完成判断**：依赖 App/Boot 工程和版本源；包核验正确，实际传输与安装链路能够使用该包。

## 4. 系统结构与主要流程

| 部分 | 总体职责与关系 |
|---|---|
| 升级服务器 | 保存与目标 App 匹配的版本清单和镜像，供设备主动获取 |
| App 配置及通信 | 提供本机版本和升级地址，查询版本并下载文件，不执行 App 区安装 |
| App 升级编排 | 管理升级请求、本地确认和业务放行条件，将完整请求交给 Boot |
| Boot | 读取来源镜像，完成备份、安装、试用、恢复和维修，不联网查询版本 |
| 外部 NOR | 保存旧 App 和备份信息，使用前由 Boot 验证 |
| FRAM 与既有配置系统 | 保存 App 业务及配置数据，容量和布局必须符合实物 |
| 配套主机工具 | 生成匹配发布材料，提供蓝牙镜像来源与核验入口 |

正常主路径：设备启动 → App 本地初始化与确认 → 网络就绪后检查版本 → 下载合格新镜像 → 提交请求并复位 → Boot 备份旧 App → 安装并验证新 App → 新 App 试用确认 → 正常业务。

关键失败路径：

- 无更高版本或一般查询、下载失败 → 不提交请求 → 继续原业务。
- 请求提交中断 → 按保留状态判断完整性 → 不把部分提交当作有效请求。
- 备份、安装或恢复中断 → 根据阶段和实体校验重新进入处理 → 不使用残缺镜像。
- 新 App 无法确认或镜像非法 → 恢复合格旧 App；恢复条件不足时进入维修。
- 蓝牙维修没有合格备份 → 拒绝安装 → 保留当前 App，不误擦写。

4G 与蓝牙共用升级请求和 Boot 安装语义，来源差异在适配层处理。具体模块文件、状态编码、提交字段、试用参数和传输调用由项目技术设计及对应里程碑细化；已有确认内容直接引用。

## 5. 关键约束与总体取舍

| 约束或选择 | 本项目采用内容与理由 |
|---|---|
| 目标硬件 | GD32L233RCT6，片内 Flash 256 KiB、SRAM 32 KiB；外部 GD25Q64 8 MiB，实物 FRAM 2 KiB |
| 镜像空间 | Boot 32 KiB、App 224 KiB；首次配对需使用与 App 槽匹配的链接镜像，不能只修改烧录地址 |
| 安装策略 | 单 App 槽加外部 NOR 备份；覆盖 App 前须具备合格备份，Boot 区及非 OTA 业务区不参与升级擦写 |
| 运行边界 | 设备自身启动后主动检查，不增加服务器唤醒休眠 MCU 的机制 |
| 恢复策略 | 保留升级阶段，验证镜像及备份，有限试用并确认；失败恢复或维修 |
| 完整性能力 | 当前采用 CRC 检测偶发损坏；现有项目没有定义数字签名认证，不将 CRC 当作发布者真实性证明 |
| 既有业务 | 保留原采集、阀门、查询、上报和补报；普通检查失败不得阻断原业务 |

FRAM 实物容量与旧驱动、分区声明不符，是已经确认的限制，处理见第 7 节。线程栈、局部缓冲、具体 AT 交互和全路径资源分析在相关设计中维护，不作为本示例的通用固定参数。

## 6. 总体验收目标

功能级完成判断沿用第 3 节；整体验收补充以下连接场景：

1. 无升级时，版本查询和原采集、阀门、上报、补报正常。
2. 4G 取得更高版本并安装后，新 App 正常运行；后续无新版本启动恢复通常业务。
3. 蓝牙升级完成主机 → Boot → App 的接续，维修准入正确。
4. 坏包、试用失败及有意义的中断代表场景按约定拒绝、恢复或维修，能够回到可操作状态。
5. 配置 URL 保存后重启读回正确，设备版本与同构建发布清单一致。

主机检查和构建用于验证对应解析、接口、镜像及工具结果。真实 Air780、蓝牙、NOR、FRAM、看门狗与 App 交接必须取得相应实物证据；采集、阀门及全业务场景需要连接相应外围设备。

具体在哪些里程碑上板、哪些功能组合验证及执行步骤，留给里程碑划分和对应设计安排。V1 覆盖必要成功、失败和恢复代表路径；完整逐写入点矩阵、最坏时序和长期压力按实际需要进入 V3。

**实际项目结果快照**：本项目于 2026-10-16 按负责人决定受限收口。软件任务完成；H1/H2 有效 PASS，H3/H4 功能代表 PASS，H5 四项 SWD 中断恢复代表 PASS。H6-1 未测，H6-2 URL 保存 FAIL，H6-3 未整体验收，SYS 未测。因此上述完整验收目标尚未全部满足，不表示正式产品发布。具体证据范围以项目原记录为准。

## 7. 未决事项与已知限制

| 事项 | 当前事实及影响 | 解决时点或后续条件 |
|---|---|---|
| URL 持久化与存储几何 | 实物 FRAM 2 KiB，旧软件按 8 KiB 声明；当前配置保存实测失败，影响 F-06，不能宣称配置持久化通过 | 负责人已决定本轮不修并受限收口；后续批准存储范围后，先确定容量、布局与数据处理方案，再修正和验证 |
| 外围设备与整体验收 | 当前未连接完成全业务验收所需外围设备，部分功能及 SYS 缺少完整验证 | 设备条件具备且负责人重新确定范围后补测；当前不自动恢复执行 |
| 正式发行版本 | 板测版本不等于正式发行决定，影响正式发布材料 | 正式产品发布前由负责人明确 |
| 深度资源、时序和故障研究 | 完整证明和矩阵尚未完成；代表性结果不能推广为全部场景通过 | 作为 V3 候选，实际立项时确定研究目标和覆盖范围；若发现当前功能失败则按当前问题处理 |

本示例展示了受限收口时的事实保留方式。已知失败、暂未验证与后续研究分别记录，产品实际状态仍以源项目入口为准。
