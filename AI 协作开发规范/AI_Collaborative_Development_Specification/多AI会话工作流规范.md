# 多 AI 会话工作流规范

所属规范：嵌入式 AI 协作开发规范。更新日期：2026-10-21。

AI 入口：[协议使用入口](AGENT.md)。前置：[总体方案设计](总体方案设计规范.md)、[里程碑划分](里程碑设计规范.md)。实例：[项目协作约定](example/ROLES.md)、[会话配置与登记](example/SESSIONS.md)。

## 术语与阅读说明

| 名称 | 本文含义 |
|---|---|
| Agent / 原生会话标识 | Agent 是实际 AI 工具；原生标识由该工具创建会话后返回，不能用角色名或显示名代替 |
| 候选 | 本轮拟审核、运行或部署的具体程序、固件及配套对象 |
| 开发自测 / 正式验证 / 审核辅助 | 分别由 D、E、C 维护相应材料和工具，职责见第 2 章 |
| Git 提交 / 远程推送 | 提交将本批文件变化保存为本地可定位记录；推送将已提交成果同步到已确认远端分支 |
| 执行任务 / `task_id` | 一次正式派发登记的工作，与总体功能编号不同；同阶段的实现、审核、修正和验证可分别使用独立执行任务编号 |
| 远端 / 分支 | 项目已确认的远程仓库目标及其成果线，实际值由项目唯一配置登记 |

## 1. 适用与使用原则

本分册用于在已确认总体方案和里程碑安排下，组织具体设计、生产实现、自测、用例实现及验证。实现与测试随能力推进，不按编码和测试两个阶段限制角色。

本分册规定执行权限和接续，工作深度沿总体方案与里程碑规范。启动/恢复按[读取规则](#session-recovery)选择当前角色和动作条款；异常步骤在触发、采取动作前补读，教学示例和设计理由按需阅读。所有条款持续生效，不以按需读取为由跳过适用约束。

<a id="runtime-core"></a>

### 1.1 共同执行底线

- 只执行实际授权范围；获批范围内纠错和必要复测连续推进。产品行为、范围、关键约束或验收的实质改变交用户决定，计划存在不等于已获实施、设备或发布权限。
- 只推进当前里程碑：新阶段全新 ABCDE，同阶段纠错续用本组；同时只有一个有效 A。各自遵守[角色权限](#2-角色与决定权限)，派发、回报及旧任务身份沿实际绑定和原任务快照，不把通知当作新任务。
- 同一可变文件、Git 写操作和设备资源按序交接；构建、审核和验证读取的相关对象保持稳定。无法确认当前授权、身份、对象或停点时，先核实受影响部分，不凭摘要重复执行。
- 实现、自测、审核和实际验证分别报告；准备、回执或成功关键词不证明功能通过。C 独立审核，[正式验证须具备放行条件](#review-gate)；FAIL、未测及证据限制如实保留，受限收口由用户决定。
- 每批文件交付完成必要检查、[显式本地提交](#local-commit)，按[最小交接内容](#handoff-content)报告实际对象、结果、材料和余项。复用已有成果及记录，不为留痕制造任务；原始失败不被后续成功覆盖。

需要改变阶段、替换会话、处理异常或操作工具时，先补读[对应步骤](#trigger-reading)。

## 2. 角色与决定权限

A/B/C/D/E 是职责槽，不绑定具体 Agent、模型或进程。读本角色行及本次动作直接涉及的权限；会话组建立与接管统一按[第 5.1 节](#51-每个里程碑新建会话组)。

| 角色 | 职责 | 决定边界 |
|---|---|---|
| <a id="role-a"></a> **A：流程协调** | 登记获批范围与任务，默认统一派发、接收回报并按固定接续安排下一执行任务，维护状态、阶段转换及异常 | 按既定技术结论推进，不增加技术审核，不改写方案、审核结果或用户目标 |
| <a id="role-b"></a> **B：方案设计** | 与用户确定当前实现及必要用例方案，分析方案冲突和原因不明的问题 | 实质修改交用户确认，不自行降低指标、扩大范围或接受产品限制 |
| <a id="role-c"></a> **C：独立审核** | 审核实现、自测、正式用例及实际证据，给出问题分类、影响和结论，维护审核辅助工具 | 按已确认依据判断，不自行决定新方案，默认不改生产代码或正式用例行为 |
| <a id="role-d"></a> **D：生产实现** | 实现获批生产代码，维护开发自测及其脚本，完成实现纠错，交付候选和材料 | 不自行验收，不擅自增加产品行为、测试钩子或进入下一阶段 |
| <a id="role-e"></a> **E：验证实现与执行** | 维护正式验证用例与脚本，执行规定验证和针对复测，保存原始证据 | 默认不改生产代码，不通过改变断言使结果迎合当前实现 |

- **V1 初版**：D 实现与 E 用例准备可并行，围绕功能链路、必要保护及代表场景推进。
- **V2 优化**：围绕实际问题或改善目标实施并回归，复用有效用例和证据。
- **V3 深度研究**：通常由本组 B 明确方案、E 实现并执行试验、C 审核证据；本组 D 已建立，暂时待命，需要生产或诊断固件修改时再派任务。

具体角色选型按[配置要求](#role-config)确定，不因换 Agent 改变职责或验证要求。

## 3. 一个里程碑的执行流程

基本关系：B 与用户确认方案 → D/E 按需实现与准备 → C 审核 → E 按计划验证 → C 核对证据 → A 核对阶段完成条件。问题按第 4 章返回，不重开整条流程。

上述箭头表达技术成果的接收与判断责任。默认由 A 使用工具逐项派发，B/C/D/E 各自回报 A，再由 A 按已确定的接续安排下一角色；C 仍独立决定审核结论和修正要求，A 不增加审批。项目明确采用直接接续时，按[唯一触发与任务登记规则](#handoff-record)办理。

<a id="stage-design"></a>

### 3.1 方案与用例确认

首个里程碑由按用户授权建立的新 A 从获批总体方案、计划和当前状态启动；后续新 A 接收已结束里程碑的交接。A 建立并登记本阶段新 B/C/D/E，核对范围、依赖、已有成果及条件，安排本组 B 细化方案，明确模块与接口、正常和关键失败路径、实施范围、交付和完成条件。

需要 E 验证时，同步确定用例目标、条件、输入或施加方式、预期结果、失败判定、证据及停止条件。研究任务还须明确研究问题、适用范围、方法、指标判定，以及完成和继续条件。负向用例按预期拒绝、恢复等行为判断。

相关高风险选择在依赖它的工作开始前完成必要审查。用户确认后，B 保存方案，A 登记任务及接续；未变化的设计、用例和授权直接引用，不因换会话重复审批。

采用后台 B、用户主要在 A 会话交流时，B 将待确认方案、取舍和问题回报 A，并明确尚待用户决定；A 在用户会话展示原方案及问题，保留实际确认来源，再向本组同一 B 会话派发定稿或继续讨论任务。A 不代替用户批准，也不新增审批层；依赖该决定的实施在确认前不启动。

<a id="implementation-preparation"></a>

### 3.2 实现与验证准备

#### 同一里程碑内的分工

接口和预期清楚后，D/E 可并行：D 完成生产实现、必要构建和开发自测；E 实现用例、脚本、断言及证据采集，并做必要调试。独立部分先完成可先交 C 审核，不等待无关交付。

回报须区分“实现交付”“用例准备”“实际验证结果”。准备完成、调试成功或离线模拟不能记为正式实测通过。E 是否启用按验证安排决定，可包括上板、系统回放或研究试验。

E 需要新增固件诊断接口或测试钩子时，由 B 确定必要设计和范围，D 实现。获批的开发定位及小范围检查可在实现中进行，保留实际对象和覆盖；正式阶段验收使用的候选与用例须具备相应有效审核。

<a id="integration-delivery"></a>

#### 工程接入与集成交付

涉及既有工程时，D 交付应说明新增模块、已有业务、配置或公共组件的实际变化，明确接入点、依赖及必须保持的行为。接收方需要重新评估的调用链、硬件条件或资源参数应说明适用范围，不能把本项目数字直接作为其他工程的合格配置。接入说明可放在现有方案或融合说明中，随代码同一交付维护；C 在现有审核中核对说明与实际代码。组合交付时同时检查实际模块连接及受影响业务，不以各部分分别通过代替集成检查。

<a id="workspace-integration"></a>

#### 工作目录与成果汇合

项目在 ROLES 说明共用工程目录或独立工作树等实际工作方式、成果汇合执行者及最终交付分支的配置入口；具体工作目录在 SESSIONS 登记，仓库、远端及分支沿项目入口取得，不重复维护配置值。生产工程通常由 D 汇合，E 提供用例和验证工具成果，A 安排顺序；已有项目分工可直接登记采用。

共用目录中，构建、审核或验证所读取的相关源码、配置、脚本及审核依据在该动作期间不得被另一任务改动；也可读取明确提交或已交付的稳定对象。需要改变相关输入时，先结束或停止受影响动作，再交付新对象，不限制无关材料的独立工作。

采用多个工作目录时，各角色的提交不自动构成集成候选。约定的执行者按授权将所需成果汇合到已确认的交付分支，交付实际集成对象；未汇合时如实标明。C 核对集成差异及既有审核的适用性，E 补受影响验证，仍按原有审核和验证环节办理，不机械重做未变化内容。

<a id="validation-method"></a>

#### 验证方法与判定可靠性

开发自测、回放和验证脚本优先使用实际生产代码或接口；使用替代环境时，核对关键行为与实际接口相符，并说明覆盖限制。首次采用新验证方法、修改关键判定或曾出现假通过时，用少量针对性反例确认关键判断能识别失败，不自动展开完整故障矩阵。

验证须确认目标条件确实发生、观测来自本轮、关键结果符合已确认预期；进程正常退出、出现成功关键词或命令回显不能单独证明功能通过。这些检查纳入 C 现有用例与证据审核，不增加固定审核轮次。

<a id="review-gate"></a>

### 3.3 审核与验证开始条件

#### 审核结论与验证启动

C 对照获批方案、实际对象和证据审核，不以摘要、回执或任务数量代替检查。已有候选及用例由 C 核对既有审核仍适用后复用，不重审未变化内容。独立审核不能由实现者换提示自审冒充。

C 写清对象、范围、发现、结论及下一动作，区分实现审核、用例审核、可执行验证和验证证据结论。一次汇总本次范围内已确认的问题，区分阻断和建议；阻断须说明依据及对当前目标的影响，一般优化建议不自动成为 V1 新任务。

只有本次执行范围所需实现与用例均已有效审核、前提具备且无相关阻断时，C 才确认“可执行验证”，注明候选或实现版本、用例版本及范围。该确认复用已有结论，不另加一轮完整审核；可以只确认已具备条件的子范围。

部分审核通过不自动启动验证，也不代表阶段完成。E 执行前核对实际对象和条件一致；D 不替换 E 正在验证的候选。后续对象或配置变化时，仅重审、复测受影响部分，不能把旧对象通过自动用于新对象。

<a id="candidate-identity"></a>

#### 构建、候选与部署对象对应

需要构建、实际运行、部署或配套交付时，交付材料须足以关联当前源码及配置、构建产物和必要配套对象，E 核对实际执行或部署对象与本轮审核范围一致。按需要使用提交标识、构建记录、产物校验值等方式定位，并核对版本信息与实际产物的关联；源码已修改、构建成功、包校验通过、设备已部署分别确认。V1 做必要关联核对，不自动要求完整构建输入冻结或逐对象可重复构建证明。

<a id="result-transition"></a>

### 3.4 结果审核与阶段接续

E 回报实际验证、复测结果和原始材料，无论结果是否通过；默认由 A 为 C 派发相应证据审核任务。C 审核后回报 A，A 核对约定交付、审核、必要验证与复测、延后验证承接及下一阶段依赖。

无需当期验证的阶段可按软件范围结束；包含当期实物或研究结果的阶段须取得相应结果。单项审核、用例准备或收到一份报告不足以关闭整个里程碑。受限收口、改变验收要求或接受产品功能失败由用户决定。

切换前，A 须确认本阶段已派工作已交付并完成规定审核，或已按授权明确停止、取消；仍在运行或待处理的当期交付不能靠换组绕过。停止或取消不等于功能完成，阶段能否结束仍按完成条件及用户决定判断，计划延后验证须有明确承接。

<a id="milestone-authorization"></a>

项目 `AGENT.md` 登记实际用户授权依据及允许接续的范围，ROLES 引用该依据。计划确认不自动等于全部代码实施或设备操作授权。仅获准当前里程碑时，结束后保留交接并等待用户决定下一阶段；已明确获准按计划连续推进时，不逐阶段重复请求启动授权。等待时由 STATE 说明缺少哪项决定，不能只写笼统的“等用户确认”。

在已授权接续范围内，本组 A 于阶段结束后安排建立下一里程碑的新 A；由新 A 组织下一组新 B/C/D/E，并安排新 B 讨论具体方案，不能直接续用本组会话执行下一里程碑。需用户确认的新方案仍等待确认，未获授权的后续范围或版本不自动启动。

## 4. 问题返回、修正与研究判定

<a id="problem-routing"></a>

### 4.1 问题返回路径

| 情况 | 处理路径与边界 |
|---|---|
| 已确认功能遗漏或实现错误 | C 明确方案依据及实现差异，交 D 修正、自测，再交 C 针对审核 |
| 开发自测或其脚本有误 | 交 D 修正，C 核对受影响实现及自测依据 |
| 正式验证用例或脚本未实现获批预期 | 交 E 修正，再做必要审核和针对验证；改变目标或验收条件时回 B、用户 |
| 审核辅助工具或分析有误 | C 维护工具并重新核对受影响审核结论，不擅自改变正式用例或验收依据 |
| 证据不足或执行有误 | C 指出缺项，由 D/E 补对应实现自测或验证材料，再交 C |
| 获批范围、方案、契约或验收需实质改变 | C 报告影响，A 交 B 分析修订，用户确认后由 D/E 修改受影响部分 |
| 原因尚不明确 | A 交 B 结合源码和现场证据分析，必要时安排有明确目的的补充观测；结论按下文返回，不让 D 猜测修改 |
| 环境、工具或必要输入阻断 | 按已有恢复办法处理；新增资源、改变范围或无法恢复的条件交用户决定 |
| 实测出现计划外状态或操作失控 | 先按[异常现场保护规则](#test-anomaly)停止相关操作并保存现场，再分类处理 |

<a id="analysis-return"></a>

B 完成原因分析后，默认回报 A，由 A 安排 C 结合分析结论继续处理。原方案成立且仅有实现偏差时，C 明确 D 的修正要求；正式用例实现问题由 E 修正，证据缺项由对应作者补充。需要实质方案修改时，B 先交用户确认，再由 A 安排 D/E 实施并交 C 针对审核。直接接续项目沿已登记的唯一触发者办理，不新增完整审核轮次。

不改变已确认范围、产品行为、接口契约、关键约束或验收条件的设计澄清与实施细节补充，由 B 在获批范围内完善依据并同步相关角色，不重新审批原方案。存在多种有实质差异的解释，或需要改变原已确认选择时，仍交用户决定，不能以“澄清”名义自行改变方案。

<a id="current-defect"></a>

后续里程碑发现之前成果的真实缺陷，由当前会话组按本章处理：明确实现问题交当前 D 修正，方案问题由 A 交当前 B 分析，实质方案调整仍由用户确认。原因不明时先分析，不猜测改代码；只限制受影响工作，不恢复旧组派发。原阶段记录保留原对象与覆盖范围，当前状态和依赖同步本次结论及修正依据。

<a id="prior-verdict"></a>

旧成果或原审核存在已确认缺陷时，当前 C 在受影响的旧 REVIEW 或已登记的等价审核入口补一条适用性说明：原对象及结论、受影响部分是否停止复用或待复核，以及当前修复任务和已有新证据入口。保留历史时点的实际结果与原始材料，未受影响部分继续有效；不得让旧的无条件“通过”继续作为受影响工作的依据。该说明随本次交付完成，不恢复旧会话组，也不重写旧阶段全过程。

<a id="correction-retest"></a>

### 4.2 修正与复测边界

<a id="retest-scope"></a>

#### 生产代码和正式用例的复测范围

实测后修改生产代码，须完成：**D 修正及自测 → C 针对审核 → E 复测受影响用例 → C 审核复测证据**。代码审核不能代替原失败场景复测。仅修改正式用例或执行脚本时，影响操作步骤、输入、观测、判定或适用条件的变化须重新执行受影响验证。

<a id="script-ownership"></a>

#### 脚本维护与机械性小修

脚本按用途分工：D 维护开发自测脚本，E 维护正式验证用例及执行、采集脚本，C 维护独立审核、证据比对及分析辅助工具；其他辅助脚本按任务确定维护者。各会话的脚本目录、索引和跨会话复用按[文档组织规则](文档组织与维护.md#internal-tools)维护。

C 可直接处理不影响执行及判定的拼写、格式、资料引用等机械性小修，记录并同步 A 及相关维护者，由维护者核对受影响材料，不强制重新上板。影响正式验证脚本行为、刺激、观测或判定逻辑的修改由 E 实施、C 审核；D 修正开发自测脚本后交 C 核对。C 的审核辅助工具用于独立复核，不能替代规定由 E 完成的实际验证，也不能通过修改正式用例或验收依据使结果通过。目标或标准的实质修改回 B、用户。

#### 授权内纠错与反复失败

获批范围内的明确纠错不重复请求相同授权。修正后只复核问题及受影响部分，新影响出现时再说明理由扩围。相同原因反复出现且没有新的有效处理方案时，停止重复派发，交 B 分析，不自动扩大研究或无限重试。

<a id="test-anomaly"></a>

#### 实测异常与现场保护

实测步骤应有明确退出和必要时间边界。出现计划外重复复位、可能破坏待验证状态的操作、观测失效或无法正常退出时，执行者停止继续施加相关输入、擦写或重复复位，保存当轮状态和失败证据，报告 C 并同步 A。已有授权内的观察、保护和恢复按规定处理；未在方案中的刷回旧固件、清除状态或额外试验，不能为了继续测试或得到通过结论而自行执行。需要新方案或扩大范围时按 4.1 返回，保留原始失败材料，不覆盖成后续结果。

预期失败用例仍按既定方案及停止、恢复条件执行，不因正常的负向结果自动增加审批；未受影响且已授权的工作可以继续。

<a id="research-boundary"></a>

### 4.3 研究完成与工程目标的区别

研究报告分别说明证据有效性、工程指标达成情况和研究任务是否完成，复用已有报告字段。C 审核方法执行、覆盖和证据，B 分析方法或方案取舍，A 按结论接续，用户决定实质修改。

| 研究结果 | 完成判断与接续 |
|---|---|
| 必要条件缺失、执行或证据不足，约定计划未完成 | 保留未完成或阻断，按 4.1 处理；方法本身不足以回答问题时，A 交 B 修订并由用户确认 |
| 完整回答了事先约定的研究问题，包括否定结论 | C 核对研究完成条件，A 可结束该研究；工程指标仍按实际结果记录 |
| 工程改进目标未达，或后续工作依赖指标达成 | 保留目标未完成，A 交 B 分析原因和取舍，由用户决定；依赖该指标的工作继续受限 |

例如，“测试并判断指标能否满足”的获批研究完整执行后，可同时得到“证据审核通过、研究任务完成、工程指标未达到”。无新方案决定时记录结束，不仅因否定结论增加 B 的任务；需要改设计、增资源或调目标时才进入相应方案讨论。

原任务若为“优化到指定指标”，未达到就未满足目标，不能事后改成仅需测量结论。研究达到事先结束条件即停止，不为得到 PASS 擅自改参数或扩展范围；研究结束不等于产品验收通过。

## 5. 会话连续性与交接规则

### 5.1 每个里程碑新建会话组

里程碑严格串行，同时只执行当前里程碑。新里程碑必须新开 A/B/C/D/E 五个会话，包括 A；不能仅重命名、续接旧会话或复制旧会话完整上下文来代替。项目计划和当前状态通过唯一文件入口连续维护，会话按里程碑隔离。

里程碑切换时：

1. 旧组 A 核对本阶段结束条件及 [Git 远程同步](#git-delivery)，停止本组继续派发；D/E 停止已结束阶段的板卡、源码及其他资源操作。
2. 旧 A 在已有状态或记录中留下获批范围、当前对象、有效结论、遗留项、后续承接验证和授权入口；处于已授权接续范围时安排下一里程碑新 A，否则说明等待的具体决定。
3. 新 A 从计划、状态及必要记录接管，沿 `SESSIONS.md` 的唯一来源建立并登记本阶段新 B/C/D/E 的实际绑定；当前组编号在 `STATE.md` 标明，核对资源已移交后按范围派发，无任务的角色待命。
4. 旧组保留原任务身份、会话和回报归属，不覆盖为新组 ID。重复回执和晚到通知仍关联原任务，不直接覆盖新阶段状态或自动重派；其中如有影响当前成果的新事实，由当前组按[问题返回规则](#current-defect)处理。

同一项目执行范围同时只有一个当前有效 A。新组接管后旧组不再指挥当前阶段；跨里程碑只交接文件、候选、结论和必要记录，不灌入全部聊天，也不因换组重做未变化且有效的检查。

**同一里程碑内的实现、修正、复核和复测继续使用本组 A/B/C/D/E。** 仅因上下文失效、用量或工具故障等需要更换个别会话时，在明确停点记录替换和未完成任务归属，办理本阶段绑定交接，不因此新开里程碑或每轮重建整组。

<a id="session-replacement"></a>

#### 同阶段个别会话替换的任务接续

`switch` 只办理实际绑定替换，不停止旧执行、不迁移上下文，也不改变旧任务冻结的执行者和回报接收者。A 或获授权维护者在已有 STATE/交接材料中明确以下安排，不另建接管表：

- **替换 A 或其他回报接收者**：明确唯一的新协调者或结果收集者，以及原执行者通知该收集者的现有消息或成果入口。旧执行者仍按原任务回报，收集者从原回报正文、原件和分接收者回执收集结果；旧接收者可用时仅转交，不能继续派发。原接收者不可用时，由新 A 或获授权维护者负责收集，不等待其恢复。若原回报不可访问，请原作者将必要正文补入可共享的已有交付材料并通知收集者；作者也不可用且材料不足时保留未完成，不伪造旧回报。收集不重定向冻结的接收者，也不要求为绕过旧通道重做已经完成的实现或验证。
- **替换任务执行者**：先确认旧执行者已停止相关工作并移交资源，再由当前唯一派发者向新执行者发送新任务，引用旧任务、已有成果及仅剩的工作，回报接收者按当前有效路径确定。新执行者用自己的新任务回报，不冒用旧身份或旧 `task_id`。无法确认旧执行已停止时，不启动可能重叠的写入、设备操作或其他依赖其停点的工作。
- **结清旧任务**：在现有状态或必要交接中标明哪些结果已收集、哪些工作已停止并交给哪个新任务，以及仍未完成或待核实的部分。原任务快照和作者归属保留；“已转交”不等于原工作已完成，不能由替代者补报成原执行者完成。晚到结果仍关联原任务，由当前收集者核对适用性，不恢复旧 A 的派发权。

新会话先按[恢复要求](#session-recovery)读取当前原文和上述接续依据；任务记录仍沿工具原快照定位，当前进度沿 STATE 维护。

<a id="handoff-record"></a>

### 5.2 固定接续、报告与重复处理

A 在用户授权内登记第 3、4 章的固定接续和任务归属。默认采用 A 统一派发：B/C/D/E 的工具任务以 A 为正式回报接收者，执行者回报后，A 按已有技术结论派发下一任务。A 是该模式的接续触发者，不把这份回报再写成仅供更新状态的抄送；A 不重新审核 C 的技术判断，也不重复请求仍有效的授权。

项目如明确采用 D→C、C→D/E 等直接接续，在 ROLES 登记实际触发者和回报路径；为接收角色显式派发独立任务，并按原任务约定回报，纯同步 A 的消息不再次派发。同一项接续只启用一种有效方式，不能同时由角色直接发送和 A 再发一次。A 仍处理阶段转换、方案冲突、原因不明、执行阻断和用户决定。

`send` 登记接收会话的执行任务，`report` 回报原执行者的任务；收到通知不建立独立执行任务。实现、审核、修正和复测分别使用自己的 `task_id`，如 `d-impl01`、`c-review01`、`d-fix01`，执行者与接收者沿原派发快照取得。同阶段新修正任务使用新编号和本组会话；原请求结果尚不确定时，不换编号重新派发，不另建编号表。

<a id="handoff-content"></a>

#### 交付的最小内容

正式交接沿用已有里程碑、任务和必要轮次标识，包含或能直接定位以下信息：

| 内容 | 必须能取得的信息 |
|---|---|
| 任务与去向 | 里程碑/任务、交付类型、发送与接收角色 |
| 实际对象 | 相关提交、候选或用例版本及必要目录、获批依据 |
| 完成及检查 | 做了什么、必要检查和结果；已在成果中说明的只给简要结论 |
| 材料入口 | 设计、审核、报告和证据的有效位置 |
| 剩余与接续 | 未完成、限制、下一角色的具体动作 |

正式派发的消息正文必须写明本次 `milestone/task_id`，如“执行任务：M01/d-impl01”，或提供接收者可直接取得且能唯一确定这两项的任务快照入口。`send` 保存任务元数据并不代表这些信息已自动附入消息，不能要求执行者猜测“最近任务”。

详细内容只保存一次，交接引用已有成果和提交；上述任务定位明确后，工具已固化的身份、目录等信息直接复用，发送者只补本批结果、限制和接续，不重抄整份快照；结果报告与接续指令分别表达，不另建重复交接表或 ID 清单。普通交付可用数行说明，不设固定字数或逐角色记录文件要求。正式验证所需原件按[证据规则](文档组织与维护.md#evidence-policy)保留。

交接须可定位、持久且能由接收角色、新会话和后续阶段访问。原生记录符合条件时直接引用，否则把必要正文补入已有交付或一份必要事件记录。快照或正文校验值不能代替正文，删除临时输入前保留必要内容的可靠来源。重要决定按[决策规则](文档组织与维护.md#4-当前方案与决策变更记录)更新方案；关键通信的归档位置及范围统一按[证据规则](文档组织与维护.md#evidence-policy)，不转录全部聊天。

通信和收件回执只证明相应派工或交接，不能代替实际执行、正式交付或 C 的独立结论。过去的放行须关联当时的候选、用例、范围及固定消息/提交，不能用后来更新的当前摘要代替。


同一派发或交付通知只处理一次；计划内重复采样和必要复测按对应任务、轮次执行，不因对象相同被误判为重复。串行交接不遗留仍在执行的旧任务；重复或晚到通知保留原归属，不直接覆盖当前判定或重派。发现新的真实缺陷时由当前组分类处理；不确定回执先核对已有任务，不盲目重建或重派。

未采用统一工具或某项能力不受支持时，在项目约定中明确实际可用方式；A 按单一路径安排，不并行保留手动和工具两条派发路线，也不把未接入的 Agent 自动换成其他 Agent。

### 5.3 共享资源

同一可变文件同时一个写入者，公共工程、索引及 Git 写操作串行。同一板卡、串口、SWD 等资源同时一个执行者；D 开发定位和 E 验证之间明确移交，不因文件不同就并行操作同一设备。

同一文件只有一个写入者仍不足以保证读取对象稳定；构建、审核、验证及多目录成果汇合按[工作目录规则](#workspace-integration)执行。

### 5.4 新会话、会话替换与上下文压缩后的读取

本节是完整的启动/恢复读取规则，其他入口仅引用。新建、替换、压缩或中断恢复后，在派工、修改或操作前取得下列**相关当前原文**；不强制加载整个协议或所有项目文件。摘要、旧记忆和“文件没变化”不证明原文仍完整在上下文中；工具已完整加载的当前有效原文可直接使用。

#### 共同必读

1. 项目 `AGENT.md`、协议 `AGENT.md`、项目 `ROLES.md`、`STATE.md`，以及本分册[共同底线](#runtime-core)和[本角色权限行](#2-角色与决定权限)。入口提供路径，不递归加载链接中的全部正文。

| 当前角色/动作 | 执行前的规则 | 项目材料 |

正常连续任务可复用当前上下文完整保留且未变化的原文；恢复不自动重开里程碑、重建会话组或重新审批有效方案。工具是否自动加载、识别压缩或触发读取，以实际能力为准。

<a id="git-delivery"></a>

### 5.5 文件操作后的 Git 提交与里程碑远程推送

<a id="local-commit"></a>

#### 本地提交

A/B/C/D/E 每次完成一批有明确目的的文件操作后，必须在本轮回报、交接或结束前，将本批改动提交到所属 Git 仓库。方案、生产代码、用例、工具、审核、报告、状态和索引均适用。以一批可交接工作为提交单位，不按每次保存或每个文件拆分；只读或没有改动时不制造空提交。

提交前完成与本批改动相称的必要检查，并更新本角色实际变化的材料；按[记录触发规则](文档组织与维护.md#record-policy)复用当前成果、提交和共享交接，不为每次提交另建过程记录。显式暂存本次文件或差异，不夹带其他任务、用户或其他会话的改动；存在归属不清的变更先核对。Git 暂存、提交、合并和推送操作串行，A 安排共享工作区的写入顺序，不要求 A 代替所有角色提交。

交付消息注明实际提交标识、改动、检查、限制和接收者；提交不是审核通过或实测通过。提交标识可在提交后随消息报告，无需为了把本提交标识写回同一提交而循环修改文件。不同角色分属仓库时，各自提交所属成果，并在交接中保持对象关联。

<a id="milestone-push"></a>

#### 阶段远程同步

**每个里程碑结束时，由 A 核对本阶段所需交付均已提交、需要汇合的成果已形成实际集成对象，完整交接材料就绪，并将所属仓库的阶段成果正常推送至项目已确认远端和分支。** 项目 `AGENT.md` 指向已确认仓库、分支和远端的唯一配置来源，`ROLES.md` 约定推送执行者及交接；已有上游时沿用，不自行更改 remote、强推或重写历史。多个成果仓库分别核对，候选可追溯到实际生产提交，不因随后仅有文档提交就机械重建镜像。

工具持续写入日志不按每条消息触发提交；本批交付需要的证据在批次结束封存或保存稳定引用，避免日志、回报和提交互相重复触发。

取得推送成功回执后再报告“已远程同步”，附实际远端、分支和提交。回执随交接消息或已有工具报告保存，不为记录刚完成的推送不断新增提交。技术完成和远程同步分别判断；推送失败、缺少上游或发生冲突时如实报告，保留本地提交，处理可安全解决的问题，涉及目标选择或历史取舍时交用户决定，未完成同步不得宣称阶段交接全部完成。

按计划进入下一里程碑前，应完成本阶段正常结束或用户明确的受限收口、Git 同步和资源交接。只因推送完成不能进入未授权范围，也不能将技术失败改写为通过。

## 6. 配置、项目文件与实例要求

<a id="role-config"></a>

### 6.1 Agent 与模型配置

项目须能取得 ABCDE 目标配置中的下列信息。采用统一工具时，以 `AI/project.sessions.json` 或已登记的兼容配置为唯一来源，`SESSIONS.md` 引用并按需同步展示；未采用结构化配置时，可由 SESSIONS 使用每角色一行的表格维护。

| 必需信息 | 填写要求 |
|---|---|
| 角色 | A/B/C/D/E 职责槽，目标选型与每个里程碑的实际会话登记分开表达 |
| Agent | 实际采用或明确的目标工具，不仅填模型名 |
| 模型 | 原生标识、别名或明确继承来源；目标与核对结果分清 |
| 思考强度 | 原生设置、继承方式或不适用；未核实映射注明待核验 |
| 必要说明 | 主用与备选、限制、确认或核验状态及配置依据；可在自动展示区外用段落说明 |

上述要求约束信息是否可取得，不强制自动展示使用固定列数。工具可把模型和思考设置合并显示为原生设置，说明段落解释继承方式及必要限制；不为满足五列表再手工维护第二套值。`sync` 只维护 SESSIONS 的指定标记区，区外保留人工说明，展示为最后登记观测，不是实时进度。改文档或目标默认值不等于运行会话已切换，实际切换沿项目授权办理。

通用规范不指定所有项目的模型；实例可给具体选型，但须说明来源和核验状态。不同 Agent 的参数、上下文和会话语义不得互相套用。

### 6.2 成果文件与存放位置

| 成果 | 规定位置与建立要求 |
|---|---|
| 项目多会话协作约定 | `AI/ROLES.md`，进入首个里程碑前形成，A 协调维护项目采用规则、分工和接续，完整内容见 6.3 节 |
| 配置阅读与同步展示入口 | `AI/SESSIONS.md`，首次确定工具配置或进入首个里程碑前建立；引用唯一来源并维护必要说明，内容见 6.4 节 |
| 工具配置及运行绑定 | 默认 `AI/project.sessions.json`；首次采用统一工具并操作会话前建立，已有兼容配置登记实际路径；格式沿[工具说明](session_handover_tool/README.md#配置及文档归属)，不复制第二份有效配置 |

项目 `AGENT.md` 保存稳定项目约束、采用范围、授权及工程入口和材料导航，分别指向 `ROLES.md`、`SESSIONS.md`、`STATE.md`；完整项目导航表在入口维护，其他正文只引用所需材料。

`ROLES.md` 规定怎样协作，`SESSIONS.md` 说明目标配置及实际绑定，`STATE.md` 反映当前进度、责任角色和下一步。当前状态只保留当前组编号和登记入口，不复制全部模型、原生 ID 或历次会话表。当前阶段和候选不反复写入项目入口或协作约定。

成果位置与维护分工见[文档组织规则](文档组织与维护.md#project-layout)、[维护责任](文档组织与维护.md#7-维护责任与会话恢复)及[里程碑成果要求](里程碑设计规范.md#11-成果文件与存放位置)，本节不重复登记角色材料表。

<a id="project-instance"></a>

### 6.3 ROLES.md 的内容与实例

`AI/ROLES.md` 承载本项目采用的多会话协作规则，由 A 协调维护；实质角色、流程或权限调整沿用户确认权限办理。已有等价文件时在项目 `AGENT.md` 登记映射，保持一处有效正文。

ROLES 重点登记项目实际选择，通用权限和步骤引用唯一正文，不要求重写一套工作流。至少能取得：

| 项目选择 | 登记内容 |
|---|---|
| 采用范围和差异 | 采用的角色权限及实际差异，用户确认来源与授权入口；无差异直接声明采用默认规则 |
| 派发与用户确认 | 统一派发或已确认的直接接续、唯一触发者、回报接收者，以及后台 B 向用户提交待确认方案的实际路径 |
| 工程和共享资源 | 共用目录或独立工作树、成果汇合责任及交付配置入口、文件和设备的交接方式 |
| 文件和 Git | 实际工具索引、交付协作、阶段推送执行者；仓库/远端/分支沿项目入口，不抄配置值 |
| 启动和特殊情形 | 引用[唯一恢复规则](#session-recovery)和项目材料入口，注明必要替换或异常安排，不复制角色读取矩阵、问题分类和研究规则 |

完整材料导航只在项目 AGENT；配置和绑定沿 SESSIONS 的唯一来源，当前进度沿 STATE。ROLES 可保留少量关键关口提醒；完整理由、教学分支和长案例放在按需说明中，不列为共同必读。

[示例 ROLES.md](example/ROLES.md)与[项目入口](example/AGENT.md)、[会话配置登记](example/SESSIONS.md)、[状态](example/STATE.md)及[当前设计入口](example/PLAN.md)组成同一套材料。规则正文与整套实例同步维护文件职责和恢复路径；项目采用时填写实际入口及确认依据。

<a id="session-register"></a>

### 6.4 SESSIONS.md 的内容与维护

`AI/SESSIONS.md` 通过来源引用、同步展示及必要说明取得以下信息；采用结构化配置时，不在人工正文重复维护实际字段：

1. **唯一配置来源与核验状态**：实际配置入口、维护者和适用范围；目标选型、已登记观测及实时运行结果分别表达。
2. **角色目标配置**：能取得 6.1 节要求的信息；采用统一工具时由结构化来源及同步区承载，人工解释放在标记区外。
3. **按里程碑分组的实际登记**：至少包含角色、里程碑或任务归属、Agent 与连接方式、工作目录、原生会话 ID、已核对模型及参数、会话运行状态。
4. **替换与交接依据**：保留旧绑定、原任务及回报归属，链接[替换接续](#session-replacement)所需的唯一结果收集者、停点及剩余工作新任务；只有无法由现有材料说明的重要事件才另存记录。

每个新里程碑登记全新 ABCDE。实际成功创建后才能填写原生 ID，未创建或未核验须注明；就绪、待命、运行和停止分别表达，创建完成不等于任务已经执行。使用本阶段明确 ID 和入口，不猜显示名、最近聊天或跨组、跨 Agent 的 ID。

A 或获授权配置维护者串行更新配置与登记。实际模型/执行器切换沿项目授权办理，先核对旧会话停点、任务归属，再登记新的真实绑定；改文档不等于已切换工具。旧任务仍关联派发时的身份和回报归属，不覆盖成新组或新执行器；默认目标表的变化也不回填改写旧组已核验的实际参数。

配置、绑定和有意义的会话生命周期变化时更新登记，任务进度在 STATE 维护，不逐消息刷新登记表。`STATE.md` 的当前快照可以覆盖更新；`SESSIONS.md` 中已结束阶段的身份与归属要保留，不能随当前组切换删除或改写。恢复读取只取当前组和直接相关配置，必要时再追溯旧组，不要求每次通读历次登记。

示例见 [SESSIONS.md](example/SESSIONS.md)。示例只放占位符，不累计真实项目绑定、凭据或本机连接信息；已有工具原生配置可直接引用，不要求为了文档另造接口或强套字段。

## 7. 会话交接工具接入与边界

### 7.1 统一入口与现有支持

默认复用 [session_handover_tool/](session_handover_tool/README.md) 的 Python API 或 CLI。工具说明维护命令、配置字段、各 Agent 原生语义和恢复办法；已有验证范围直接引用 [VALIDATION.md](session_handover_tool/VALIDATION.md)，不在协议复制测试清单，也不把重复工具测试作为项目推进的固定前提。具体项目任务的实现、审核和实物验证继续按本协议执行。

项目 `AGENT.md` 登记共享工具和唯一配置入口，配置中的授权依据记录实际用户指示，不由填写配置自行产生授权。操作会话的角色读取所用接口和适配器说明；不支持项按说明保留，不猜参数、不换 Agent 代替原调用。 工具命令示例只演示接口，实际接收者、任务范围及接续以项目 ROLES 和当前获批任务为准。

### 7.2 会话建立、执行任务与回报

新里程碑仍须建立五个新会话。可创建的适配器按原生方式创建并登记；Codex App 由宿主新建后显式绑定，不绑定旧阶段会话冒充新组。Codex CLI 的创建初始消息仅安排读取入口与确认待命，正式实施另行派发；Antigravity/Harness 的空闲创建与后续发送按工具说明分开办理。

用户对 A 的启动指示、方案确认以及 A 向用户的阶段报告沿用户会话办理，不把用户虚构成工具原生接收者。B/C/D/E 的实际工作使用 `send` 登记，完成后用 `report` 回报自己的任务；报告注明实际执行者，接收者由原派发快照确定。默认回报 A 后，由 A 按第 5.2 节派发下一执行任务；模块本身不调度流程或自动续派。

执行任务编号、消息正文中的任务定位和回报归属统一按[交接规则](#handoff-record)办理；`switch` 不代替[旧任务收集和剩余工作接续](#session-replacement)。

`record` 可引用已有审核、报告或必要事件记录，没有独立记录时可省略；提交标识及简短交付沿已有参数和正文表达，不因接口示例使用记录参数就为每项任务新建文件。接续只补实际缺失信息，创建、送达、执行完成和技术通过分别判断。

### 7.3 异常、展示与材料

请求结果未知时先查原回执、原会话及已有运行任务，按[工具恢复办法](session_handover_tool/README.md#回执与失败处理)办理，不盲目补建或换请求编号重发。回报按接收者分别判断，只有确定失败项才按同一回报标识恢复；接收方忙不等于技术任务失败，不据此重做实现或验证。

A 派发后结束本轮并等待交付，避免保持阻塞轮询占用回报接收会话。需要查询时沿适配器已有方式取得原请求结果；目前仅 Harness 提供统一 `probe/read/wait`，其余通道沿所支持的原生结果或执行者交付判断，不假定所有通道都有相同等待接口。

配置及有意义的绑定变化由工具登记，SESSIONS 只同步展示，任务进度仍由 A 维护 STATE。运行回执、必要正文及日志在项目选定运行目录保存；正式材料按证据规则保留或引用，不逐消息提交、不把整个运行目录复制进协议仓库。通用代码、原生调用说明及已有验证记录仍在工具模块维护。
