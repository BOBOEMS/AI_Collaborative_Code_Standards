# 嵌入式 AI 协作开发规范 V2.0

版本：V2.0（试行）  
日期：2026-09-10  
适用范围：MCU、RTU、BootLoader、驱动、RTOS、通信、低功耗及配套 PC 工具的项目建设与维护。

本规范建立“项目目标 → 总体方案 → 里程碑详细设计 → 获批分片实现 → 验收与代码理解交付”的工作关系。AI 调查事实、提出方案和取舍建议；用户确认架构、文件与函数设计、关键运行逻辑及实施边界；AI 完成获批工作并整理证据。主要精力投入设计、实现和必要验证，独立复审集中在有明确需要的关键节点。

新项目从总体方案开始，已有项目引用或补齐基线，局部维护复用已确认的设计。日常入口见[实际项目结构](#project-files)，执行顺序见[项目工作流](#workflow)。

## 1. 用语与职责

- **必须 / 不得**：需要遵守的要求；违反时暂停受影响的工作并报告。**应**表示默认采用，偏离时说明原因；**可**表示按需要采用。
- **总体方案**：项目目标、系统边界、模块及文件职责、共用契约、主函数与主要运行和失败路径、资源约束和总体验收标准。
- **里程碑**：具有明确进入条件、阶段成果和完成条件的一组工作。完成情况以其验收结论为准。
- **分片**：一个能独立说明目标、依赖、交付结果和完成条件的工作单元。类型包括方案讨论、必要预研、代码实现和集成验证。
- **设计冻结**：指定版本的设计由用户明确确认；需要独立复审的对象先完成规定复审。未决部分须标明边界和依赖。冻结记录不自动授权全部代码实施。
- **批准范围**：用户明确确认的方案版本、文件职责、函数设计与关键逻辑、可执行分片、验证方式、检查点及操作权限。以实际原话或可访问记录为依据。
- **行为变化**：接口、协议字节、状态、所有权、时序、错误码、重试、超时、资源、功耗、复位或恢复方式的改变。
- **证据**：可复查的检查输出、构建日志、测试结果、产物、测量值或板端记录。设计、计划和批准记录证明约定，不能证明实现已通过验证。

用户掌握设计决定权。AI 负责整理具体方案、比较有意义的选择、指出问题并说明推荐依据，形成用户可以理解和修改的设计稿，不能要求用户先独自设计完整工程。用户确认的内容包括：

- 总体架构、文件划分、每个文件的职责和依赖。
- 拟新增或修改的每个自研函数，包括 `static` 辅助函数：职责、接口、调用关系、关键逻辑、边界行为及注意事项。
- 主函数和主流程：初始化与调用顺序、触发和转移条件、状态与数据变化、正常出口、异常处理及关键约束。

复杂或高风险函数展开关键步骤和失败路径；简单辅助函数可以用一行说明其功能、输入输出和边界行为。已有已确认设计可引用，未变化的函数无需重复确认。复用厂商或自动生成代码时记录使用入口和契约，不逐个重写其内部函数设计；需要修改时仍确认受影响设计。

AI 可在已确认设计内完成局部变量命名、排版、注释和语义已经确定的具体编码。细节以是否影响行为、结构或约束划分，不以行数划分：空参数是报错还是忽略、超时是返回还是重试，都属于设计决定。新增或拆合函数、改变职责或调用顺序，以及新增状态、任务、队列、定时器、重试、恢复、依赖、配置、抽象和外部行为，均须在实施前纳入用户确认；不能以“健壮性”或“普通实现细节”为由自行补入。测量已批准预算内的增量属于验证，超预算时按设计偏离处理。

用户要求建立或更新方案、计划和规范时，AI 可以编写相应文档并保留待确认项。编写草案、通过 AI 复审或更新状态字段都不能代替用户的实际批准。

## 2. 规范包：一份正文与四种模板

```text
v2.0/
├─ PROTOCOL.md
└─ templates/
   ├─ AGENTS.template.md
   ├─ PROJECT.template.md
   ├─ PLAN.template.md
   └─ MILESTONE.template.md
```

| 文件 | 作用 |
|---|---|
| 本文 `PROTOCOL.md` | 通用流程、权限、复审、证据与完成声明的唯一规则正文 |
| [AGENTS.template.md](templates/AGENTS.template.md) | 项目的规则入口、操作约束、构建测试入口和文档导航 |
| [PROJECT.template.md](templates/PROJECT.template.md) | 项目目标、总体架构、文件职责、主流程、共用契约及总体方案确认 |
| [PLAN.template.md](templates/PLAN.template.md) | 里程碑安排、依赖和当前工作指针 |
| [MILESTONE.template.md](templates/MILESTONE.template.md) | 阶段函数设计、分片、授权、实施检查、运行逻辑讲解与验收 |

规则正文解释要求，模板提供字段和填写说明。A、E 等级及完整红线不复制到各项目的 `AGENTS.md`；入口必须保留读取顺序和少量带来源的关键执行提示，提示随权威正文同步，不成为第二份独立规则。项目需引用可访问的固定规范版本；必须携带离线副本时保留一份明确标识的副本。

## 3. 实际项目结构与信息归属

```text
项目根目录/
├─ AGENTS.md
└─ docs/ai/
   ├─ PROJECT.md
   ├─ PLAN.md
   ├─ milestones/
   │  ├─ M01-xxx.md
   │  └─ M02-xxx.md
   └─ evidence/
      ├─ M01/
      └─ M02/
```

这是“三份常驻文件 + 每个里程碑一份工作文件”的默认结构。里程碑详细文件在进入近期规划时建立，证据目录在实际产生材料时建立；不预生成全部阶段的空文件。

| 信息 | 唯一维护位置 | 其他文件的用法 |
|---|---|---|
| 规范入口、构建测试命令、项目操作约束 | `AGENTS.md` 或其引用的现有说明 | 引用入口，不重复解释通用规则 |
| 项目目标、技术基线、总体架构、现行文件职责与主流程、共用契约、总体验收定义 | `PROJECT.md` 或其引用的已有权威文件 | 引用章节、ID 和相关版本 |
| 里程碑成果摘要、顺序、依赖、详细入口和当前工作指针 | `PLAN.md` | 不另建进度汇总正文 |
| 阶段进入/完成条件、函数详细设计、分片状态、实施权限、检查与验收结果、运行讲解 | 对应 `milestones/Mxx-xxx.md` | 总计划保留摘要和链接 |
| 原始日志、测量、测试输出和必要产物 | `evidence/Mxx/` 或已有证据系统 | 用证据 ID 与链接复用 |

总体方案确认记录跟随 `PROJECT.md`，计划确认记录跟随 `PLAN.md`，局部设计及实施批准跟随里程碑文件。同一次决定覆盖多个对象时只记录一次，其他位置引用记录及适用范围。

`PROJECT.md` 的文件职责表按函数或设计 ID 指向当前详细设计。函数在后续里程碑变更时，引用已确认版本、只补本次差异，并更新相应入口；原记录保留为历史，不另建一份独立维护的全项目函数说明书。

`PROJECT.md` 中的总体验收定义只保存预期条件。里程碑引用其 ID，补充阶段场景并保存实际结果。最终系统验收里程碑逐项汇总总体验收结论，引用已有证据并补足集成验证。

当前技术值只有一个权威来源；验证使用的源码、配置、产物和硬件标识属于历史快照，必须保留，不能按重复信息删除。旧方案和旧批准要能按版本追溯；有版本管理时引用提交，没有时按需保存冻结快照。

### 3.1 阅读与维护

1. 读取项目及修改目录适用的 `AGENTS.md`，按其入口先读采用的 AI 协作规范正文，确认分析、设计、编码与操作的权限边界。
2. 从 `PLAN.md` 定位当前里程碑，读取相关总体设计、文件职责、函数设计、主流程、当前任务和真实批准记录，明确本次允许实施的内容及仍未决定的边界。
3. 需要新增或修改 C/H 文件时，编码前必须读取项目采用的 C 规范。有按需路由时先读其 `AGENTS.md`，再读基础、注释及本次适用专项正文；无路由时按已明确的规范入口读取。核对适用的格式、命名、接口、注释和构建要求，不默认重读合订版或来源矩阵。其他语言按对应规范入口执行。
4. 读取必要源码、配置和证据，形成当前分片的约束与检查记录后再实施。历史阶段按依赖读取。
5. 完成工作后在一次自检中核对授权范围、设计一致性、语言规范和功能，分别记录结论并复用证据；任务状态及验收在里程碑，推进位置在计划，共用设计变更在总体方案。

首次进入项目或采用的规范变化时，读取实际规范正文；新会话、上下文恢复、切换里程碑或任务范围变化时，重新核对上述入口和受影响规则。已经在当前工作上下文读取且版本未变的内容可以复用，但历史记忆、交接摘要、仅看链接或一句“之前读过”不能代替需要读取的原文。

每个代码分片开工前，在里程碑现有基线记录中关联生效规范的位置和版本或内容标识、关键条款 ID/章节、已确认的文件与函数设计及检查入口。共用记录可引用，后续只补充差异；摘录关键条款用于执行提醒，不缩减完整规范的适用范围。此核对由 AI 完成，沿用已有批准，不增加逐片重复审批，也不逐片重抄规范或项目背景。

规范来源不可访问、条款冲突或批准边界无法确认时，先说明具体缺口，暂停依赖该决定的实现；其他独立且已授权的工作可继续。不能自行用常见代码风格或既有代码习惯替代用户指定的规范。

同一事实可被摘要引用，但不得出现两份独立维护的当前设计、批准正文或 PASS/FAIL 表。项目原有 README 保留产品说明与入口，任务聊天用于沟通，结论和实际批准整理到上述权威位置。

### 3.2 裁剪与既有项目

- 已有同等职责的需求、架构、配置或验收文件可以直接映射和引用，不强制改名或迁移历史记录。
- 小任务可作为现有里程碑的一条分片；纯分析按所需事实和建议裁剪，低风险修改简记目标、已确认设计或具体用户决定、范围、结果和必要验证。
- 不默认另建 `TASKS.md`、`DECISIONS.md`、`FEATURE_SPEC.md`、`IMPLEMENTATION_PLAN.md`、`ACCEPTANCE.md`、日报或交付报告；相应内容归入上述文件。
- 单个里程碑过大时先按能力或风险重新拆分；确需拆出长设计或记录时，保留一个权威正文和原文件中的引用。
- 既有项目采用本规范只改变后续文档组织约定，不自动迁移、删除旧文件或追认旧代码符合新方案。

## 4. 从项目启动到交付

| 阶段 | AI 需要产出的可审查结果 | 进入后续工作的条件 |
|---|---|---|
| 需求与边界确认 | 目标、系统边界、不做事项、约束、可判断的成功条件 | 用户确认影响设计的目标和取舍 |
| 总体方案讨论与必要预研 | 模块与主要文件职责、主函数与主路径、共用契约、候选方案、事实与未知项 | 影响总体选择的未知项取得依据，或明确哪些范围仍受阻 |
| 总体方案冻结 | `PROJECT.md` 指定版本及独立设计复审结果 | 阻断问题得到处理，用户明确确认总体方案 |
| 里程碑规划 | `PLAN.md` 中整体目标分解、依赖和验收轮廓 | 用户确认计划，当前及近期阶段可继续细化 |
| 当前里程碑细化 | 文件与函数清单、关键逻辑和异常路径、分片及依赖、验收办法、范围与检查点 | A3 详细设计完成独立复审；用户确认本阶段设计和可执行分片 |
| 获批分片实施 | 局部结果、构建/测试、自审及规定的独立复审 | 前置条件满足且在批准范围内，按约定连续推进 |
| 里程碑验收与最终系统验收 | 阶段能力、设计与代码对应讲解、实际证据与剩余问题 | 满足规定验收及用户检查点，才关闭相应阶段或宣布项目验收完成 |

方案草稿和里程碑轮廓可以共同迭代，表中的条件约束依赖它们的工作。必要预研可先于总体方案最终冻结：明确问题、试验范围、完成条件和实际操作权限，把结论送回对应设计决定。涉及 A3 的预研须先对试验范围的详细设计独立复审并由用户确认。试验代码进入正式实现时仍须满足正式设计、构建、复审和验收要求。

新项目没有旧源码或构建结果时据实写明，并安排建立可构建骨架和验证入口。已有项目先确认实际生效版本以及目标设计与现有行为的差异。局部维护引用既有架构，只确认本次影响范围，不重新冻结整个项目。

### 4.1 总体方案需要确认到什么程度

至少明确项目目标、模块及主要文件职责与依赖、关键接口及数据所有权、主函数的初始化和调度方式、正常与失败主路径、兼容要求、关键资源预算和总体验收标准。主流程应能沿“触发 → 判断 → 调用 → 状态或数据变化 → 下一步或退出”讲清，包含关键异常由谁发现、处理和结束。候选方案按实际需要比较，不为凑数量制造选项。

先冻结跨模块、跨里程碑共用的决定。当前及近期里程碑再展开全部拟新增或修改的函数设计，不要求启动时确定所有远期函数的细节。新增文件须在实现前补齐其职责与设计入口并由用户确认。影响某个实现选择的未知项，必须在依赖它的实现开始前解决；写明影响、解决方式与时点、受阻任务及结论位置。

### 4.2 里程碑怎样拆

里程碑按可交付能力或明确风险闭环组织，写出目标映射、进入条件、前置依赖、分片和完成条件。整体目标、顺序和验收轮廓前期确立，当前及近期阶段详细展开。

当前阶段的函数清单至少说明所属文件、职责、输入输出、主要调用关系及边界行为。关键函数补充有序步骤或简短伪代码、分支与状态转移、错误处理与退出、所有权和资源注意事项；共用契约引用总体方案。多个相关函数可以一次讨论并确认，不按每个函数分别启动审批或独立复审。

应尽早安排关键未知项和能够贯穿主要链路的集成验证。各模块分别通过不能直接推出系统通过；最终系统验收必须覆盖 `PROJECT.md` 的所有适用总体验收项。

## 5. 分片、批准与连续推进

| 分片类型 | 交付结果 | 完成条件 |
|---|---|---|
| 方案讨论 | 方案取舍、明确设计和待决问题处理 | 所需复审完成，影响后续实现的设计得到用户确认 |
| 必要预研 | 围绕一个未知项的可复查事实与结论 | 满足预先约定的调查或实验目标，结论足以支持选择或否定原假设 |
| 代码实现 | 满足已批准设计的一个行为或失败边界 | 规定构建、检查、复审及本片验收条件满足 |
| 集成验证 | 模块连接后或真实环境中的运行证据 | 约定场景达到规定证据等级，未覆盖场景明确列出 |

分片类型描述交付物，A 等级描述实际操作权限，二者分别判定。只读分析高风险问题不取得修改权限；标成预研也不能绕过实际硬件或代码操作的授权。

每片写清所属里程碑、依据设计版本、前置设计/任务/证据、目标、完成条件、风险和实施范围。代码切片按一个可独立审查、验证和回退的行为组织，不按函数或文件机械拆分。设计讨论可独立成片，其完成不要求修改生产代码。

**默认推进节奏：每个里程碑先确认文件与函数设计、可执行分片和检查点，AI 在已批准范围内连续推进。** 拆片计划先具体化，再批准；尚未解决函数职责、关键逻辑或异常处理等设计问题的分片不能被隐含包含在批量授权中。

分片实现与自检完成后，可记录为“实现完成，待集中复审/验收”。到达约定检查点前，可以继续依赖条件已满足的获批分片；需要先取得复审或实测结论的依赖仍须满足。待检查状态不等于分片验收或里程碑通过。

用户批准在对应版本和范围内持续有效，不因进入下一已批准分片、实际行数变化或遇到已明确包含的高风险面而重复询问。到达约定停止检查点、出现实质偏离或新增操作权限需求时，暂停受影响工作。进入后续里程碑时核对其授权和依赖；总计划中列出该阶段不代表已允许全部实施。

批准可以一次覆盖设计和多个实施分片，也可以仅批准讨论或预研。记录必须保留实际来源、对象版本、范围、验证要求和检查点；AI 不得用默认选项、未答复、草案文字或自身复审结果生成批准状态。

切片以完整行为、明确依赖和可验证、可回退为依据。文件数与行数只用于评估理解负荷，不单独触发拆片、独立复审或重复批准；多个独立行为或难以解释的风险耦合应重新评估拆分。相关分片共用设计、基线和检查记录，并可在约定节点合并复审。

<a id="authority"></a>
## 6. AI 权限与嵌入式红线

生产文件包括交付固件、配套工具和生产配置涉及的源码、头文件、启动/链接及配置文件。有效生产代码指新增或改变语义的代码，不含纯格式、注释和自动生成输出；生成源及工程配置变化须单独说明。

| 等级 | 适用范围 | 实施条件 |
|---|---|---|
| A0 只读分析 | 分析、解释、审查、诊断或先给方案 | 可读文件、分析和运行非破坏性检查；未获授权不得顺手修改源码、配置或文档 |
| A1 已确认设计内直接修改 | 一个局部行为，约 2 个生产文件及 80 行有效生产代码以内，不触及红线 | 用户已要求修改，相关文件、函数与行为已有确认，或本次明确指令已确定所需设计；无影响行为的未决问题 |
| A2 方案后修改 | 非红线的多文件、内部接口或行为调整，规模超出 A1 | 提出简短方案，明确行为、范围、基线和验证，批准后实施 |
| A3 设计冻结后修改 | 下表任一红线 | 冻结相关设计并明确实施授权，按分片推进，保留规定的目标板验收 |

开始修改前按实际最高风险判级。AI 可主动升级，不得自行降级。A1 超出适用边界须升级；只改一行地址、优先级或有效标志也可能是 A3。独立 AI 复审不降低权限或证据要求。

A 等级不放宽用户的设计决定权，所有等级均遵守第 1 节。判级以实际改动及影响为准：仅修正注释或排版且不改变行为时，不因位于高风险文件而自动要求 A3 复审，仍须检查对应规范。

| 红线领域 | 必须明确的设计与验证内容 |
|---|---|
| BootLoader / OTA | 分区、向量、镜像有效条件、校验及安装顺序、版本/降级、回滚和最大镜像；损坏镜像、空间边界、复位掉电与旧镜像保留 |
| Flash / EEPROM / FRAM | 布局、格式、迁移、擦写粒度、原子提交、CRC 和寿命；提交顺序、掉电中断点、重复写入及容量边界 |
| 硬件 / 寄存器 | 引脚、时钟、复位、上电电平、电源轨、模拟阈值、校准、PWM/执行器；实际手册和勘误、状态变化及必要仪器验证 |
| ISR / DMA | 可调用 API、所有权、生命周期、完成/错误/中止、原子性、缓存/对齐/屏障；竞争、高负载、超时和重复使用 |
| RTOS 并发 | 任务、优先级、栈、锁/队列、阻塞、锁顺序和 ISR-safe API；栈余量、队列满、超时、优先级及死锁路径 |
| 协议 / RS485 | 线上格式、端序、长度、ACK、回显/噪声、半双工切换、重试、幂等和超时；丢包、重复、错长、CRC 错、乱序和恢复 |
| 低功耗 / 电源 | 进入条件、唤醒源、GPIO 保持、时钟与外设恢复、网络/GNSS 周期；实测电流、多次和异常唤醒 |
| 看门狗 / 恢复 | 喂狗位置、覆盖阶段、复位原因和恢复动作；真实卡死或超时复位及复位后的安全状态 |
| 安全与关键控制 | 鉴权、密钥、固件可信条件、调试口、执行器默认状态、故障降级；信任边界及失败安全状态 |
| 资源 / 实时性 | RAM、Flash、堆、栈、CPU、ISR 延迟、启动时间、功耗及增量预算；Map、栈高水位、时序或功耗基线对比 |

普通日志、解析和参数检查一旦影响上述行为，同样按实际风险执行。

A0–A3 管理 AI 修改权限，E0–E4 描述验证证据。项目在 `PROJECT.md` 或已有基线中明确协作方式及真实确认来源：个人+AI 按本文执行设计确认、自检和必要独立复审；多人团队还执行其已采用的 R0–R2 或其他人工评审制度。既有项目沿用已确认方式，不能因引入 C 规则或当前只有一名用户就自行切换。A、R、E 不能机械换算，AI 复审次数不折算成人工评审人数。

两种方式都执行适用的 C 等技术规则和验证门槛。个人+AI 可引用已有风险及技术影响说明，不另填第二套风险登记；团队仍保留所需人员和真实批准记录。技术规范中的构建、专项测试等要求按实际变化适用，不能因没有单独填写 R 标签而省略。

## 7. 基线、修改和工具边界

A2/A3 编码前记录实际仓库和源码状态、未提交修改、相关硬件与 BOM、工具链和配置矩阵、修改前构建/告警/资源与测试结果；A1 在条件允许时采集。已有基线可引用，执行时保存实际版本及差异。历史目录、旧日志和旧注释不能自动替代当前事实。

目标在修改前已经构建失败时，先用独立分片修复，或由用户明确批准已知失败基线、可继续范围与替代检查。继续工作不得新增或扩大失败，必须报告“目标构建未通过”，不得合并、发布或进入依赖该构建结果的分片。

新项目的初始骨架应以建立规定目标构建为完成条件。确需暂时不可构建的脚手架分片，须明确授权并标为不可交付；在规定目标恢复可构建之前，不进入下一实现分片或合并。基线通过时，代码分片结束必须保持规定目标通过。

- 只修改已批准范围，保留用户已有修改；未知改动先核对，不覆盖或擅自回退。
- 可沿调用链只读查看必要依赖、配置与历史材料；不据此扩展修改或纳入无关问题。
- 厂商生成文件、链接脚本、启动文件、生产配置及协议常量须在批准范围内；保留原有编码和必要产物标识。
- 编译、静态检查、PC 测试和日志分析属于正常验证。目标板擦写/烧录、生产设备修改、远端推送、删除文件和其他不可逆操作须有明确授权；具体目标、范围和次数已授权时不重复询问。
- 新增代码、脚本、测试、文档和依赖需说明用途，不夹带无关格式化、重构或未来扩展。构建与临时输出使用项目约定位置，不覆盖交付物。

<a id="changes"></a>
## 8. 设计变更与停止条件

以下情况暂停受影响的实现：计划外文件、函数增删或拆合、职责、接口、调用顺序或关键分支变化；协议/存储格式、所有权、任务模型、时序、失败策略、兼容性、预算或验证要求改变；批准依赖的事实失效；关键验证不可执行且继续工作需要猜测硬件行为；需要新增不可逆操作权限。

变更在实施前写入对应权威文件，说明原因、方案、受影响的设计、里程碑、分片和已有证据，再完成所需复审与用户确认。文件职责、主流程和共用契约回到总体方案，函数细节留在对应里程碑。只重新确认受影响部分，其他已批准范围继续有效。发现已写入未经确认的函数或逻辑时，报告实际偏差并暂停受影响工作，不得用事后补填记录冒充事前批准。

进度维护、指针调整、修正链接和批准范围内的实现细节不构成重新审批。证据因变更失去适用性时保留原记录，标注失效范围和待补验证，不能直接沿用旧 PASS。

需求不清时，优先询问会改变架构、行为、兼容性、安全、并发、资源或验收的最小问题。环境不可用时可以继续独立分析和测试准备，但验证必须记为未执行。

紧急修复可压缩文档，仍须确认范围、保持最小改动、执行规定目标构建与关键恢复检查，补齐板端验证和决定记录。豁免写在受影响事项处，包含条款、原因、风险、替代控制、真实批准来源与失效条件；不得取消红线任务的最终验收要求。

<a id="review"></a>
## 9. 设计复审与实现复审

用户讨论并确认设计属于主要设计工作；独立 AI 复审用于发现具体缺口。审查按触发条件、覆盖范围和结束条件控制成本，不因函数多、分片多或文档更新而逐项增加审查轮次。

### 9.1 冻结前的设计复审

**总体架构以及涉及 A3 红线的详细设计，必须先由独立上下文的 AI 复审，再由用户确认冻结。** 方案形成可供决定的完整版本后集中初审一次；相关函数和分片共用的设计合并覆盖。已冻结且设计与相关依赖未变化时引用原记录，实质变化只复核受影响部分；索引、进度或已确认细节的回填不重启架构复审。普通详细设计默认由 AI 提案、用户确认，不额外安排独立复审；用户指定或出现需要独立判断的具体风险时说明对象及理由后安排。

设计复审围绕目标、方案和验收要求，检查目标覆盖、模块连接、共用契约、状态与所有权、时序和失败路径、资源预算、未决假设及验证可行性；不要求已经存在实现 diff。应指出缺口的影响、依据及建议，设计负责人处理后再提交用户确认。

实质设计修改后，原复审不能自动覆盖新版本。独立复审无法执行时，可以继续准备材料和不依赖该冻结的获批工作；受影响设计保持待复审、待确认，不得以自审冒充独立复审。

### 9.2 实施后的复审

实现者对本次改动完成一次自检，将授权与设计一致性、C 等语言规范、功能和必要构建测试合并安排，分别给出结论，不另起多轮同内容自审。A1/A2 默认不启动独立复审；用户明确要求，或发现跨模块契约矛盾、关键行为缺乏设计依据等需要独立判断的具体问题时，说明范围和理由，开展针对性复审。设计未决定时先讨论确认；实际触及 A3 时按红线升级，不能用自检替代。

A3 实现必须独立复审，默认把相关分片合并为能说明完整行为、验证和回退边界的功能单元，在约定检查点集中初审一次，覆盖所含分片的变化、依据和证据；各分片引用同一记录。会影响后续安全或正确性的关键设计与实现，须在依赖工作开始前完成必要复审并处理阻断问题，不能推迟到最终验收。

共享内部接口、修改规模或板端验证尚未完成，本身不自动触发额外独立复审。验证缺口按约定补充构建、测试或实测并记录未验证；需要该证据的后续工作仍受依赖约束，增加 AI 审查不能替代缺少的证据。

实现复审围绕已确认的文件与函数设计、授权、实际生效的语言规范、diff 和验证结果，可只读追踪必要依赖、头文件和配置。重点检查未获确认的函数或逻辑、需求遗漏、状态与所有权、并发/生命周期、异常恢复、兼容性、资源增量及证据缺口。已有检查确实覆盖且对象未失效的内容引用其结果，独立复审重点判断关键逻辑和未覆盖的语义问题。

已明确规定的格式、命名和注释要求属于规范符合性检查，违反时按对应规则等级处理，不能归为个人风格建议。只有规范未要求的个人偏好、规范本身的建议项及无关旧问题才按建议处理。发现应说明具体问题、位置、条款或设计依据、影响和处理建议；没有发现阻断问题时简记覆盖范围、结论及局限，不为生成长报告扩展整改范围。

独立上下文应取得必要目标、设计、事实、变更和证据，自行形成结论；实现者换一个提示进行自审不算独立复审。记录对象版本、复审来源、发现及处理情况。独立 AI 复审用于发现缺口，不提升 E 等级，不代替人的确认、目标构建或板端测试。

### 9.3 用户检查点

设计确认时，AI 先用流程、函数说明或伪代码讲清正常主路径和关键异常路径，再由用户决定取舍。实现交付时沿实际代码说明设计如何落地、在哪里判断和处理异常、哪些状态或结果可供排查，具体要求见第 11 节。该讲解合并进里程碑交付，复用已有设计与检查结果；普通机械性代码按风险抽查，不要求用户逐行重推整个工程。

### 9.4 复核与结束条件

- 同一对象默认一次初审加必要的问题复核；修正后只复核问题、受影响代码、依赖和证据。新增实质风险、修复扩大影响或相关检查失败时才扩大范围，并说明具体原因。
- 约定范围已覆盖、阻断问题已处理、该检查点所需检查已完成，就结束本次审查。后续计划中的待验证项继续跟踪，不据此声明整个里程碑通过；不以多轮“零问题”作为完成条件，也不因泛泛担心重复审查相同输入。
- 提供当前对象、设计与规范入口、必要约束、变化和证据即可，不重复输出全项目背景或规范全集。复用仍在上下文中且未变化的内容；首次读取及上下文恢复仍遵守第 3.1 节。
- 一次检查或复审只保存一份结果，相关分片和验收项引用；默认不为同一对象启动多名 AI 互审或生成独立长报告。已有自动检查负责其实际覆盖的规则，AI 核对未覆盖的语义问题；缩短报告不降低明确的规范与验收要求。

## 10. 验收与证据

| 等级 | 实际证据 | 能支持的结论 | 不能据此声称 |
|---|---|---|---|
| E0 | 源码阅读、调用链和静态推理 | 已分析入口、事实、风险或假设 | Bug 已修复、硬件通过 |
| E1 | 静态检查、规定目标编译链接、Map、告警和镜像检查 | 列出的构建或静态检查通过 | 功能、时序、功耗或板端通过 |
| E2 | PC 单测、Mock、协议回放、模拟器及主机故障注入 | 列出的主机或模拟场景通过 | 真实外设、中断、功耗或板端通过 |
| E3 | 指定目标板、真实外设及调试器/仪器测试 | 列出的板级场景通过 | 未执行异常、长期可靠性或量产通过 |
| E4 | 指定目标板或真实系统的断电、复位、丢包、噪声、压力、长稳及温度/电源边界等故障注入 | 列出的实机故障或环境场景通过 | 未执行场景安全或量产通过 |

实施前为每个适用验收项确定预期结果、范围、验证方法/环境和所需证据等级，实施后再记录实际结果与实际等级。讨论与设计确认引用评审及用户决定，不把批准套成代码或硬件验证通过。

证据要求按风险选择：纯解析可由 E2 覆盖；真实收发切换、ISR/DMA/RTOS 行为需 E3，竞争或压力边界按要求取 E4；OTA/NVM 的掉电一致性通常需 E4；低功耗电流与唤醒至少需仪器支持的 E3。不得为提前完成而事后降低已确认的验收标准。

同一种故障在 PC/Mock 中模拟，最高仍为 E2。E3/E4 必须关联实际板卡/PCB/BOM、源码、构建配置、固件标识、测试条件、施加方法和原始结果。编译及资源对比保留修改前后数据，历史失败与新增回归分开报告。

里程碑中的最小证据索引包含：证据 ID、源码状态、构建标识、产物及 SHA-256（适用时）、硬件与测试条件、原始材料位置。未提交时用可复查的工作区状态或补丁标识源码。原始材料放证据目录或已有系统，同一证据可被多项验收引用。

验收结果使用 `PASS / FAIL / 未验证`，必须关联证据并区分所需与实际等级。取得部分 E2 证据但尚缺规定的 E3/E4 时，仍为未验证或按场景拆分结果，不能把整体写成 PASS。已执行且不满足预期的项写 FAIL。

### 10.1 授权范围与代码规范检查

自检中还须核查本次 diff 是否超出已确认的文件、函数和关键逻辑，以及代码是否符合适用的语言规范。授权与设计一致性、规范符合性、功能验证在同一次检查中安排，分别保留结论并共用证据，不能用编译或功能成功替代其他结论。记录按工具或专题合并，包含条款、实际对象、方法、结果和证据位置，不逐条抄写整个规范。

C 等语言检查表作为本次技术检查索引，适用门禁关联到现有里程碑记录，不额外复制整张表或启动一轮语言规范复审。同组不适用项可合并说明依据，适用但未执行的项记为未验证；同一源码、配置、范围及相关依赖的有效结果直接复用，变化后只补受影响项。技术规则发现的设计缺口先提出并由用户确认，不因此自行增加函数或逻辑。

| 约束类别 | 核查方式 |
|---|---|
| 文件、函数和计划外逻辑 | 对照已确认的文件职责、函数设计、主流程和实际 diff，核对函数增删或拆合、关键分支、调用顺序、异常处理和其他未批准的行为 |
| 缩进、空格、花括号布局等排版 | 执行项目已固定版本和配置的格式检查，记录命令与结果 |
| 命名、注释约定、文件编码和声明规则 | 按条款采用适用的专项检查或针对变更的逐项复核，明确自动检查没有覆盖的内容 |
| 所有权、并发、时序、恢复及注释内容是否有效 | 结合实际代码、设计和证据进行语义自检，按第 9 节安排必要独立复审及验证 |

格式配置文件存在、规则被标记为 `AUTO-BLOCK` 或清单已经勾选，都不证明检查实际执行。项目接入格式或专项检查时，应确认其覆盖哪些条款；工具未覆盖的规则保留复核要求。注释格式、命名语义或行为越界不能默认由格式化器覆盖。

已规定的检查未执行时，记录未验证及原因，不能声明规范检查通过；发现阻断违规时在批准范围内修正，超出范围则提交变更或报告受阻。自动检查入口的新增、工具安装或 CI 接入按实际任务范围实施，不因本文要求核查而取得额外修改权限。

检查聚焦本次新增和修改的自研代码，保护历史编码、厂商代码和无关改动；不得为了规范检查顺手全仓格式化。检查覆盖与未覆盖项保存在里程碑，具体命令或现有脚本入口由 `AGENTS.md` 引用。

## 11. 完成声明与交接

- 编译成功只称目标构建通过；PC/Mock 成功只称列出的主机场景通过；无实机证据写“实机尚未验证”。
- 代码已实现但尚缺规定验收时，分别写“实现完成”和“阶段/发布验收未完成”。方案阶段按其设计确认条件完成，不虚构代码进度。
- 里程碑关闭需满足阶段范围内的设计、分片、必要复审、验收及代码理解交付和用户检查点；分片全部结束不自动证明集成通过。
- 项目验收完成需最终系统验收里程碑逐项覆盖总体验收要求，并明确源码/产物版本及剩余适用限制。不能用任务数量、测试数量或目录完整度代替验收。

到检查点时给出简短交付说明：实际完成及入口、行为变化、依据的设计与批准、修改前后结果、函数或逻辑变化及事前确认来源、验证与未验证项、偏差和下一工作入口。详细事实更新到里程碑，聊天引用结果，不额外生成重复交付文件。

代码理解交付与里程碑交付合并，记录在该阶段文件：

- 将本阶段设计映射到实际文件和函数，走通一条正常主路径及约定的关键异常路径，说明调用顺序、判定条件、状态或数据变化、错误传播和最终出口。已讲解且未变化的部分引用原说明，只补本次差异。
- 对约定的典型异常现象列出优先检查的文件或函数、可观察的状态/返回值/已有日志，以及区分可能原因所需的检查或实测。新增日志、状态或诊断逻辑仍须先纳入已确认设计。
- 用户能够据此说明主要运行逻辑、责任边界和初步排查入口，在检查点记录实际反馈及待澄清处。初步定位需要调试与实际证据确认根因；讲解和用户理解不提升 E 等级，也不替代功能验收。

交接时更新 `PLAN.md` 的当前工作指针，确保当前里程碑的版本、批准、依赖、阻断问题和证据入口完整。关闭阶段的文件保留为记录，后续按需读取。
