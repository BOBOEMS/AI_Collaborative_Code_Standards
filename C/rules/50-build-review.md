## 16. C 风险扩展、评审与热修复

### 16.1 C 风险扩展

协作方式以项目基线为准，适用边界见 [共享治理基线](../../共享/团队治理与评审基线.md)。多人团队按 R0/R1/R2 登记风险；个人+AI 可引用已有协作记录中的风险及技术影响说明，不要求另填一套 R 等级。技术验证仍按实际变更适用 R0/R1/R2 的门槛，不能把 AI 权限等级直接换算成 R 等级或降低证据要求。无法确定技术风险时按更高一级处理。

C 的 R2 触发项见第 1.1 节。R1/R2 的基础证据仍须包含 clean build、零新增警告和与风险匹配的主机或板级测试；个人+AI 项目涉及同类变化时同样适用。专项规则中的 R2 测试要求按技术影响执行，不依赖是否另填 R 标签。

- **[REV-001][REVIEW-BLOCK]** 多人团队的每个模块必须在现有责任记录或 [共享责任模板](../../共享/模块责任与轮值模板.md) 实例中登记主负责人和备份，负责人不拥有跳过评审的特权。个人+AI 记录实际责任人及批准来源，不虚设备份或轮值角色。
- **[REV-002][REVIEW-BLOCK]** 多人团队的评审人数与作者不得自批要求按 [共享治理基线](../../共享/团队治理与评审基线.md) 执行；个人+AI 按项目明确采用的协作规范执行自检、必要独立复审和用户确认，不能自行取消已有团队要求。
- **[REV-003][REVIEW-BLOCK]** 检查记录必须能追溯风险或技术影响、变更范围、验证结果、资源变化、兼容/回滚影响及适用豁免，可直接使用现有里程碑或等价记录。[C 检查索引](../pr_checklist.md) 的 19 项门禁只核对适用项；同组不适用项可合并说明依据，未执行项须标为未验证。同一对象、配置和覆盖范围的有效检查结果只记录一次，其他位置引用，不重复填写完整表单或抄写规则。
- **[REV-004][AUTO-BLOCK]** 目标配置必须构建成功且零新增警告；生成物、Keil `OBJ/`、`Listings/`、用户 `.uvguix` 和编辑器日志不得进入提交，项目明确要求归档的发布产物除外。
- **[REV-005][REVIEW-BLOCK]** R1/R2 测试必须可复现，记录固件版本、硬件版本、配置、输入、预期、实测和日志/波形/抓包位置；“能编译”不等于功能验证。
- **[REV-006][ADVISORY]** 人工代码超过 300 行或涉及超过 8 个代码文件时，在约定检查点评估能否理解、验证和回退；团队由作者与评审者共同判断。这是负荷提醒，不因数量单独增加审批或独立复审，也不机械拆片。

技术检查至少覆盖本次适用的错误返回和资源恢复、长度/溢出/字节序/对齐、并发/ISR、栈/堆预算、协议/NVM/OTA 兼容及回滚，以及无关改动。将这些内容并入已有自检或集中复审，保留设计一致性、规范符合性和功能验证的分项结论；通过项简记，具体问题再展开。

### 16.2 生产热修复接口

热修复只用于已影响生产、现场服务或安全的紧急缺陷，不用于绕过普通开发流程；适用方式和操作步骤见 [共用热修复流程](../../共享/豁免与紧急修复流程.md)。已有里程碑或事件记录覆盖必要字段时直接引用，不要求另建热修复单。

- **[HOT-001][REVIEW-BLOCK]** 热修复单必须记录事件编号、影响、根因假设、最小改动范围、风险等级、部署步骤、回滚包/回滚步骤和负责人。
- **[HOT-002][REVIEW-BLOCK]** 部署前至少完成目标配置 clean build、零新增警告、针对缺陷的冒烟测试，并履行项目所采用流程的批准；多人团队至少取得 1 名非作者批准。无法执行的检查必须逐项记录风险和补偿措施。
- **[HOT-003][REVIEW-BLOCK]** 多人团队的 R2 热修复可在紧急情况下先由 1 名非作者批准部署，但须在下一个工作日补齐第二名评审。两种协作方式均须按共用流程补齐完整专项测试、所采用流程要求的复审和事故复盘；未补齐前不得关闭事件。
- **[HOT-004][REVIEW-BLOCK]** 热修复必须保持可回滚；部署后按约定观察关键指标，触发回滚判据时由事件负责人执行既定回滚。

## 17. 自动化、项目配置与可复现构建

第一阶段仅检查新改动，不对历史工程做全仓格式化。

- **[BLD-001][AUTO-BLOCK]** 仓库必须固定团队 `.clang-format` 版本和内容；当前基线版本为 clang-format `19.1.7`，配置以本规范的 4 空格、100 列和同一行左花括号为准。版本升级必须单独评审格式差异。OpenTitan 仅用于比较可执行格式选项，不得直接复制其默认缩进并宣称符合本规范。
- **[BLD-002][AUTO-BLOCK]** 格式检查只作用于新增/修改的团队 C 文件或改动行；未经独立评审禁止全仓 `-i` 格式化。
- **[BLD-003][REVIEW-BLOCK]** 每个项目必须维护执行配置：权威编译器及精确版本、C 标准、Device Pack/SDK/FreeRTOS 版本、编译/链接选项、链接脚本、硬件变体、功能开关和构建入口。已有 `PROJECT.md`、机器配置或专项文档可直接承载，不强制新建配置文件；只构建项目声明支持的工具链，不强制 ARMCC5 项目同时移植 GCC。
- **[BLD-004][AUTO-BLOCK]** Debug/Release 构建必须能从干净工作区通过脚本或明确命令重现；依赖版本必须锁定，生成文件必须记录生成工具和输入。禁止把 `__DATE__`、`__TIME__` 等不可控时间写入功能固件。
- **[BLD-005][REVIEW-BLOCK]** 工具链支持时，相同源码、配置和工具链应生成字节一致产物；做不到时必须列出已知非确定字段，比较规范化后的镜像或有效段哈希，并在发布清单记录原因。
- **[BLD-006][AUTO-BLOCK]** 构建门禁必须检查零新增警告；历史警告建立带数量和指纹的基线，新增、升级或消失后复现的警告均不得静默忽略。
- **[BLD-007][AUTO-BLOCK]** 发布构建必须用 map/size 检查 Flash、静态 RAM 和 MSP 预算，并用目标板运行证据检查任务栈高水位及 heap 最低剩余量；阈值写入项目执行配置，超限阻断发布。
- **[BLD-008][REVIEW-BLOCK]** 发布清单必须记录源码版本、未提交差异、工具链/依赖版本、硬件变体、配置、测试证据和产物哈希；正式发布必须来自无未提交差异的受控源码状态。
- **[BLD-009][ADVISORY]** 静态检查分阶段接入，优先检查空指针、数组越界、未处理的业务返回值、死代码、隐式转换和未初始化变量。

推荐把格式检查、clean build、警告差分、资源预算及适用测试接入项目已有检查入口；相同对象、配置及相关依赖的有效结果可复用，变化后补受影响项。必要工具在初始化或配置变化时接入，不因每次读取规范重新安装工具、搭建 CI 或校验规范包。工具与规范出现差异时执行 `GOV-002`。

## 18. 豁免与版本管理

记录模板、批准人与下一工作日补齐要求统一见 [共用豁免与紧急修复流程](../../共享/豁免与紧急修复流程.md)；以下规则保留 C 分册的稳定 ID。

- **[EXC-001][REVIEW-BLOCK]** 豁免必须包含：规则 ID、技术原因、风险、替代控制、适用文件/版本、负责人、批准人和到期日。
- **[EXC-002][REVIEW-BLOCK]** 临时豁免到期后必须删除、续期或转为正式设计决策；过期豁免阻断后续相关变更。
- **[EXC-003][REVIEW-BLOCK]** 新增强制规则或破坏既有规则时升主版本，新增兼容规则时升次版本，文字澄清升修订版本；规则 ID 不随章节移动而改变。
- **[EXC-004][ADVISORY]** 团队每 3 个月或重大事故复盘后评审一次规范；删除无收益规则时保留 ID 和删除原因。

豁免记录示例：

```text
Rule: RTOS-006
Scope: app_meter_task.c @ release/1.2
Reason: ...
Risk: ...
Compensating control: ...
Owner / Approver: ... / ...
Expires: YYYY-MM-DD
```
