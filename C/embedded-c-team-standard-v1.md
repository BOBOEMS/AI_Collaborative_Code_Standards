## 1. 目标、规则编号与共用治理

本规范按以下顺序优化：**安全可维护、可验证、便于协作、风格一致**。它吸收 BARR-C 的嵌入式实践、Zephyr 的工程约束，并把 OpenTitan 仅作为自动格式配置的参考；本规范不是 MISRA 合规声明，也不替代产品安全认证。

每条可执行规则使用稳定 ID。ID 发布后不复用；删除的 ID 保留在变更记录中。`AUTO-BLOCK`、`REVIEW-BLOCK`、`ADVISORY` 的含义以及冲突优先级统一见 [团队治理与评审基线](../共享/团队治理与评审基线.md)。

同一次自检或评审核对本次适用的技术规则，共用已有有效结果；`REVIEW-BLOCK` 不表示每条规则都要独立 AI 复审。规范核对发现需要补充接口、状态、超时或恢复等设计时，先按项目流程提出并确认，不直接增加未获确认的实现。

- **[GOV-001][REVIEW-BLOCK]** 不能满足阻断规则时，必须按 [共用豁免流程](../共享/豁免与紧急修复流程.md) 获得有期限的豁免；口头约定不算豁免。
- **[GOV-002][REVIEW-BLOCK]** 规则与自动工具冲突时，必须修正规范或工具配置；修复前按 `GOV-001` 临时豁免，不得长期依赖人工忽略。

### 1.1 C/FreeRTOS 的 R2 扩展

除共享基线外，Boot/链接、时钟/电源、IRQ/DMA/并发、FreeRTOS 栈/heap、NVM、OTA、看门狗、安全、协议兼容和资源预算的变更均为 R2；具体验证要求见第 16 节和 [C 合并检查表](pr_checklist.md)。

## 2. 适用边界与目录责任

### 2.1 上游代码

- **[SRC-001][REVIEW-BLOCK]** 芯片厂商库、CMSIS、FreeRTOS 内核及 portable 层、第三方协议栈、启动文件、链接脚本和生成代码必须在仓库说明中记录来源、版本、许可证及本地补丁。
- **[SRC-002][REVIEW-BLOCK]** 修改上游代码时，必须把本地补丁限制在需求范围内，并保留可识别的差异和验证证据；禁止仅为符合团队格式而重排上游文件。

### 2.2 分层规则

推荐调用方向：

```text
业务/状态机/协议  ->  服务层  ->  驱动抽象层  ->  BSP/HAL/寄存器
                                  ->  FreeRTOS/芯片库
```

- **[ARC-001][REVIEW-BLOCK]** 生产业务代码不得直接读写寄存器或调用厂商 HAL，必须经驱动或 BSP 接口。板级 bring-up、诊断程序和遗留适配层如需例外，必须隔离目录、明确退出产品构建的方式，或取得有范围和到期日的豁免。
- **[ARC-002][REVIEW-BLOCK]** 驱动不得包含产品流程、联网协议或业务策略；BSP 只处理板级引脚、时钟、电源和外设实例差异。
- **[ARC-003][AUTO-BLOCK]** 模块只能暴露头文件声明的接口；模块私有函数和状态必须使用 `static`。

## 3. 文件、编码与格式

### 3.1 文件规则

- **[FMT-001][ADVISORY]** 一个功能模块通常由一对 `module_name.c` 和 `module_name.h` 组成。
- **[FMT-002][AUTO-BLOCK]** 新文件名、目录名和 `#include` 路径必须使用 ASCII `lower_snake_case`；符号命名按第 4 节分别处理，不适用“一律小写”。
- **[FMT-003][AUTO-BLOCK]** 团队自研的新增 `.c` 和 `.h` 文件必须使用 UTF-8（无 BOM）；同一文件内换行符必须一致，禁止提交无关的编码或换行转换。
- **[FMT-004][AUTO-BLOCK]** 每个头文件必须有唯一 include guard，例如 `RTU_DRV_ADC_H`；项目不依赖 `#pragma once`。
- **[FMT-010][REVIEW-BLOCK]** 现有非 UTF-8 自研文件需要新增或修改中文注释时，必须先通过独立的编码迁移改动转换为 UTF-8（无 BOM），并完成该项目要求的基础构建或语法检查；编码迁移不得与功能修改混合。厂商库、第三方代码和自动生成代码保持上游编码，除非取得有范围的豁免。
- **[FMT-011][REVIEW-BLOCK]** 团队自研头文件必须自行包含声明所需的类型和宏定义，不得依赖调用方先包含其他头文件；在项目声明支持的配置下，以仅包含该头文件的最小翻译单元验证语法。依赖生成配置的头文件必须明确生成前置步骤。

### 3.2 排版规则

- **[FMT-005][AUTO-BLOCK]** 缩进为 4 个空格，禁止 Tab；自动格式目标列宽为 100。
- **[FMT-006][AUTO-BLOCK]** 函数及控制语句的左花括号同行，块内语句另起一行；右花括号另起一行，`else`、`else if`、`do` 对应的 `while` 以及类型声明尾部按团队 `Attach` 配置紧随右花括号。
- **[FMT-007][REVIEW-BLOCK]** `if`、`else`、`for`、`while`、`do` 和 `switch` 的所有分支必须使用花括号；格式化工具不能替代此项语义检查。
- **[FMT-008][AUTO-BLOCK]** 二元运算符两侧、逗号后和关键字后各留一个空格；指针星号贴近变量名，如 `uint8_t *buffer`。
- **[FMT-009][REVIEW-BLOCK]** `.c` 文件的 include 顺序为：本模块头文件、C 标准库头文件、项目头文件、第三方/RTOS 头文件、芯片/系统头文件，各组之间空一行。团队格式化配置保留现有 include 顺序，因此由评审检查此项。

```c
#include "drv_adc.h"

#include <stdbool.h>
#include <stdint.h>

#include "app_fault.h"
#include "board_config.h"

#include "FreeRTOS.h"
#include "task.h"

#include "gd32f30x_adc.h"
```

## 4. 命名规则

- **[NAM-001][REVIEW-BLOCK]** 名称必须表达业务含义和单位；禁止使用 `data1`、`temp2`、`flag` 等无上下文名称。
- **[NAM-002][REVIEW-BLOCK]** 缩写只使用团队词汇表中的通用缩写；有物理单位的变量必须在名称中写明单位，例如 `timeout_ms`、`voltage_mv`。
- **[NAM-003][REVIEW-BLOCK]** 布尔量使用肯定式名称，如 `is_ready`、`has_fault`、`enable_logging`。

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| 文件 | `lower_snake_case` | `drv_adc.c` |
| 变量、参数、结构体成员 | `lower_snake_case` | `retry_count`、`timeout_ms` |
| `const` 对象、对象式宏、编译期开关 | 带模块前缀的 `lower_snake_case` | `drv_adc_timeout_ms` |
| 函数式宏 | 带模块前缀的 `lower_snake_case` | `drv_bit_mask(bit_index)` |
| 团队自研函数 | `Module[_Feature]_VerbObject` | `CardReader_OTA_GetState()`、`DrvADC_ReadVoltageMV()` |
| 结构体、联合体类型 | `UpperCamelCase_t` | `DrvRS485Config_t` |
| 枚举类型 | `UpperCamelCaseEnum_t` | `SystemStateEnum_t` |
| 枚举值 | 带模块或类型前缀的 `UPPER_SNAKE_CASE` | `SYSTEM_STATE_IDLE` |
| 其他类型别名 | `lower_snake_case_t` | `rtu_status_t` |
| 文件内静态变量 | `s_` 前缀 | `s_sample_count` |
| 跨模块全局变量 | 原则上禁用；批准后使用 `g_模块_含义` | `g_system_uptime_ms` |

- **[NAM-004][AUTO-BLOCK]** 团队自定义的变量、`const` 对象和宏必须匹配 `[a-z][a-z0-9]*(?:_[a-z0-9]+)*`；宏必须带模块前缀，文件内静态变量必须带 `s_` 前缀。禁止使用行首、行尾或连续双下划线形式的团队自定义标识符。
- **[NAM-005][REVIEW-BLOCK]** 跨模块可变全局变量默认禁止；确需使用时必须说明并发、初始化、所有权和修改入口。
- **[NAM-006][ADVISORY]** 不为基本类型创建无抽象价值的 `typedef`，也不以大小写差异表达不同语义。
- **[NAM-007][REVIEW-BLOCK]** 团队自研函数统一使用 `Module[_Feature]_VerbObject`：所属模块在前，可选功能域居中，动作和对象在末尾；普通单词使用大驼峰，团队词汇表认可的 `OTA`、`UART`、`CRC` 等缩写保持全大写。函数名必须包含明确动作，禁止使用缺少动作的 `CardReader_OTA()` 或缺少所属模块且含义模糊的 `Get_OTA_Flag()`。
- **[NAM-008][REVIEW-BLOCK]** C 标准入口、启动文件、ISR、RTOS/HAL 回调、芯片库和第三方接口按其固定签名和名称保留；include guard 保持大写。完整或裁剪的 `error.h` 必须保留既有 errno 风格符号，作为 `NAM-004` 的明确命名例外；符号同名不表示与标准库 errno 数值或返回约定兼容，隔离要求见 `API-008`。
- **[NAM-009][REVIEW-BLOCK]** 结构体和联合体类型使用 `UpperCamelCase_t`，枚举类型使用 `UpperCamelCaseEnum_t`；团队词汇表认可的缩写保持全大写。枚举值使用带模块或类型前缀的 `UPPER_SNAKE_CASE`。例如 `DrvRS485Config_t`、`SystemStateEnum_t` 和 `SYSTEM_STATE_IDLE`。

## 5. 数据类型、整数与位操作

- **[TYP-001][REVIEW-BLOCK]** 硬件寄存器、通信帧、持久化格式、位运算及范围明确的数据必须使用 `uint8_t`、`int16_t`、`uint32_t` 等固定宽度类型。
- **[TYP-002][AUTO-BLOCK]** `char` 只用于字符和字符串，不得用于二进制数据或数值运算；FreeRTOS API 保留其规定的 `BaseType_t`、`UBaseType_t`、`TickType_t` 等类型。
- **[TYP-003][REVIEW-BLOCK]** 有符号/无符号混用、窄化转换和可能溢出的加减乘必须先验证范围，再显式转换；不得依赖溢出或实现定义的转换结果。
- **[TYP-004][REVIEW-BLOCK]** 状态、模式和命令码可使用 `enum`，但协议或存储布局不得依赖枚举底层宽度。
- **[TYP-005][AUTO-BLOCK]** 编译期整数常量使用带模块前缀的宏，运行时常量优先使用 `static const`；禁止未命名的业务“魔法数字”。
- **[TYP-006][REVIEW-BLOCK]** 移位前必须验证位号小于操作数位宽；位掩码使用明确宽度的无符号常量，如 `UINT32_C(1) << bit_index`。不得右移负的有符号数或左移可能溢出的有符号数。
- **[TYP-007][REVIEW-BLOCK]** 禁止使用 C bit-field 或仅靠 `packed` 结构体直接映射寄存器、通信帧和持久化格式；必须用掩码、移位及显式字节序读写函数。
- **[TYP-008][ADVISORY]** 对协议字段和关键尺寸使用编译期断言，尽早发现工具链或配置漂移。
- **[TYP-009][REVIEW-BLOCK]** 整数除法和取余必须在运算前确认除数非零，且结果可由整数提升及通常算术转换后的运算类型表示；特别检查该有符号类型最小值与 `-1` 的组合。后置强转不能修复已经发生的未定义行为；失败策略由接口契约规定。

以下尖括号内容是项目落地时必须替换的依据占位符，不得原样保留在产品代码中：

```c
/**
 @brief ADC 驱动支持的最大通道数量。
 @note 依据 <芯片手册名称及版本> 第 <章节/表格> 和 <板级引脚分配表编号>。
 */
#define drv_adc_max_channels (8U)

/**
 @brief ADC 单次转换的最长等待时间，单位为 ms。
 @note 依据 <ADC 采样时序需求编号>；超时后驱动必须返回错误。
 */
#define drv_adc_timeout_ms (20U)

/**
 @brief 系统运行状态。
 @note 本枚举只表示软件状态，不得按枚举底层宽度写入协议或持久化存储。
 */
typedef enum {
    SYSTEM_STATE_INIT = 0, /* 系统正在初始化，尚未提供业务服务。 */
    SYSTEM_STATE_RUNNING,  /* 系统初始化完成，正在提供正常服务。 */
    SYSTEM_STATE_FAULT,    /* 系统检测到不可忽略的故障，等待恢复处理。 */
} SystemStateEnum_t;
```

## 6. 函数与接口设计

- **[API-001][ADVISORY]** 函数只承担一个职责，建议不超过 60 行、参数不超过 5 个；超出时优先拆分或使用配置结构体。
- **[API-002][REVIEW-BLOCK]** 团队自研的新增函数，或声明、函数体有效代码发生修改的既有函数，必须按 `DOC-006` 补齐或同步更新中文函数注释；纯格式化、换行或独立编码迁移不单独触发此要求。公共函数、任务入口、ISR 和非直观算法还必须说明前置条件、单位/范围、调用上下文和副作用等适用信息。
- **[API-003][REVIEW-BLOCK]** 指针参数必须说明所有权、读写方向及可否为 `NULL`；缓冲区接口必须传递可验证的容量，并区分容量、有效输入长度和实际输出长度。仅当固定容量契约能通过类型约束、调用点检查或受控封装验证时，才允许省略独立长度参数，并记录验证方式。形参 `uint8_t buffer[16]` 会调整为指针，声明中的 `16` 及函数内的 `sizeof buffer` 都不能证明调用方容量；不得据此省略长度验证。
- **[API-004][REVIEW-BLOCK]** 可能失败且以状态码返回结果的团队接口必须使用有符号整数类型或项目定义的有符号状态类型；`0` 是唯一成功值，负数表示失败，正数禁止用于状态返回。调用方必须检查返回状态，或在评审记录中说明安全的忽略理由。
- **[API-005][REVIEW-BLOCK]** 可能失败的函数优先返回状态码，并通过输出参数返回业务数据；禁止以隐式全局状态传递函数结果。无失败路径的纯计算或查询函数可以直接返回数据；C 标准入口、ISR、任务入口和平台回调按固定签名执行。
- **[API-006][REVIEW-BLOCK]** 禁止递归，除非已证明最大深度和栈占用并取得豁免；禁止可变参数函数，受控日志封装除外。
- **[API-007][REVIEW-BLOCK]** 状态接口必须返回错误码符号，禁止直接返回未经命名的负数字面量。本目录的 `error.h` 是可选完整目录，不得要求所有项目无条件包含；任何经资源预算确认的资源受限项目都可以形成裁剪版，BootLoader 只是其中一种常见场景。`error.h` 裁剪只能删除未使用项，不得改变文件引用方式及保留项的符号、数值、别名或语义。例如 `ERROR_OK` 恒为 `0`、`EPERM` 恒为 `-1`。本目录的错误码以宏定义提供，裁剪版必须保持宏定义形式，不得为了裁剪改写为枚举。每个构建只能选择一个权威 `error.h`，直接返回其中的负值符号时不得再次取负。
- **[API-008][REVIEW-BLOCK]** 本目录 `error.h` 是项目私有负值目录，不是 `<errno.h>` 的兼容替代。同一翻译单元及其直接/间接包含链不得同时使用该目录与标准库或第三方提供的同名错误码定义；不得靠包含顺序或 `#undef` 覆盖解决冲突。接入外部库时，通过不同翻译单元的适配层显式映射错误语义，边界头文件不传播两套同名宏；不得假设外部错误值简单取负即可对应。项目必须用实际构建配置检查包含依赖、宏重定义诊断和最终宏值，并覆盖受支持变体。GCC 项目可使用 [错误码包含检查脚本](check_error_header_usage.ps1)；其他工具链采用等价检查，不要求为此移植工具链。

### 6.1 资源受限项目的 `error.h` 裁剪示例

以下示例适用于任何经评估需要缩减 Flash 或 RAM 占用的项目，例如 BootLoader、小容量 MCU 应用、恢复固件或出厂测试固件。裁剪对象是本目录已提供的宏定义版 `error.h`，不改用枚举。

`error.h` 裁剪只能删除未使用项，不得改变文件引用方式及保留项的符号、数值、别名或语义。

本文件是项目私有负值目录，`EPERM` 等名称只沿用 errno 风格；它不兼容标准库的正值 errno 约定。同一翻译单元不得同时包含两套同名宏，也不得通过 `#undef` 或调整包含顺序覆盖；适配层须在不同翻译单元中按错误含义映射，不能假设数值简单取负就匹配。按 `API-008` 检查实际包含链和最终宏值。

“未使用项”还须排除被保留别名依赖的宏：例如保留 `EWOULDBLOCK` 时必须同时保留其目标 `EAGAIN`；保留 `EDEADLOCK` 时必须同时保留 `EDEADLK`。

完整版 `error.h` 片段：

```c
#define ERROR_OK 0     /* 成功。 */
#define EPERM -1       /* 操作不允许。 */
#define ENOENT -2      /* 对象不存在。 */
#define EIO -5         /* 输入输出失败。 */
#define ENOMEM -12     /* 内存不足。 */
#define EINVAL -22     /* 参数非法。 */
#define ETIMEDOUT -110 /* 操作超时。 */
```

某个资源受限固件只使用其中五项时，项目内同名 `error.h` 只删除 `ENOENT` 和 `ENOMEM`：

```c
#define ERROR_OK 0     /* 成功。 */
#define EPERM -1       /* 操作不允许。 */
#define EIO -5         /* 输入输出失败。 */
#define EINVAL -22     /* 参数非法。 */
#define ETIMEDOUT -110 /* 操作超时。 */
```

业务代码不区分完整版或裁剪版，调用方式保持不变：

```c
#include "error.h"

/**
 @brief 擦除指定地址所在的 Flash 扇区。
 @param flash_address 待擦除扇区的起始地址。
 @return 成功时返回 ERROR_OK；地址非法时返回 EINVAL；写保护时返回 EPERM；擦除失败时返回 EIO。
 @note 地址必须按芯片扇区边界对齐，且不得指向当前固件的受保护代码区。
 */
int32_t Storage_Flash_EraseSector(uint32_t flash_address) {
    if (!Flash_IsAddressValid(flash_address)) {
        return EINVAL;
    }

    if (Flash_IsWriteProtected(flash_address)) {
        return EPERM;
    }

    if (Flash_EraseSector(flash_address) != ERROR_OK) {
        return EIO;
    }

    return ERROR_OK;
}
```

宏定义本身不单独占用 Flash。若裁剪后 Flash 实测减小，应在相同工具链和优化选项下对比 MAP 与 BIN 结果，并记录随未使用错误码一同被移除的错误文本、映射表、分支、模块代码或其他段与符号。禁止为了裁剪将错误码宏改写为枚举；这会改变错误码的声明和类型模型，并可能在特定工具链或用法下增加 Flash 或 RAM 占用。

以下示例假定 `rtu_status_t` 是项目定义的有符号状态类型，`rtu_status_ok` 为 `0`，其他错误码均为负数：

```c
/**
 @brief 读取一个 ADC 通道并转换为毫伏值。
 @param channel 输入的 ADC 通道号，范围为 0～drv_adc_max_channels - 1。
 @param voltage_mv 输出电压，单位为 mV，不得为 NULL。
 @return 成功时返回 rtu_status_ok；失败时返回项目错误码头文件定义的负数错误码。
 @note 仅允许在任务上下文调用；最长等待时间为 drv_adc_timeout_ms。
 */
rtu_status_t DrvADC_ReadVoltageMV(uint8_t channel, uint16_t *voltage_mv);
```

## 7. 控制流与错误处理

- **[ERR-001][AUTO-BLOCK]** 不得在条件表达式中赋值；`switch` 必须有 `default`，故意穿透必须有工具可识别的明确注释。
- **[ERR-002][REVIEW-BLOCK]** 错误路径必须释放资源、恢复外设到已知状态或向适当层上报；禁止静默吞掉错误。
- **[ERR-003][REVIEW-BLOCK]** 一次操作中的等待和轮询必须有明确单位、总时间上界及耗尽后的动作；禁止无上限忙轮询。作为任务空闲态的无限事件等待仅在满足 `RTOS-002` 的明确条件时允许，不能用来规避一次操作的响应期限。
- **[ERR-004][REVIEW-BLOCK]** `goto` 只允许作为单一函数内的统一资源清理出口，标签命名为 `cleanup:`；其他用途必须取得豁免。
- **[ERR-005][REVIEW-BLOCK]** 禁止未定义行为，禁止依赖未指明的求值顺序或结果，禁止在无先后保证的子表达式中对同一对象读写或多次修改。确需使用实现定义行为时，必须在项目配置中记录编译器/ABI 依据、适用目标、封装边界及验证方式；例如寄存器整数地址到指针的转换只能在经验证的底层封装中使用。不得将未定义行为登记为实现定义例外；数值运算和转换仍执行 `TYP-003`、`TYP-006`、`TYP-009`。

```c
/**
 @brief 启动示例驱动并完成必要的硬件配置。
 @param config 输入的驱动配置，不得为 NULL。
 @return 成功时返回 rtu_status_ok；失败时返回项目错误码头文件定义的负数错误码。
 @note 仅允许在任务上下文调用。
 */
rtu_status_t DrvExample_Start(const DrvExampleConfig_t *config) {
    rtu_status_t status = rtu_status_ok;

    if (config == NULL) {
        return rtu_status_invalid_argument;
    }

    status = DrvExample_EnableClock();
    if (status != rtu_status_ok) {
        goto cleanup;
    }

    status = DrvExample_Configure(config);

cleanup:
    if (status != rtu_status_ok) {
        DrvExample_DisableClock();
    }
    return status;
}
```

## 8. 指针、内存与缓冲区

- **[MEM-001][REVIEW-BLOCK]** 外部输入的长度、索引、地址、枚举值和帧字段必须在使用前检查范围。
- **[MEM-002][REVIEW-BLOCK]** 数组访问不得越界；长度计算使用 `size_t`，并检查加法和乘法溢出。
- **[MEM-003][REVIEW-BLOCK]** 调用 `memcpy`、`memset` 时必须核对目标容量、操作长度和重叠条件；二者的返回指针无需机械检查。可能重叠时使用 `memmove`。`snprintf` 等有业务意义的返回值必须用于判断错误或截断。
- **[MEM-004][REVIEW-BLOCK]** 禁止将结构体内存直接作为通信或持久化格式；必须显式处理字节序、对齐、填充和版本兼容。
- **[MEM-005][REVIEW-BLOCK]** 不得通过不兼容类型指针强转规避类型系统；寄存器和字节流访问必须封装，并说明对齐与别名假设。
- **[MEM-006][REVIEW-BLOCK]** 运行期动态分配默认禁止；允许的分配阶段、堆实现和失败策略必须写入项目执行配置。ISR 和高频循环中禁止分配或释放。
- **[MEM-007][REVIEW-BLOCK]** 默认禁止变长数组（VLA）和 `alloca` 等运行期栈分配；确需使用时须取得有范围的豁免，证明输入上界、最坏栈占用和超限处理，并纳入任务栈或 MSP 预算。编译器支持时启用相应诊断，不能用禁止 heap 分配代替栈分配检查。
- **[MEM-008][REVIEW-BLOCK]** 将外部字节缓冲区作为 C 字符串使用前，必须在有效可读范围内确认终止字符 `\0`；输出容量必须包含终止字符空间。禁止向 `strlen`、`%s` 等无显式长度接口传入未验证的缓冲区。不得假设 `strncpy` 总会终止；使用 `snprintf` 时先检查负返回值，再比较所需长度与容量并处理截断。二进制帧按显式长度处理，不以字符串终止符判断帧长。

## 9. 宏、预处理与编译条件

- **[PRE-001][ADVISORY]** 优先使用 `static inline`、枚举或 `static const` 代替函数式宏。
- **[PRE-002][AUTO-BLOCK]** 函数式宏必须完整括号化、每个参数只求值一次；多语句宏必须用 `do { ... } while (0)` 包装。
- **[PRE-003][REVIEW-BLOCK]** 公共头文件原则上不得因功能开关而改变公共函数或结构体声明，产品差异优先通过稳定接口、配置结构或实现文件处理。确需裁剪公共 API 时，开关必须集中在项目配置头文件中，并覆盖所有受支持变体的构建和接口测试。
- **[PRE-004][REVIEW-BLOCK]** 每个编译开关必须有默认值、用途、影响范围和维护者；每个有效 `#if` 分支必须被 CI 或发布前周期构建覆盖。

## 10. 中断、DMA 与硬件访问

- **[IRQ-001][REVIEW-BLOCK]** ISR 只允许确认/清除中断源、搬运最少数据、更新受控状态并通知任务；不得阻塞、延时、打印、访问文件系统、复杂解析或动态分配。
- **[IRQ-002][REVIEW-BLOCK]** ISR 与任务共享的数据必须说明生产者、消费者、原子性/临界区措施、缓存一致性和丢失策略；`volatile` 不能替代同步。
- **[IRQ-003][REVIEW-BLOCK]** 项目必须维护 IRQ 优先级表，记录 IRQ 名称、逻辑优先级、写入 NVIC 的编码值、是否调用 FreeRTOS API、最大执行时间和共享资源。
- **[IRQ-004][REVIEW-BLOCK]** 调用 FreeRTOS 的 ISR 必须只使用 `...FromISR()` API，并按需执行 `portYIELD_FROM_ISR()`；其抢占紧迫程度不得高于 `configMAX_SYSCALL_INTERRUPT_PRIORITY` 规定的系统调用上限。Cortex-M 项目必须同时核对 `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY` 与实际 NVIC 编码，并启用 `configASSERT` 捕获非法优先级。
- **[IRQ-005][REVIEW-BLOCK]** DMA 缓冲区必须定义所有权、生命周期、对齐、缓存维护（适用时）和完成/错误/取消通知路径。超时或发出取消请求不等于 DMA 已停止访问；释放、复用或重新挂接缓冲区前，必须依据目标硬件及驱动契约确认 DMA 已停止访问，并处理可能迟到的中断/回调。停止完成的判据、缓存或屏障要求及停止失败的处理方式必须明确，禁止仅清软件标志就归还缓冲区。
- **[IRQ-006][REVIEW-BLOCK]** 寄存器访问仅允许在 BSP/驱动层；读改写前必须确认并发和硬件语义，包括写 1 清零、只写与保留位。
- **[IRQ-007][REVIEW-BLOCK]** 外设初始化、引脚复用、时钟和 IRQ 优先级必须集中配置；禁止不同模块重复初始化同一外设。

## 11. FreeRTOS、栈与堆

- **[RTOS-001][REVIEW-BLOCK]** 每个任务必须记录职责、阻塞条件/周期、优先级、栈预算、看门狗策略、输入队列和输出接口。
- **[RTOS-002][REVIEW-BLOCK]** 任务不得无延时忙等；周期任务使用 `vTaskDelayUntil()`，事件任务阻塞在队列、通知、信号量或事件组上。有响应期限、超时恢复或周期健康检查职责时，必须设置满足该职责的有限超时。没有待完成操作的事件任务可在设计论证后无限等待，但必须记录唤醒源、所持资源、健康监督方式及适用的取消/停机路径，不能持有其他任务继续运行所需的锁。使用 `portMAX_DELAY` 时须核对具体 API、内核版本和 `INCLUDE_vTaskSuspend` 配置下的实际语义；长期无事件不能被误判为任务失活。
- **[RTOS-003][REVIEW-BLOCK]** 队列传递指针时，接口必须声明对象生命周期、所有权转移和释放责任。
- **[RTOS-004][REVIEW-BLOCK]** 共享可变状态优先消息传递；确需共享时必须使用 mutex、临界区或经验证的原子操作。临界区不得包含日志、延时、外设等待或阻塞 API。
- **[RTOS-005][REVIEW-BLOCK]** Mutex 只能在任务上下文使用；ISR 与任务同步必须使用任务通知、队列或 ISR 安全的信号量 API。
- **[RTOS-006][REVIEW-BLOCK]** 项目必须为每个任务定义 `stack_budget_bytes` 和 `min_free_bytes` 验收阈值；在目标板压力场景测量高水位并统一换算为字节。未达到阈值不得发布。
- **[RTOS-007][AUTO-BLOCK]** FreeRTOS 项目必须启用 `configCHECK_FOR_STACK_OVERFLOW >= 2` 和栈溢出 Hook；启用堆时还必须启用 malloc-failed Hook。
- **[RTOS-008][REVIEW-BLOCK]** MSP/中断栈必须结合链接图、最大嵌套中断和最坏调用链设置预算，并在发布检查中保留余量证据。
- **[RTOS-009][REVIEW-BLOCK]** 使用 FreeRTOS heap 时必须固定 heap 实现、总预算、允许分配阶段和失败动作；发布测试必须记录最小历史剩余堆，低于项目阈值时阻断发布。

## 12. 状态机、时间与看门狗

- **[TIM-001][REVIEW-BLOCK]** 复杂业务流程必须采用可追踪的显式状态机；一次调度必须在有限时间内返回，长操作拆为状态或异步事件。
- **[TIM-002][REVIEW-BLOCK]** 模块内部必须声明统一时间基准和单位，变量名带单位；tick、毫秒和 RTC 秒可以在明确边界转换，但转换必须集中、检查溢出，不得在业务表达式中随意混算。
- **[TIM-003][REVIEW-BLOCK]** tick 超时必须使用回绕安全的差值比较，例如 `(TickType_t)(now - start) >= duration`；禁止直接以 `now >= deadline` 判断。单次持续时间必须小于 tick 全范围的一半。
- **[TIM-004][REVIEW-BLOCK]** 嵌套调用必须共享同一个总超时预算，并根据已耗时传递剩余时间；禁止每层重新启动完整超时。
- **[TIM-005][REVIEW-BLOCK]** 喂狗只能由确认关键任务健康的监督者执行；禁止在普通循环或 ISR 中无条件喂狗。
- **[TIM-006][REVIEW-BLOCK]** 故障必须区分可重试、需降级和需复位；一次操作的重试必须有最大尝试次数或总时间预算，并明确是否计入首次尝试、失败终止动作和资源恢复方式。只限制退避间隔不能保证重试结束。长期重连等持续服务须作为有设计依据的独立状态，明确每次尝试的超时、退避策略、退出/取消条件、资源及健康监督约束，不得隐藏在一次同步调用的无限重试循环中。

## 13. 日志、断言与诊断

- **[DIA-001][REVIEW-BLOCK]** 日志必须带模块和事件上下文；不得输出密钥、完整凭据、敏感数据或未初始化缓冲区。
- **[DIA-002][REVIEW-BLOCK]** 高频正常路径不得无节制打印；日志等级、速率和编译开关必须可控。
- **[DIA-003][REVIEW-BLOCK]** `assert` 只验证开发期不变量，不得替代生产错误处理；失败动作必须由项目配置明确。
- **[DIA-004][REVIEW-BLOCK]** 故障码必须稳定、可检索，并记录含义和恢复动作。

## 14. 注释与需求追溯

- **[DOC-001][REVIEW-BLOCK]** 关键逻辑注释必须解释原因、约束或风险，不得只复述代码；公共 API、协议、非直观位操作、并发边界和硬件时序必须有有效注释。
- **[DOC-002][REVIEW-BLOCK]** 硬件地址、容量、时钟、超时和协议常量必须注明依据，依据至少精确到链接脚本文件及区域、分区表版本及表项、原理图页码、芯片手册版本及章节、协议版本及章节或需求编号之一。安全、OTA、存储一致性和故障恢复逻辑必须关联需求、缺陷或测试编号。
- **[DOC-003][AUTO-BLOCK]** 禁止保留大段注释掉的代码；临时事项统一写为 `/* TODO(负责人, YYYY-MM-DD): 原因; task ID. */`，其中负责人必须是可识别的个人或团队标识，日期是预计清理截止日，task ID 必须可追踪。
- **[DOC-004][REVIEW-BLOCK]** 多行 C 块注释（`/* ... */` 或 `/** ... */`）的中间行不得使用行首 `*` 作为装饰字符；直接书写句子或标签，避免上下文被 `*` 视觉隔开。普通注释可使用 `/* ... */` 或 `// ...`；文件、函数、类型、宏的声明级说明以及需要跨行解释的关键逻辑优先使用块注释。
- **[DOC-005][REVIEW-BLOCK]** 团队自研的新增 `.c` 和 `.h` 文件必须在许可证或归属声明之后、include guard 或 `#include` 之前添加中文文件注释，至少使用 `@file` 标识文件并用 `@brief` 说明文件职责；存在职责边界、输入输出、资源所有权或调用上下文限制时使用 `@note` 说明。文件头不得维护作者、日期或手工变更历史，这些信息以版本控制记录为准。
- **[DOC-006][REVIEW-BLOCK]** 团队自研的新增或有效代码发生修改的函数必须使用中文块注释，并至少使用 `@brief` 说明用途。存在参数时，每个参数分别使用 `@param` 说明含义，并按适用情况说明输入/输出方向、单位、范围、所有权和能否为 `NULL`；存在非 `void` 返回值时使用 `@return` 说明成功和失败语义；存在任务/ISR 上下文、锁前提、可重入性、阻塞时间、副作用或其他调用限制时使用 `@note`。公共函数的权威注释放在 `.h` 声明前，文件内私有函数放在 `.c` 定义前，头文件内的 `static inline` 函数放在定义前；公共函数定义处不得机械复制同一注释。
- **[DOC-007][REVIEW-BLOCK]** 团队自研的新增或修改结构体、联合体必须在类型定义前使用中文块注释说明整体用途，并为每个成员说明业务含义；存在单位、范围、特殊值、生命周期、所有权、对齐或并发访问要求时必须一并说明。注释不能替代显式序列化，协议、寄存器和持久化格式仍不得直接依赖结构体布局。
- **[DOC-008][REVIEW-BLOCK]** 团队自研的新增或修改枚举必须在类型定义前使用中文块注释说明状态或取值域，并为每个枚举值说明业务含义。用于协议或持久化格式的枚举值必须显式赋值并注明协议名称、版本和章节，不得依赖声明顺序或枚举底层宽度。
- **[DOC-009][REVIEW-BLOCK]** 除 include guard 和 `NAM-008` 明确列出的兼容符号外，团队自研的新增或修改宏必须使用中文注释说明用途。对象式数值宏还必须按适用情况说明单位、范围和依据；函数式宏必须使用 `@param`、`@return` 和 `@note` 说明参数、结果及求值限制；配置开关必须说明默认值、影响范围和维护者。来源相同且相邻的一组宏可以共用一段范围明确的依据说明，但每个宏仍须说明自身含义。
- **[DOC-010][REVIEW-BLOCK]** 团队自研代码中新增或修改的说明性注释必须使用中文；标识符、寄存器名、协议字段、标准术语和 Doxygen 标签可以保留英文。`error.h` 中既有 errno 风格条目及外部固定接口按 `NAM-008` 豁免，项目新增内容仍须使用中文。禁止编写只翻译符号名称、与代码行为不符或无法长期维护的注释。

`/**` 和 `*/` 仅作为边界，中间行不添加装饰性 `*`。文件职责注释示例：

```c

 @brief 实现 RS485 半双工收发、方向控制和 DMA 完成处理。
 @note 本文件只负责驱动层，不解析 Modbus 或 OTA 业务协议。
 */
```

函数注释示例：

```c

 @brief 查看指定卡片的余额。
 @param card_id 输入的卡片标识符缓冲区，不得为 NULL。
 @param card_id_size card_id 的长度，单位为字节，必须符合卡片协议要求。
 @param balance 输出余额，单位为分，不得为 NULL。
```

## 15. NVM、OTA 与可恢复性

### 15.1 Flash/FRAM 持久化

- **[NVM-001][REVIEW-BLOCK]** 持久化记录必须显式定义 magic、格式版本、长度、递增序号和完整性校验；多字节字段必须固定字节序，不得直接写入 C 结构体镜像。
- **[NVM-002][REVIEW-BLOCK]** 更新必须采用掉电可恢复策略，例如双槽、日志或“写数据—校验—最后提交标记”；启动时只能选择完整且有效的最新记录。
- **[NVM-003][REVIEW-BLOCK]** 格式变更必须给出向前/向后兼容或迁移策略，以及失败后的安全默认值；不得无版本地改变已发布布局。
- **[NVM-004][REVIEW-BLOCK]** Flash 写入必须检查地址范围、对齐、擦写粒度、寿命和错误返回；FRAM 同样必须检查地址范围、总线错误和部分写入。
- **[NVM-005][REVIEW-BLOCK]** R2 验证必须覆盖每个提交阶段的掉电/复位、损坏记录、序号回绕及双槽均无效场景。

### 15.2 OTA/Boot

- **[OTA-001][REVIEW-BLOCK]** 接受镜像前必须验证产品/硬件型号、目标地址范围、长度、版本策略和完整性；联网产品还必须验证签名或可信 MAC。CRC 只能发现偶然损坏，不能代替真实性验证。
- **[OTA-002][REVIEW-BLOCK]** 下载区、运行区和 Boot 写入边界必须由链接和分区配置唯一确定；任何长度或地址计算溢出都必须拒绝镜像。
- **[OTA-003][REVIEW-BLOCK]** 升级过程必须在断电、校验失败或首次启动失败时回到已知可用镜像或安全恢复模式；回滚判据、启动尝试次数和确认新镜像的时机必须明确。
- **[OTA-004][REVIEW-BLOCK]** R2 验证必须覆盖中断下载、中断写入、镜像损坏、错误型号、版本拒绝、启动失败和回滚；发布包必须保留镜像哈希、签名状态和对应源码版本。
- **[OTA-005][REVIEW-BLOCK]** Boot 与应用必须定义启动交接契约：跳转前验证入口和初始栈值符合目标内核及链接布局，栈值满足对齐与有效栈区约束，并明确允许的栈顶边界；明确向量表定位/重映射、栈与执行模式、中断屏蔽及挂起状态、系统时基、外设/DMA、时钟和看门狗由哪一侧接管。缓存及屏障按目标内核要求处理，不得把某个 Cortex-M 的 VTOR 或跳转序列无条件套用到所有 MCU。交接代码及其调用约束必须有编译器/架构依据，并以目标板验证有效镜像交接、非法入口拒绝及交接时未完成中断/DMA 的处置。

## 16. C 风险扩展、评审与热修复

### 16.1 C 风险扩展

协作方式以项目基线为准，适用边界见 [共享治理基线](../共享/团队治理与评审基线.md)。多人团队按 R0/R1/R2 登记风险；个人+AI 可引用已有协作记录中的风险及技术影响说明，不要求另填一套 R 等级。技术验证仍按实际变更适用 R0/R1/R2 的门槛，不能把 AI 权限等级直接换算成 R 等级或降低证据要求。无法确定技术风险时按更高一级处理。

C 的 R2 触发项见第 1.1 节。R1/R2 的基础证据仍须包含 clean build、零新增警告和与风险匹配的主机或板级测试；个人+AI 项目涉及同类变化时同样适用。专项规则中的 R2 测试要求按技术影响执行，不依赖是否另填 R 标签。

- **[REV-001][REVIEW-BLOCK]** 多人团队的每个模块必须在现有责任记录或 [共享责任模板](../共享/模块责任与轮值模板.md) 实例中登记主负责人和备份，负责人不拥有跳过评审的特权。个人+AI 记录实际责任人及批准来源，不虚设备份或轮值角色。
- **[REV-002][REVIEW-BLOCK]** 多人团队的评审人数与作者不得自批要求按 [共享治理基线](../共享/团队治理与评审基线.md) 执行；个人+AI 按项目明确采用的协作规范执行自检、必要独立复审和用户确认，不能自行取消已有团队要求。
- **[REV-003][REVIEW-BLOCK]** 检查记录必须能追溯风险或技术影响、变更范围、验证结果、资源变化、兼容/回滚影响及适用豁免，可直接使用现有里程碑或等价记录。[C 检查索引](pr_checklist.md) 的 19 项门禁只核对适用项；同组不适用项可合并说明依据，未执行项须标为未验证。同一对象、配置和覆盖范围的有效检查结果只记录一次，其他位置引用，不重复填写完整表单或抄写规则。
- **[REV-004][AUTO-BLOCK]** 目标配置必须构建成功且零新增警告；生成物、Keil `OBJ/`、`Listings/`、用户 `.uvguix` 和编辑器日志不得进入提交，项目明确要求归档的发布产物除外。
- **[REV-005][REVIEW-BLOCK]** R1/R2 测试必须可复现，记录固件版本、硬件版本、配置、输入、预期、实测和日志/波形/抓包位置；“能编译”不等于功能验证。
- **[REV-006][ADVISORY]** 人工代码超过 300 行或涉及超过 8 个代码文件时，在约定检查点评估能否理解、验证和回退；团队由作者与评审者共同判断。这是负荷提醒，不因数量单独增加审批或独立复审，也不机械拆片。

技术检查至少覆盖本次适用的错误返回和资源恢复、长度/溢出/字节序/对齐、并发/ISR、栈/堆预算、协议/NVM/OTA 兼容及回滚，以及无关改动。将这些内容并入已有自检或集中复审，保留设计一致性、规范符合性和功能验证的分项结论；通过项简记，具体问题再展开。

### 16.2 生产热修复接口

热修复只用于已影响生产、现场服务或安全的紧急缺陷，不用于绕过普通开发流程；适用方式和操作步骤见 [共用热修复流程](../共享/豁免与紧急修复流程.md)。已有里程碑或事件记录覆盖必要字段时直接引用，不要求另建热修复单。

- **[HOT-001][REVIEW-BLOCK]** 热修复单必须记录事件编号、影响、根因假设、最小改动范围、风险等级、部署步骤、回滚包/回滚步骤和负责人。
- **[HOT-002][REVIEW-BLOCK]** 部署前至少完成目标配置 clean build、零新增警告、针对缺陷的冒烟测试，并履行项目所采用流程的批准；多人团队至少取得 1 名非作者批准。无法执行的检查必须逐项记录风险和补偿措施。
- **[HOT-003][REVIEW-BLOCK]** 多人团队的 R2 热修复可在紧急情况下先由 1 名非作者批准部署，但须在下一个工作日补齐第二名评审。两种协作方式均须按共用流程补齐完整专项测试、所采用流程要求的复审和事故复盘；未补齐前不得关闭事件。
- **[HOT-004][REVIEW-BLOCK]** 热修复必须保持可回滚；部署后按约定观察关键指标，触发回滚判据时由事件负责人执行既定回滚。
